# ライン管理カレンダー — 設計

画面は Flask + HTML/CSS/JS、業務ロジックは Python、データは**すべて SQLite**。
元は Excel VBA + Access のツールで、業務判断は VBA の移植です。
取り込み元は VER3.1.0 で `.accdb` から `.sqlite3` へ寄せました(§4.1)。

構成は社内「汎用Webアプリ作成 基盤仕様書」に沿っています。
節番号(例: 基盤仕様書 2.4)はその文書を指します。

---

## 1. 守っている約束

破ると必ず事故になるので、**違反はバグとして扱います**。

1. **業務判断はすべて Python**。JS が持つのは「ビューモデル → DOM」の
   純関数と、選ばせる順番だけ。二重に持つと、テストの無い側に分裂する
2. **APIは更新後のビューモデル一式を返す**(差分ではない)。この規模
   (42セル・数KB)で差分を使う利点は無く、画面側の不整合バグの温床になる
3. **HTTPステータスで断りの種類を分ける**
   - `400` 入力の形が違う。**サーバの状態は動いていない**
   - `422` 形は正しいが業務として断る
   - `409` 別の誰かが先に変えていた
4. **断りの種類は `code` 定数で運ぶ**。文言から推し量らない
   ── 文言を直した日に区別が壊れる
5. **同じ事実を2か所に持たない**。持つと必ずどちらかが古くなる
6. **一覧に無いものは選べない**。画面で絞るだけでなくサーバでも確かめる
7. **色だけで意味を運ばない**。色の出どころは `tokens.css` ただ1つ
8. **正式なデータは共有の取り込み元(`.sqlite3`)だけ**。手元の SQLite は
   表示用の写しと送信待ちの置き場にすぎない(§4)

## 2. 構成

```
Start.vbs ─▶ start_app.py ─▶ launch_guard.py ─▶ server.py (waitress)
  (通常)       (環境確認)      (プロセスを1つに)   │
                                                   ├─ boot_server (待機画面だけ) ─▶ ブラウザ
                                                   └─ 差し替え ─▶ app/ (Flask)
start.bat ─▶ 同じ経路(コンソール表示・診断ログ詳細)
stop.bat  ─▶ process_manager.py ─▶ POST /api/shutdown → 応答が無ければPIDで停止
画面を閉じる ─▶ 心拍が途切れる ─▶ idle_exit ─▶ 同じ停止の道
タブを2枚開く ─▶ screen_lock ─▶ 2枚目は断る(画面を1枚に)
```

```
  ブラウザ                app/templates/*.html   画面の骨格(Jinja2)
                          app/static/js/         描画と入力(ESモジュール)
                          app/static/css/        tokens.css が色の唯一の出どころ
        │ fetch / JSON(同一オリジン)
  ─────▼──────────────────────────────────────────────
  app/routes/                   Blueprint。入力の形だけ見て下へ渡す
  app/shell.py                  帯とレール(外枠)に渡す値
  calendar_app/presenters/      ビューモデルの組み立て
  calendar_app/repository.py    業務ロジック(VBA modData / modDB)
  calendar_app/holiday.py       祝日判定(VBA modHoliday)
  calendar_app/sync_service.py  同期を回す(プロセスに1つ)
  calendar_app/admin_password.py 設定を変えるときの関門
  calendar_app/terminals.py     どのPCがどの設定かの一覧
  calendar_app/sync/            取り込み元への送信・削除の転送・業務ルール
  calendar_app/dbkit/           他プロジェクトと共通のDB基盤
  calendar_app/accdb/           .accdb の読み取り。**変換ツールだけが使う**
  ─────┬──────────────────────────────────────────────
        ▼
   SQLite(手元・写し + 送信待ち)  ⇄  .sqlite3(共有・正)
```

**SPA にしていません。** ルータ・状態管理・ビルド工程という3つの複雑さに
見合うものが、画面2つのこの規模では得られないためです。npm も webpack も
使わないので、社内端末では `pip install -r requirements.txt` だけで動きます。

**画面の移動でも soft-nav をしていません**(参考にした梱包資材ツールは
`nav.js` で `<main>` を差し替えています)。あちらは画面が7つあり、移動が
頻繁なので「同じ画面の中に居る感覚」に価値がありました。こちらは
カレンダーと設定の2つで、設定はほぼ最初の1回しか開きません。素の
リンクにしておけば、行き先とURLの対応をサーバだけが持ち、モジュールの
使い回しに伴う後始末(listener とタイマーの切り忘れ)も起きません。

### 状態の置き場所

| 持ち物 | 置き場所 | なぜそこか |
|---|---|---|
| 同期の状態・送信待ちの件数 | `sync_service`(プロセスに1つ) | 画面を閉じても同期は続く。画面に持たせると、タブを閉じたとたん送信待ちが溜まる |
| 表示中の月 | 画面(`views/calendar.js` の `view`) | 1画面の中で完結し、保存する意味が無い |
| この端末の設定(ライン・取り込み元の場所) | `settings.json` | PCごとに違う。VBA はレジストリだった |
| 業務データ | 手元の SQLite → 取り込み元 | §4 |

画面側にも1か所だけ「持ち物」があります。**同期状態の写し**
(`app/static/js/sync.js`)で、`GET /api/sync` を叩くのはここだけです。
帯・レールのバッジ・設定画面の3つが要りますが、それぞれが叩くと
**同じ事実を三か所で持つ**ことになります。見張りは1本にして、欲しい側が
`subscribe()` で受け取ります(間隔は送信待ちがあれば1秒、無ければ15秒)。
**判断は何もせず、返ってきたものを写すだけ**です。

`sqlite3` の接続はスレッドをまたげないので、**要求ごとに取り直します**
(`app/__init__.py` の `get_db`)。waitress は要求ごとに別スレッドで
処理するため、プロセスに1つ持ち回すことはできません。

## 3. 起動と停止

### 3.1 待機画面より前に、重いものを置かない

起動でいちばん時間を食うのは **Flask とアプリ本体の import** です。
それを済ませてからブラウザを開くと、待機画面が出るころには待つ理由が
ほぼ終わっています ── 出す意味がありません。

    ポートを決める → 待ち受け開始(待機画面だけ)→ ブラウザ
        → 本体を組み立てて差し替え → 重い初期化 → 準備完了

最初の3つは標準ライブラリと `app_config` だけで済みます。
差し替えは `boot_server.Handover` が WSGI の呼び先を入れ替えることで行い、
**待ち受けを開き直しません** ── 開き直すと、その瞬間の問い合わせが落ちて
画面が「接続できません」に見えます。

待機画面の骨格は `calendar_app/boot_screen.py` に**1つだけ**あり、
起動サーバ(Flask 前)と Flask 側の `/` の両方が同じものを出します。
2枚持つと、直したほうと直していないほうが場面によって出ます。

段は4つ(実行環境 / 準備 / 同期 / 完了)。進捗率を正確に出すことではなく、
**無反応に見える時間をなくし、失敗時の次の行動を示す**のが目的です。

### 3.2 確実に終わる

窓が無いアプリなので、**タブを閉じたら終わったつもりになります。**
残っていると、次の起動が「すでに起動しています」と判定して、入れ替えた
新しい版がいつまでも動きません。3つの道すべてが同じ `srv.stop()` を通ります。

| 何をしたか | 道 |
|---|---|
| 画面の [終了] | `POST /api/shutdown` |
| `stop.bat` | `process_manager.py` → `POST /api/shutdown` → 駄目ならPID |
| タブを閉じた | 心拍が途切れる → `idle_exit` |

**同期中は止めません。** 送信の途中で落とすと、取り込み元へ届いたかどうかが
分からないまま終わります。`409` を返して、中断してよいかを利用者に選ばせます
(`--force` / 画面の「中断して終了」)。

`waitress` の受付の輪は、つながったままの接続が1本でもあると回り続けます。
`server.close()` が閉じるのは待ち受けソケットだけなので、ブラウザの
keep-alive 接続を別途閉じないと**プロセスが残ります**
(`AppServer._close_open_connections`)。さらに `start_app._hold_until_stopped`
が上限つきで待ち、それでも終わらなければ `os._exit` で確実に落とします。

### 3.3 多重起動 ── プロセスを1つに絞る

> 「多重起動」には**2つある**ので、分けて書きます。ここは**プロセス**の話
> (`launch_guard`)、次の 3.4 は**画面(ブラウザのタブ)**の話
> (`screen_lock`)。片方を止めても、もう片方は止まりません。

**入口はOSの排他ロックでひとつに絞ります**(`launch_guard.StartupLock`)。
`runtime/instance.lock` に `fcntl.flock` / `msvcrt.locking` を掛け、
プロセスが生きているあいだ握り続けます。

ロックファイルの中身を読む判定だけでは足りません。判定から書き込みまでに
1〜2秒の窓があり、**そこに2つ入ると両方が起動します。** `Start.vbs` は
画面が出ないので、反応が無いと思った人がもう一度ダブルクリックする ──
ちょうどこの窓です。実際に2つ動き、しかも**ポートの取り合いに負けたほうが
「起動しました」と言って終わり、生きているほうのロックを消していきました。**

OSに預けるのは、**stale という状態を作らないため**です。自分で「起動中」の
印を置くと、電源が落ちたときに消えない印が残り、それを賢く判定しようと
するほど壊れやすくなります。OSのロックはプロセスが死んだ時点で必ず
解放されます。

入口を通ったあと、誰が動いているかは2段構えで見ます:

1. PIDのプロセスが存在するか(PIDは使い回されるので、これだけでは足りない)
2. そのポートの `/api/health` が**同じ `app_id`** を返すか
   (別のアプリがHTTPを返していることがあるので、これだけでも足りない)

| 決めごと | なぜ |
|---|---|
| 入口のロックは**判定より先**に取る | 判定と書き込みのあいだの窓を無くす |
| 入口が取れなければ `check_existing` に任せる | 「先に居るから合流」と決め打つと、**古い版が動いているとき新しい版が永久に動かない**(古い版が入口を握ったままになる) |
| ロックが無くても**常用ポートを叩く** | ロックファイルは消える(手で・掃除ツールで・落ちたプロセスに持っていかれて)。「ロックが無い = 誰も居ない」と決めると、8730 で自分が動いているのに 8731 に立てる |
| 消えたロックは**持ち主が書き直す**(`keep_lock`) | 外から分かるのはポートまでで、**起動トークンが失われる**。すると `stop.bat` も版の入れ替えも「止められない」状態になる |
| 終了時は**自分のロックだけ**消す | 無条件に消すと、あとから起動して落ちたプロセスが生きているほうのロックを持っていく |
| 待ち受けの失敗は**値で持ち帰る**(`AppServer.listen_error`) | 別スレッドで開始するので例外が届かない。届かないまま「起動しました」と言うのが一番悪い |

**版が違えば合流しません。** 入れ替えたのに古いプロセスが残っていると、
「すでに起動しています」と答えて古いほうのブラウザを開いてしまいます。
版が違うときは古いほうへ停止を頼み、終わってから立て直します。

### 3.4 画面(タブ)を1枚に絞る

起動を1つに絞っても、**ブラウザのタブは何枚でも開けます。** 3.3 は
そこには効きません(同じプロセスに繋がるだけなので、合流したことにすら
ならない)。ところが2枚開くと、**どちらでも登録できて、どちらも
「自分が見ているものが最新」の顔をします。**

* 片方で登録 → もう片方は古い月を出したまま(気づくのは次の描き直し)
* 設定を両方で開く → 後から保存したほうが黙って勝つ
  (先に直したほうの人は、直したつもりのままになる)
* 削除のダイアログを開いたまま、もう片方で同じ日を触る

どれも「壊れた」とは見えず、**どちらが本当か分からない**という形で出ます。
そこで**使ってよい画面を1つだけ**にし、2枚目は開いた時点で断ります
(`calendar_app/screen_lock.py`)。

```
画面を開く ─▶ POST /api/screen/claim {screen_id}
                 ├ 誰も居ない / 同じ画面 / 前の画面が45秒無反応 → 200
                 └ 別の画面が使用中 → 409 other_screen + 誰がいつから
心拍(20秒) ─▶ POST /api/alive {screen_id} → {"active": false} なら画面を塞ぐ
タブを閉じる ─▶ sendBeacon {leaving:true} → その場で空く
```

| 決めごと | なぜ |
|---|---|
| 画面の名前は `sessionStorage` に持つ | **タブごとに別で、画面遷移(カレンダー↔設定)では変わらない。** 「同じタブの中で移動しただけ」と「もう1枚開いた」を取り違えない |
| **取って代われる道を必ず残す**(「この画面で使う」) | ブラウザごと落ちた・PCが固まった、で合図が届かないことがある。締め出されて何十秒も待たされるほうが現場では困る |
| 45秒(`SCREEN_STALE_SEC`)心拍が無ければ空ける | 心拍は20秒ごと。2回落としても持ちこたえ、かつ次の人を待たせすぎない長さ |
| **裏に回った画面は空けない**(`hidden`) | ブラウザは裏のタブの心拍を間引く・止める。空けると Excel を見ているあいだに2枚目が黙って入れる(§8.5) |
| 守りは**サーバ側**に置く | 画面側だけで塞ぐと、「断ったのに書ける」経路が残る。登録・削除・設定変更は `X-Screen-Id` を見て 409 で断る |
| 断るのは**書くときだけ** | 見るだけなら害が無い。塞いだ画面にも状態は出したい |
| **名乗らない相手は判定しない** | `stop.bat` やコマンドからの取り込みは画面を持たない。**止められなくなるのが一番困る**。守りたいのは「2枚目のタブ」で、画面は必ず名乗る |
| `/api/alive` は画面を問わず受ける | 外れた画面も送ってくる ── **そう返すために受ける必要がある**(黙って古い表示を続けさせない) |
| 塞ぐ面はモーダルより上(`z-index:400`) | 削除の確認を開いたまま取って代わられることがある |

これは**プロセスに1つ**の判断で、ファイルには何も残しません。起動し直せば
まっさらになります ── 画面の話なので、プロセスより長生きする必要が無い。

## 4. データ ── 正式なのは取り込み元だけ

各PCのローカル SQLite は、次の2つの役割しか持ちません。

* 表示を速くするための**読み取り用の写し**
* まだ取り込み元へ送れていない入力を貯めておく**送信待ちの置き場(outbox)**

```
 L-1 のPC   [SQLite] ─┐  送信(標準の sqlite3)
 HVC のPC   [SQLite] ─┼─→ 共有フォルダの 連絡帳.sqlite3 (正)
 コイルのPC [SQLite] ─┘  ←─ 取り込み
```

処理の流れ:

```
入力 → ローカル SQLite に保存 (即座に画面へ反映)
         ↓ 直後に自動で
       取り込み元へ送信 (送れたら送信待ちから消す)
         ↓ 一定間隔 (既定 20 秒) で
       取り込み元から取り込み直す (他ラインの登録が見えるようになる)
```

* **読み書きとも標準の `sqlite3`**(`dbkit/source_db.py`)。
  ドライバも Access 本体も要りません
* **送れなかった場合** — 送信待ちに残り、次の機会に送り直します。
  **入力が失われることはありません**

**未送信の入力があるうちは取り込みません。** 取り込みはテーブルを
入れ替えるため、まだ取り込み元に届いていない入力が消えるからです。

### 4.1 なぜ Access をやめたか(VER3.1.0)

取り込み元を `.accdb` から `.sqlite3` へ寄せ、約1,900行を捨てました。

| | Access のころ | いま |
|---|---|---|
| 読み取り | `.accdb` のバイナリを自前で解析 | 標準の `sqlite3` |
| 書き込み | ODBC(`odbc32.dll` を ctypes で直呼び)か `cscript` + ADODB | 標準の `sqlite3` |
| 書けない端末 | 反映用ファイルを書き出し、別PCで流す手動運用 | **無くなった** |
| 書き込み経路の試験 | Windows + ACE が要り、開発機では1行も動かせなかった | **そのまま試験できる** |

決め手は最後の行です。**壊れても気づくのは現場で使ったとき**で、しかも
症状は「保存できたつもり」でした。いまは `test_sync.py` と
`test_web_master.py` が、本物の取り込み元を作って**実際に書かれた中身**まで
見ています。

消したもの: `dbkit/access_odbc.py`、`sync/exporter.py`(反映用ファイルの
書き出し)、`accdb/importer.py`、`tools/export_to_access.py`。
`accdb/reader.py` だけは残してあり、**変換ツール
(`tools/convert_accdb.py`)専用**です。

### 4.2 共有フォルダ上の SQLite で気をつけること

Access はレコード単位のロックを持っていました。SQLite の SMB 上での
ロックは OS 任せで、**壊れ方が「エラー」ではなく「破損」になりうる**のが、
この構成の唯一の弱点です。

| 対策 | なぜ |
|---|---|
| `journal_mode = DELETE`(**WAL にしない**) | WAL は共有メモリ(`-shm`)を使う。SMB にはそれが無く、WAL のまま置いたファイルは誰からも開けなくなる |
| `busy_timeout`(10秒) | 他ラインが書いている最中でも、すぐ諦めない |
| 書き込みは**1文ずつ短いトランザクション** | 掴んでいる時間が短いほど、鉢合わせも途中で切れる危険も減る |
| **書く前に控えを取る**(`backup\`、直近10世代) | 万一壊れても戻せる状態を先に作る |
| 控えは **`sqlite3` の写し取り**で作る(丸写しにしない) | 丸写しは、写している最中に他の端末が書いていると**途中が混ざる**。「控えがあるつもりで戻せない」が一番たちが悪い。開けないファイルのときだけ丸写しに落とす |
| 控えは**続けて取り直さない**(`BACKUP_MIN_INTERVAL_SEC` = 5分) | 1行直すたびに共有を丸ごと読むと、台数ぶん行き来が増える。守りたいのは「戻せる状態がある」ことで、編集1回ごとの世代ではない |
| 取り込みは **1つの時点から読む**(`reading()`) | 休み管理・削除履歴・班員名簿を続けて読むので、1文ずつだと合間に書かれて**表どうしがずれた組み合わせ**を取り込む。読んでいる間は他の端末が書けないが、読むのは一瞬なので釣り合う |

**開き方は3通りを順に試します** ── URI(`mode=ro`)→ 素のパス →
手元への写し。共有フォルダでは1つ目が通らないことがあり、「開けません」
だけで止めると現場では原因に辿り着けません。写しから読んだときは
**その旨を必ず言います**(中身が少し古いことがある)。
写しは**読み取りのときだけ**で、書き込みには決して使いません。

**開けたかどうかは、引けたかどうかで決めます。** `sqlite3.connect()` は
ファイルに触らないので、成功しても何も分かりません。実際に
`SELECT ... FROM sqlite_master` を1回引いて確かめます。

### 二重登録の防止

VBA は登録前に毎回 Access へ問い合わせていました(`ExistsRecord`)。
Python 版は手元の SQLite しか見られないため、**別のラインが同じ作業者を
同じ日に登録していても、登録時点では気づけません。** そこで送信の直前に
取り込み元へ問い合わせ、同じ日・同じ識別コードの行があればその1件を
送りません(`sync/business_rules.py` の `duplicate_guard`)。

**取りやめたことは、その端末の画面に知らせます**(`sync/notices.py`)。
以前はデバッグログに残るだけで、後から届いた側の画面は「登録しました」の
まま ── 先に届いた側と直や繋ぎが違えば、**こちらで選んだ内容が黙って
消えていました**(2台で同時に登録して確かめたときに見つかった)。

| 決めごと | なぜ |
|---|---|
| 取りやめた行を手元の `_sync_meta` に覚え、`GET /api/sync` の `skipped` で返す | 帯が数秒ごとに読むので、開いている画面にすぐ届く。取り込み元へは書けない(相手は他の端末の登録) |
| **[閉じる] を押すまで出す**(`POST /api/sync/skipped/ack` で消す) | 一瞬のトーストは見落とす |
| 出すのは**使っている画面だけ** | 2枚目のタブで押しても書き込みは断られる。操作の途中(モーダルを開いている)にも割り込まない |
| 文言はサーバが組む | 画面は写すだけ(§1) |

**送信の二重適用は別の話です。** こちらは送信1回ごとの**送信ID**と、
取り込み元側の一意索引で防ぎます(`dbkit/outbox_sync.py`)。
同じ送信が2回届いても2行にはなりません。業務上の重複と、同じ送信が
2回適用されることは、原因も対策も違うので分けてあります。

### 4.3 消しすぎない・上書きしない(あとから直した)

書き込みが衝突して**壊れる**ことは起きていませんでした(6台から同時に
送っても欠けは出ません)。起きていたのは、衝突していないのに
**黙って消える**2つです。どちらも**その場では気づけません** ──
消した人の画面では消えていますし、直した人の画面では直っています。

#### 消しすぎ ── 他のラインの行まで消えていた

削除の転送は、取り込み元の ID がまだ分からないあいだ**自然キー**で
対象を指します。そのキーが `日付・区分・登録内容・識別コード` だけで、
**班もラインも入っていませんでした。** 連絡は識別コードが `-` 固定なので、
手がかりは日付と文面だけです。

> 2つのラインが同じ日に「残業なし」と出す → 片方が自分の1件を消す
> → **両方消えた**

| 直したこと | なぜ |
|---|---|
| 自然キーに**班・ライン**を足す | 手がかりを増やさないと絞れない |
| **1行だけ消す**(`build_delete_one`) | 自然キーは一意とはかぎらない。`DELETE ... LIMIT` は使えない作りの SQLite があるので `rowid` の絞り込みで行う |

消し足りないほうは次の転送でまた当たります。**消しすぎたぶんは戻せません。**

#### 上書き ── 先に直した人の修正が消えていた

マスタ管理の画面は鍵以外の**全列**を送ります。2人が同じ行を開くと、
後から保存したほうが、自分が触っていない欄まで**開いたときの写し**で
上書きします。両方に「直しました」と出ます。

そこで「開いたときはこうだった」(`expected`)を一緒に受け取り、
**そのままなら書く**ようにしました。変わっていれば `409 stale_row` で
断ります。確かめと書き込みは1文(`UPDATE ... WHERE 鍵 AND 開いたときの値`)
なので、確かめてから書くまでの隙間がありません。

* 断りは行き止まりではありません ── 断ったときも**いまの中身**を返すので、
  相手の修正を見たうえで出し直せます
* `expected` を渡さない呼び出し(コマンド経由)は素通しします。
  **確かめようが無いものを、断る理由にはしない**

## 6. セキュリティ

待ち受けは `127.0.0.1` だけなので LAN からは届きません。それでも
**同じPCで開いている別のWebページ**は要求を投げられるので、3つで守ります。

1. **起動トークン** — 起動ごとに作る秘密。知っているのは、このプロセスが
   開いたブラウザだけ。業務データを返す経路(`/api/*` と `/print`)に要求する
2. **Host の確認** — `127.0.0.1`/`localhost` 以外の名前で来たものは断る
   (DNS リバインディング対策)
3. **同一オリジンの確認** — 別のページから投げられた**更新**要求を弾く

`/api/health` と `/api/alive` だけ素通しにしています。前者は
**まだトークンを知らない相手**(多重起動の判定・起動待機画面)が正当に
問い合わせる場面があり、返すのは識別情報と状態だけだからです。後者は
トークンを要求すると、**切れた画面が黙って死んだ扱いになり**、開いているのに
終了してしまうからです。どちらも業務データを1つも含みません。

フォルダ参照(`/api/settings/browse`)は**名前しか返しません**。
ファイルの中身を読む口をここに作らず、件数にも上限を置いています。

## 7. 画面

### 7.1 カレンダー

42セル(7列×6行)。どの日をどう塗るか・何を書くかは
`presenters/calendar.py` が決め、JS は写すだけです。
色分けの意味は VBA から変えていません(日曜・祝日=赤系 / 土曜=青系 /
前後月=グレー / 当日=橙の枠)。**変えたのは濃さだけ**で、tkinter 版は
塗りが強く42セル並ぶと文字より地が目立っていたため、塗りを淡くして
文字を主役にしました。当日の枠は逆に強くしています ── 42個の中から
1つを見つける印なので、淡くすると役に立ちません。

日付を押したあとの流れは tkinter 版と同じです:

```
日付 → [休み / コメント・連絡 / 内容閲覧 / 削除]
         休み           → 作業者 → (3交替なら) 直 → 残業繋ぎ → 早出繋ぎ
                          (繋ぎは前の直が残業・次の直が早出。下記)
         コメント・連絡 → ライン → 班 → 本文
         内容閲覧       → その日の登録内容(読むだけ)
         削除           → チェック → 最終確認
```

**直を聞くかどうかはサーバが決めます**(`needs_shift`)。A/B/C/D 以外
(昼勤・日勤)は3交替に属さないので、直と繋ぎの確認をしません。
画面は班の一覧を持たず、返ってきた真偽値を見るだけです。

繋ぎ担当者の「未登録のまま」は**取り消しではなく選択**です。
`modal.js` の `NONE` で区別しています ── `null`(取り消し)と同じにすると、
「未登録で登録したい」が「やめる」になってしまいます。

#### 繋ぎの2画面は、見て区別できるようにする(あとから直した)

繋ぎは**作業者の一覧を続けて2回**出します。最初はここで
**見出しの文字しか変わりませんでした**(「残業繋ぎの担当者」→
「早出繋ぎの担当者」)。一覧の中身も並びも位置も同じなので、

> 選んだのが効いていないのかな

と見えます。直を聞く画面は形そのものが変わるので分かるのに、
繋ぎだけ分からない ── **押した結果が画面に出ていない**のが理由でした。

VBA のころはメッセージボックスで1つずつ**止めて**聞いていました。
戻りたい作りではありませんが、あれには「進んだことが嫌でも分かる」という
**メリハリ**がありました。止めずに同じだけの区別を付けます。

| 足したもの | 何が分かるようになるか |
|---|---|
| **帯を丸ごと塗る**(残業=橙 / 早出=青緑。`--tone-*`) | 見出しを読む前に、色が入れ替わったことで分かる |
| **上端に太い線**(`modal__box--toned`) | 箱の形からして違う。並べて見なくても違いが分かる |
| **塗りつぶしの札**(`modal__tag`) | 小さくても遠目に効く。「残業繋ぎ」「早出繋ぎ」と**文字でも**言う |
| **どの直を繋ぐのかを見出しに出す**(「1直の残業で繋ぐ人」) | 残業と早出で見出しが根本から変わる。**誰の代わりなのか**も分かる |
| **ここまでに選んだもの**を上に並べる(`chosen`) | 直前に選んだ人がそこに出る ── **押したことが効いている**と分かる |

色だけに頼っていない点が大事です(設計 §1)。札の文字・見出し・
段(3 / 4)・既選択の並び ── **色が見えなくても4つで分かります。**

「ここまでに選んだもの」で色を付けるのは**いま増えた1つだけ**で、
その色は画面の色(`--tone`)ではなく骨格の色を使います。前の画面で
選んだものを、いま聞かれていることと同じ色にすると、どちらの話か
分からなくなるためです。

どの直が繋ぐかは**サーバが渡します**(`/api/workers` の `shift_links`)。
画面が数えると、閲覧やツールチップと言い方がずれて、同じ登録が
2通りに見えます。求め方は `repository.shift_neighbours` の1つだけです。

#### ダブルクリックで1つ飛ばさない(あとから直した)

**同じ形の画面が続けて出る**のがこの流れの特徴です。作業者を選ぶ画面は、
残業繋ぎと早出繋ぎで**同じ場所に同じ並び**で2回出ます。

ここでダブルクリックすると、1打目で残業の画面が閉じ、**2打目が早出の
画面の同じ位置に届きます。** 早出の画面は一瞬出て消え、押した覚えの
無い人が早出繋ぎとして保存されます。画面から見えるのは

> 休む本人 → 直 → 残業繋ぎ **で終わってしまう**

で、飛ばされたことにも、勝手に入った値にも気づけません。Access のころの
癖で一覧はダブルクリックで選ぶ人が多いので、現場では普通に起きます。

`modal.js` が、開いた直後(`SETTLE_MS` = 400ms)の**2打目だけ**を
捕捉して止めます(`event.detail >= 2`)。

| 決めごと | なぜ |
|---|---|
| 止めるのは**2打目だけ** | 時間だけで切ると、速く押しただけの人の1打目まで消える ── **「押しても何も起きない」**そのものになる |
| 捕捉(capture)で止める | 中のボタンより先に受けないと、止める前に選ばれてしまう |
| `modal.js` に置く(流れごとに書かない) | 同じ危険は削除の確認・連絡の宛先にもある。**1か所で塞ぐ** |

### 7.2 設定

tkinter 版で上部のボタンに散らばっていた
[ライン設定] [同期設定] [取り込み] [今すぐ同期] を1画面に集めました。
**毎日使うもの(日付を押す)と、最初に1度決めるもの(ライン設定)が同じ
高さに並んでいた**のが元の形で、そこを分けています。

並びは決める順です: ライン → 参照パス → 取り込み → 班員名簿 → いまの状態。

ファイル選択は**サーバ側のフォルダを歩きます**。ブラウザのファイル選択
ダイアログは中身しか渡さず、アプリが要るのは「このPCから見た共有フォルダの
パス」なので、選ばせても意味がありません。

### 7.3 画面の見た目(ライト / ダーク)

| 決めごと | 理由 |
|---|---|
| 選べるのは「自動・ライト・ダーク」(`settings.THEME_CHOICES`)。一覧に無い値は 422 `not_listed` | §1 の「一覧に無いものは選べない」 |
| **この端末の** `settings.json` に覚える(パスワード不要) | 見た目は人と場所の好み。業務の動きは変わらない |
| **HTML を返す時点で** `<html data-theme>` を付ける。「自動」は付けず OS(`prefers-color-scheme`)に任せる | 画面の JS が読んでから切り替えると、開くたびに一瞬白く光る |
| 色は `tokens.css` だけ。ダークの2つの節(OS がダーク / 選んでダーク)は同じ値(試験で見る) | 片方だけ直すと、選び方で色が違う |
| 塗りの上の文字は `--on-accent` / `--on-error`(白を直に書かない) | ダークは塗りが明るくなるので、白い字では読めない(コントラスト比 2 程度になる) |
| `color-scheme` も明暗で切り替える | 入力欄・選択肢・スクロールバー(ブラウザが描く部品)が白く浮かないように |
| 印刷は見た目に関係なく白い紙 | 印刷用の HTML は `tokens.css` を読まない(紙の色は固定) |

明暗どちらでも、本文・状態表示・塗りの上の文字はコントラスト比 4.5 以上(`tests/test_theme.py`。
ダークは本文 13 以上・状態表示 8 前後)。

## 8. 参照パスとマスタ管理

### 参照パスはフォルダで持つ

取り込み元(共有の `.sqlite3`)は**フォルダ**で設定し、ファイルはその中から
探します(`calendar_app/sources.py`)。

ファイルのフルパスを設定させると、上流がファイル名を変えただけで
動かなくなり、現場からは「急に読めなくなった」としか見えません。
フォルダなら名前が変わっても拾えますし、保存用とマスタが同じ共有に
並んでいる普通の置き方にも合います。

- 既定の名前(`連絡帳` / `梱包資材マスタ`)で探し、**拡張子違いも同じもの**
  として扱う(`.sqlite3` / `.db`)
- 保存用が見つからなければ、そのフォルダの `.sqlite3` のうち
  マスタ以外で最初のものを使う
- マスタは**名前が合うものだけ**。「マスタでない最初の1つ」で代用すると、
  班員名簿の入っていないDBを黙って掴む
- マスタのフォルダが未設定なら、保存用と同じフォルダも見る
- **旧設定のフルパスも読む。** フォルダ方式へ移る前に設定した端末が、
  更新の日に置き場所を見失わないようにするための逃げ道
- 相対パスは**アプリのフォルダから**たどる(`config.resolve_dir`)。
  「いまの作業フォルダ」から見ると、同じ設定でも起動の仕方で違う場所を指す

**開けたかどうかは、引けたかどうかで決めます。** `Path.exists()` も
`sqlite3.connect()` もファイルの中身に触らないので、壊れている・
別のものが置かれているファイルを「見つかった」と答えてしまい、最初の
取り込みで初めて落ちます。`sources.probe()` は実際に1回引いてから答え、
駄目なときは**大きさ・`-wal`/`-shm` の有無・どの開き方で駄目だったか・
次の一手**まで返します(`source_db.Probe.hint()`)。

### パスが無いと変更ができない

書き先が決まっていないのに「保存しました」と言うわけにはいきません。
**参照パスが決まるまで、書き込みはすべて `no_source` で断ります。**

| 操作 | 断る条件 |
|---|---|
| 休み・連絡の登録、削除 | 保存用DB(連絡帳)が見つからない |
| マスタの追加・修正・削除 | マスタDB が見つからない / 開けない / 班員名簿が入っていない |

正式なデータは共有の取り込み元だけで、手元の SQLite は写しと送信待ちの
置き場にすぎません(§4)。送り先が決まっていないのに登録を受けると、
入力はその端末に溜まり続け、他のラインには永遠に届きません。
**「保存できたつもり」が一番たちが悪い**ので、入り口で断ります。

断るのは**そもそも場所が決まっていない**ときだけです。設定してある共有が
一時的に見えないだけ(ネットワーク断・共有の停止)なら断りません ──
そのための送信待ちです。

**読み取りは断りません。** 見ることと書き換えられることは別の話で、
中身を確かめられないと参照パスが合っているかすら分かりません。

### マスタ管理 ── 直す先は取り込み元だけ

`calendar_app/master_admin.py`。班員名簿は起動のたびに黙って読まれる
だけで、中を見る手立ても直す手立ても画面にありませんでした。名前や班が
違っていても、現場には**「休みにしたい人が一覧に出ない」**としか見えず、
共有のDBを開ける人を探すところから始まります。

**書き先は取り込み元ただ1つです。** 取り込みは総入れ替えなので、手元の
DBを直しても次の取り込みで消えます(§1 の規則5)。

```
画面 → 取り込み元(.sqlite3)へ書く → その表だけ取り込み直す → 手元が追いつく
```

最後の一手を飛ばすと、元は直っているのに画面の動きが変わりません。
**直したのに効かない**が一番たちが悪いので、その場で取り込み直します
(`importer.import_master_table`)。

| 決めごと | 中身 |
|---|---|
| 行の指し方 | `管理番号`。班員名簿の主キーで、取り込みは `INSERT OR REPLACE` でこの値を軸に入れ直すため、**取り込みをまたいで同じ行を指す** |
| 直せる表 | 班員名簿だけ(`MANAGED`)。休み管理・削除履歴は**業務データ**で、直すのはカレンダー画面から |
| 直せる列 | こちらの定義 ∩ 取り込み元に実在する列。**既にある事実を読むだけ** |
| 鍵の列 | 作るときだけ受ける。あとから変えられると、同じ人が2行に増える |
| 必須 | `管理番号` と `名前`。空で上書きさせない |
| 一度に出す行 | 200行。切ったぶんは必ず数で言う |
| 並べ替え | 列名を押すと 昇順→降順→元の並び。**サーバで並べてから200行で切る**(画面で並べると、出ている200行の中だけの順番になり、本当の先頭が見えない)。数だけの値は数として比べ、空欄は向きによらず最後。保存の応答も同じ並びで返す(`view` に q/sort/desc を載せて送る) |
| 書く前 | **控えを取る**(`backup\`、直近10世代)。共有フォルダ上の SQLite は最悪の壊れ方が「破損」で、マスタは全員が使う |

`WHERE` の無い `DELETE` は投げません。空の `WHERE` は「全行」で、
取り込み元は共有のマスタなので、1回の取り違えで全員が困ります。

**直せないときも中身は出します。** 「読めません」しか出ないと、参照パスが
合っているのかどうかすら確かめられません。断ったときの応答にも
更新後の一覧一式を載せてあります。

### 見るだけの表も同じ枠に並べる

マスタ確認が扱う表は1つではありません(`MANAGED`)。班員名簿は直せる表、
端末一覧(§8.1)は**見るだけの表**です。

確かめたいものと直したいものを別の画面に分けると、探すところから
始まります。同じ枠に並べ、画面は `editable` を見て描き分けるだけに
してあります ── **画面の側に「この表は直せない」を書かない。**
書くと、表が増えた日に必ず食い違います。

直せない表へ書こうとしたら `not_editable` で断ります。表ごとに違うのは
「どちらの取り込み元にあるか」(`where`)と「行を指す鍵」(`row_key`)の
2つだけで、読み書きの道は同じです。

## 8.0 マスタ確認に並ぶ3つの表

確かめたいものと直したいものを別の画面に分けると、探すところから
始まります。そこで**1つの画面に並べ、できることだけ変えます**。

| 表 | どこに | できること |
|---|---|---|
| 班員名簿 | マスタDB | 直す・足す・消す |
| 端末一覧 | 保存用DB | **見る・消す**(値は直せない。§8.1) |
| 削除履歴 | 保存用DB | **見るだけ**(記録なので直さない) |

画面は `editable` と `removable` を見て描き分けるだけです
(`Managed` に1行足せば表が増えます)。

**削除履歴は新しい順**に並べます ── 直近を探しに来るのがふつうで、
古い順だと毎回いちばん下まで送ることになります。見るだけの表では
鍵が空の行も捨てません(**見せないほうが困る**)。

## 8.0.1 配布設定 ── 1台で決めた設定を、配った先でそのまま使う

端末の設定は `%LOCALAPPDATA%` の `settings.json` にあり、**利用者ごと・
PCごとに別**です。配った先で1台ずつ設定画面を開いて打ち直すのは手間で、
打ち間違えると**別の取り込み元へ送る**端末ができてしまいます。

姉妹ツール(python-web-tools)の「配布設定」と同じ作りにしてあります
(`calendar_app/distribution.py`)。

    1. 1台で起動して設定し、設定画面の「6. 配布設定」で書き出す
    2. ツールのフォルダの直下(start.bat と同じ階層)に 配布設定\ ができ、
       配るものが全部そこに入る
    3. フォルダごと配る(tools\make_dist.bat で配布用フォルダを作る)
    4. 配った先は起動したとき 配布設定\ を見つけて読み込む

    配布設定\
      設定.json          {"format": 1, "created_at", "created_on", "version",
                          "settings": {settings.json の鍵: 値}}
      はじめに読む.txt   何が入っているか・配った先で何が起きるか(BOM 付き)

| 決めごと | なぜ |
|---|---|
| **この端末のいまの設定を書き出す**(別の入力欄を持たない) | 確かめ終わった値をそのまま配る。打ち直すと1文字違う、が起きる |
| 入れる項目を選ぶ。**ラインは既定で外す** | 端末ごとに違う。入れたまま配ると全端末が同じラインになる |
| この端末で変えていない(空の)項目は入れない | 配った先の既定を「空」で上書きしない |
| 鍵は `settings.json` の鍵そのもの | 読み込みは写すだけで済む。知らない鍵は捨てる |
| **作ってから入れ替える**(`配布設定.作成中` → `配布設定`) | 途中で失敗して、半分だけ新しい配布設定を残さない |
| **起動時は、その端末にすでに値がある項目を読まない** | 端末で直した値が次の起動で戻されない。空文字は「無い」と見なす(既定に戻すと空文字で残るため) |
| 揃えたいときは「読み込み直す」(上書き) | 狙って揃える道は残す |
| 書き出す・読み込み直す・消すは管理者パスワード。**起動時の読み込みには要らない** | 配布設定を置いたのは、フォルダを配った管理者本人 |
| **読み込んだあとの最初の同期で班員名簿も入る**(`AutoSync._receive_members`) | 班員名簿はマスタDBにあり、保存用DBの取り込みでは入らない。以前は「取り込む」を押すまで0件で、**配ったばかりの端末は休みの作業者を選べなかった**。受信のたびにマスタDBから名簿だけ入れ直す(書き戻しの無い表なので送信待ちに関係しない)。マスタDBが見えなくても受信は失敗させない |
| 置き場所がドライブ文字(`Z:\`)なら書き出すときに注意する(止めはしない) | ドライブ文字の割り当ては PC ごとに違うことがあり、配った先で見つからない |
| 読むのは同期より前(`start_app._initialize` の最初) | 置き場所が入っているので、読む前に同期を始めると古い場所を見る |
| 手で平文が書かれていても、端末には撹拌して持つ | 端末の設定ファイルに平文を置かない |
| リポジトリに入れない(`.gitignore`) | 配る人がその場で書き出すもので、ソースではない |
| フォルダ名は `配布設定`(姉妹ツールと同じ) | 配る人が両方のツールを扱うので、同じ名前・同じ手順にそろえる |

**配布用フォルダ**(`tools/make_dist.py`、`tools\make_dist.bat`)は、配るもの
(`INCLUDE`)だけを写し、`配布設定\` は `--no-settings` で外せます。
ツールのフォルダの中には作らない・中身のある場所は `--force` のときだけ・
最後に入っていてはいけないもの(tests・開発機の settings.json など)が
無いか確かめる、も姉妹ツールと同じです。直下にファイルを足したら、
`INCLUDE` に入れるかどうかを決めさせる試験(`tests/test_make_dist.py`)があります。

以前の形(`config/app.json` の `defaults`、`config/distribution.json`、
`distribution\` フォルダ)は読みません。書き出し直してください。

### アプリのフォルダに何も書かない

基盤仕様書 2.7 のとおり、実行中に書くものはすべて `%LOCALAPPDATA%` へ
行きます。**ただし Python の `__pycache__` だけは、アプリのフォルダに
できていました**(ローカル領域に `pycache` の置き場は作ってあったのに、
誰もそこへ向けていなかった)。アプリを共有に置くと、起動した端末の数だけ
共有へ書きに行くことになります。

`start_app.py` の最初で `sys.pycache_prefix` をローカル領域へ向けています。
向け先を知るために読む `app_config` の1回だけは、写しを作らずに読みます
(`sys.dont_write_bytecode`)── これで**アプリのフォルダへの書き込みは0**です。

## 8.1 端末一覧 ── どのPCがどの設定か

ライン設定は**その端末にしか無い**ので、外からは見えません。
「コイルの連絡が来ていない」と言われたとき、調べる手立ては
**その端末まで歩いて行って設定画面を開くこと**だけでした。

そこで各端末が、自分の設定を取り込み元へ置いていきます
(`calendar_app/terminals.py`、取り込み元の `端末設定` 表)。

| 決めごと | 中身 |
|---|---|
| 置き場所 | **保存用DB(連絡帳)側**。どの端末も必ずそこへ書いているので、マスタDBが見えない端末でも記録が残る |
| 行を指す鍵 | `端末キー` =「ログインID@PC名」。**両方で1行**(下記) |
| 書くとき | **中身が変わったとき**と、**古くなったとき**(既定6時間)だけ。ふだんは1行読むだけ |
| 書く場所 | 同期のついで(接続は既に開いている)と、ライン設定を変えた直後 |
| 失敗したとき | **黙って諦める。** 見るためのもので、業務データではない |
| 直し方 | その端末の設定画面から。**値は一覧からは直せない** |
| 消し方 | **一覧から消せる**(`Managed.removable`)。入れ替えたPCの行が残り続けると「まだ古い設定の端末がある」ように見える。消してもその端末が次に起動すればまた出る |
| 前もって決める | **一覧の `次のライン` に置く**(下記)。実績の `ライン` は直せないまま |

書き込みを増やさないのは、共有フォルダ上の SQLite の弱点が同時書き込み
だからです(§4.2)。毎回の同期で書くと、端末の台数ぶん負担が増えます。

一覧から直せないのは、直してもその端末の `settings.json` は変わらず、
**次の同期で元に戻る**からです。直ったように見えて直っていない状態を
作るくらいなら、はじめから断るほうが早く終わります。

### 前もって決めておく ── 直すのではなく「予約」する

「一覧を直せれば、配る前に決めておけるのに」という声に応えるための形です。
**一覧の `ライン` を直させるわけにはいきません** ── 直しても端末の
`settings.json` は変わらず、次の同期で元に戻ります。直ったように見えて
直っていない、が一番たちが悪い。

そこで**別の列に「次はこうしてほしい」を置き、端末が取りに来ます**。

```
一覧の [次のライン] に置く         予約日時・予約者も一緒に残る
        ↓
端末が起動する                    terminals.take_reservation()
        ↓
settings.json に入れて予約を消す    → 実績の [ライン] が変わる
```

| 決めごと | なぜ |
|---|---|
| 実績(`ライン`)と予約(`次のライン`)を**別の列**に持つ | 同じ列に置くと、端末の報告が予約を踏み潰す。どちらが「いまの姿」でどちらが「これからの姿」かも読めなくなる |
| 受け取るのは**起動のときだけ** | 使っている最中に黙って切り替わると、その人には何も起きていないように見えたまま表示だけがずれる ── 直したばかりの不具合そのもの |
| 受け取ったら**予約を消す** | 二度効かせない。端末で直したのにまた戻る、を作らない |
| `ログインID@PC名` と `PC名` の**2通りを見る** | 配る前は誰がログインするか分からない。PC単位で置けるようにし、細かいほう(自分あて)を優先する |
| **管理者パスワードが要る**(`terminal_line`) | 他の端末のラインを決めるのは、その端末で変えるのと同じこと。むしろ目の前に無いぶん危ない |
| 誰がいつ決めたかも残す(`予約日時` / `予約者`) | 違っていたときに、直す相手が分からない |
| 一覧に無いライン名は**受け取らずに消す** | 一覧に無いものは選べない(§1)。残すと毎回同じ警告が出るだけで、誰も直せない |

画面側は「列ごとに打てる/打てない」を見て描き分けます
(`Column.editable` / `at_create`)。表ごとの真偽だけでは、実績の中に
1列だけ打てる欄がある、が表せません。

### 鍵が「PC名」だけでは足りない(あとから直した)

設定は `%LOCALAPPDATA%` に置くので、**Windows の利用者ごとに別**です。
3交替で同じPCを別のIDで使えば、ライン設定も別々に持てます。
ところが鍵が `PC名` だけだと、その2人が**1行を奪い合い**、
後から起動したほうの設定だけが見えます ── 見ている人には、
もう片方が存在しないように見えます。

そこで鍵を `ログインID@PC名` にしました。逆に、同じIDで別のPCを使う
場合は PC名 が違うので、はじめから別の行になります。

主キーは後から変えられないので、**前の版が作った表は作り直します**
(`terminals._rekey`)。一度きりで、記録されていた内容は引き継ぎます。
途中で落ちても失うのは一覧だけ(業務データではなく、各端末が次に
つないだときに置き直す)ですが、共有の業務ファイルを触るので
**先に控えを取ります**。

**これは権限ではありません。** 誰がその端末を使えるかを決めるものではなく、
いまどうなっているかを見えるようにするだけです。

## 8.2 管理者パスワード ── 設定を勝手に変えられないように

VBA 版は**どの端末からでも、誰でもライン設定を変えられました**。
上部のボタンを押して一覧から選ぶだけです。ライン設定は「この端末に
何を見せるか」を決めるもので、変えられると

* コイルの端末が全ラインを表示する(見えてはいけないものが見える)
* 作業長の端末がコイルだけになる(見えるはずのものが消える)

という形で、**その端末の人には何も起きていないように見えたまま**
表示だけがずれます。参照パスも同じで、変えられるとその端末の入力だけが
別の場所へ行き、他のラインには永遠に届きません。

どちらも「毎日使うもの」ではなく「最初に1度決めるもの」なので、
関門を置いても現場の手数は増えません。

| 決めごと | 中身 |
|---|---|
| 守る対象 | `PROTECTED_LABELS` に1行足せば増える(いまはライン・保存用DB・マスタDBのフォルダ) |
| 関門の位置 | **書く前**。1つでも書いてしまうと、断ったのに一部だけ変わった状態が残る |
| 聞く条件 | **本当に値が変わるときだけ。** 変わらないものに聞くと「押しても何も起きない」になる |
| 断り方 | `need_password` / `wrong_password` / **403**。形は正しく、この端末では**まだ**できない |
| 言い分け | 「違う」と「送っていない」を**言い分ける**(下記) |
| 聞き直す回数 | 3回まで。**超えたら打ち切って戻し方を出す** ── 同じ問いを無限に出さない |
| 持ち方 | PBKDF2 で撹拌(`pbkdf2$繰り返し$塩$結果`)。**平文では持たない** |
| 既定 | `config.ADMIN_PASSWORD`(環境変数で上書き可)。**一度も変えていない端末はこれで通る** |
| 忘れたとき | `settings.json` の行を消す。画面から戻せるようにすると、確認そのものが意味を失う |

**画面は押す前から欄を出しません。** 要るかどうかはサーバが持っている
(同じ値なら聞かない)ので、画面が先回りすると必ず食い違います。
断られてから聞いて、同じ要求をもう一度だけ送ります。

### 「違う」と「送っていない」は言い分ける(あとから直した)

最初は言い分けていませんでした ── 言い分けると総当たりの手がかりになる、
という理由です。**これが行き止まりを作りました。**

打ち間違えても返ってくるのは1回目とまったく同じ問いなので、画面は
黙って同じ問いを出し直します。利用者から見えるのは
「**永遠にパスワードを聞かれて、ラインも参照パスも設定できない。
間違っているのか壊れているのか分からない**」という状態です。

隠して守れるものがありません。これはアクセス制御ではなく押し間違い
防止のUIガードで、値は同じ端末の設定ファイルにあり、既定値は
README に書いてあります。**総当たりを気にする相手は、画面を使わずに
設定ファイルを書き換えます。**

そこで3つ直しました。

| 直したところ | 中身 |
|---|---|
| 送ったのに通らなければ `wrong_password` | 「管理者パスワードが違います」と言う |
| 断りに**先へ進む道**を添える | 初期値のままの端末には README の場所を、変えてある端末には `settings.json` の戻し方を |
| 画面は**3回で打ち切る** | 超えたら聞き直さず、最後の断りをそのまま出す |

**これはアクセス制御ではありません。** 誤って押されないためのUIガードで、
パスワードを知っている人なら誰でも変えられますし、設定ファイルを
直接書き換えれば通ります。参考にした梱包資材ツールでは、
「誰がその端末を使えるか」は別の仕組み(アクセス権限マスタ)が持って
います ── こちらのカレンダーにはその区別が要る場面がまだありません。

## 8.3 開けっぱなしにされる前提で作る

このツールは**朝に開いて一日中そのまま**、という使い方をされます。
「起動してすぐの数分」しか考えていないと、次のような形で崩れます ──
どれも**その場では気づけず**、気づくのは何日か経ってからです。

| 何が起きるか | なぜ起きたか | どうしたか |
|---|---|---|
| 他ラインの登録が画面に出ない | 背景の同期は手元を入れ替えるが、画面を描き直す合図が無かった(押したときだけ描き直していた) | `GET /api/sync` に `last_received_at` を載せ、変わったら描き直す。**帯の見張り1本に相乗りする** |
| 翌朝も昨日のセルに枠が付く | 「今日」を描いた時点で決めていた | 同じ合図に `today` を載せ、変わったら描き直す |
| 1つのログが数十MBになる | ファイル名を起動時に1回だけ決めていた | 日付が変わったら書き先も移す(`DailyFileHandler`)。古いものは30日で消す |
| 古いタブが押しても全部 403 | 起動し直すと起動トークンが変わるが、版が同じだと気づけなかった | 画面に `pid` を持たせ、答えているサーバが別物なら読み込み直す |
| 開いたままの削除ダイアログが別の行を消す | ID だけで消していた。取り込み元の ID は**再利用される** | 画面が見ていた中身の印を添え、合わなければ 409 `gone` |
| 取り込み元を差し替えたら送信が全部失敗する | 「送信ID列はある」を覚えていた | 覚えない。実在するかは毎回見る(PRAGMA 2回で済む) |
| 蓋を開けた瞬間に、送らずに終了する | 休止中も `monotonic` は進むので「何時間も心拍が無い」と判定され、同期が1回も回らなかった | **未送信があるあいだは終わらない**(下の §8.4) |

**共通しているのは「古いものを最新だと読ませない」です。** 基盤仕様書 2.9
が「黙って古い表示を出し続けない」と言っているのは切断のときの話ですが、
開けっぱなしの画面はそれと同じ状態になりえます ── しかも切れていないので、
利用者には**確かめる手立てがありません**。

描き直しの判断は画面側(`sync.js` / `health.js`)が持ちますが、
**根拠はすべてサーバが返します**。「変わったかどうか」を画面が自分で
数えはじめると、同じ事実を2か所で持つことになります(§1 の規則5)。

## 8.4 未送信を抱えたまま終わらない

`idle_exit` は「誰も見ていなければ終わる」ですが、**まだ外へ出せていない
仕事があるあいだは終わりません**(`HOLD_SEC`、既定10分)。

【効くのは「目覚めた瞬間」】
蓋を閉じて帰るとPCが寝てプロセスも止まり、そのあいだは何も送れません。
翌朝ふたを開けるとプロセスが動き出しますが、`time.monotonic()` は休止中も
進むので「何時間も心拍が無い」と判定され、**同期が1回も回らないうちに
自分を終わらせていました。** 未送信は次に誰かが起動するまで届かず、
タブは開いたままなので**利用者には送られたように見えます**。

| 決めごと | 中身 |
|---|---|
| 粘る条件 | `unsent()` が 1 以上。**送り先が決まっていなければ 0 を返す**(待っても送れないので居座らせない) |
| 粘りはじめ | 定期実行を待たずに1回だけ送信を頼む(`retry`)。目覚めた直後はここが効く |
| 上限 | 10分。**長さに大きな意味は無い** ── 届くなら同期1回(20秒)で終わる。共有が死んでいるときの歯止め |
| 諦めたとき | 件数をログに残し、`on_exit` で手元に覚える |
| 誰か戻ってきたら | 粘りを解く(そのまま使わせる) |

【基盤は業務の事情を知らない】
`idle_exit` は起動基盤の一部で、他のプロジェクトでも使います。そこで
**件数の数え方と送り直しの頼み方は渡すだけ**にしてあり
(`start_app.py` が `sync_service` の関数を渡す)、`idle_exit` 側は
「0 なら粘る理由が無い」しか知りません。「参照パスが未設定なら粘らない」
という業務の判断も、渡す側が 0 を返すことで表します。

【残したことは、次につながったときに見える】
**書きたい瞬間には共有へ書けません。** 未送信のまま終わるのは共有が
落ちているときなので、その場で端末一覧(§8.1)へ書くことはできません。
手元の `_sync_meta` に覚えておき、次につながったときに
`端末設定` の「未送信のまま終了」へ載せます。後からになりますが、
「この端末だけ連絡が届いていない」を探すには足ります。
きれいに終わったときは**消します** ── 前回の記録が居座ると、
直ったのに出続けます。

## 8.5 裏に回ったタブ ── 心拍が止まっても終わらない

ブラウザは、見えていないタブのタイマーを間引きます。Chrome は隠れて
5分たつと1分に1回まで、Edge の「スリープ中のタブ」や Chrome の省メモリは
**タブごと凍らせるので心拍が完全に止まります。** 別の道具で、Excel を見て
いるあいだに心拍が途切れ、アプリが終わっていたことがありました。

```
裏に回る   visibilitychange(hidden) / freeze ─▶ sendBeacon {state:"hidden"}
             └ サーバ: その画面が戻るか閉じるまで
                 ・自動終了しない(idle_exit)
                 ・タブを空けない(screen_lock)
表に戻る   visibilitychange(visible) / resume / pageshow / online
             ─▶ すぐ心拍 {state:"visible"} + 接続確認 + 同期の状態を取り直す
スリープ明け(画面) 5秒ごとの時計が60秒以上飛んだ ─▶ 表に戻ったのと同じ
スリープ明け(サーバ) 見張りの1周が30秒以上あいた ─▶ そこから数え直す + 同期を頼む
閉じる     pagehide ─▶ sendBeacon {leaving:true}(裏のままでも効く)
```

| 決めごと | なぜ |
|---|---|
| 裏に回る合図は **`sendBeacon`** | 凍らされる直前は `fetch` が届かないことがある |
| **裏の画面がある間は、心拍の途切れで終わらない。上限も置かない** | 上限を置くと、昼休みに裏へ回したタブが戻ったら終わっていた、が起きる。閉じた合図が届かずに残っても、次の `Start.vbs` は合流し、版が違えば入れ替わる(`launch_guard`)ので困らない |
| 終わるのは、閉じた合図・[終了]・`stop.bat` | 裏でも、閉じたことは分かる |
| **閉じた画面から遅れて届く「隠れます」は無視する** | 閉じるときにも見え方が変わって合図が飛び、合図どうしは順番が入れ替わる。取り消すと裏のまま閉じたタブで終わらない(ブラウザで確かめて実際にそうなった)。画面側も閉じた合図のあとは何も送らない |
| **取って代わられた画面の「隠れます」は数えない** | 使われていない画面のせいで、いつまでも終わらなくなる |
| 表のままの画面は、今までどおり90秒で終わる | 裏に回っていない画面の心拍は間引かれない。途切れたなら本当に居ない |
| 心拍にはいつも見え方(`state`)を添える | 間引かれながらも届いた心拍で、裏のままであることを保ち直せる |
| **スリープ明けはサーバでも気づく**(単調時計と実時刻の大きいほう) | 表のまま蓋を閉じると、画面のイベントは何も来ない。休止中に単調時計が進むかは OS による(Windows は進む・Linux は止まる)ので、どちらでも気づけるように |
| **別のサイトからの心拍は数えない**(`Origin` が別なら 403) | 心拍はトークン無しで受けるので、同じブラウザの他サイトのタブからも `sendBeacon` で届く(実際に届くことを確かめた)。数えると、誰も見ていないのに終わらない・閉じたのに取り消される、が外から起こせる |
| 心拍の間隔は **サーバから渡す**(`window.APP.heartbeatMs`) | 見張る側と送る側が別々に持つと、片方だけ変えたときに途切れと誤る |

**ブラウザで確かめたこと**(Playwright):

* 裏に回したあと心拍を115秒遮断 → **動き続けた**。比較として表のまま
  遮断 → 90秒で終わった
* 裏に回して凍らせ(`Page.setWebLifecycleState`)130秒 → 動き続け、
  表に戻すと見張りを再開した
* サーバのプロセスを110秒止めてから再開(スリープの再現) → 戻った瞬間に
  終わらず、画面の心拍を待った
* 裏に回したタブを閉じる → 8秒後に終わった

## 8.6 印刷 ── 紙の端から5mm以上内側に描く

プリンターは紙の縁から約4mmには印刷できません。ブラウザの印刷プレビューは
紙の端まで描くので、**画面では収まって見えても紙では欠けます。**

以前の作りは `@page { margin: 10mm }` に頼っていて、しかも1日に数件の
登録で A4 横1枚に収まらず2枚目へこぼれていました(Chromium で PDF にして
確認)。1枚に収めようとダイアログで「余白: なし」や倍率を選ぶと、表が
紙の端まで寄ります。

```
@page { margin: 0 }            ダイアログの「既定」「なし」で同じ結果
└ .sheet 297×203mm, padding 8mm(SAFE_MM)  ← この padding が安全な余白
   └ .content(見出し・表・フッター)  多い月は zoom で縮めて収める
```

| 決めごと | なぜ |
|---|---|
| 余白は**ページの内側に自分で取る**(`.sheet` の padding) | `@page` の余白は、ダイアログで「なし」を選ばれると消える |
| `SAFE_MM = 8`(決まりは5mm以上) | 刷れない幅は機種と給紙のずれで前後する。4mm に余裕を足す |
| 台紙の高さは紙より低い 203mm | 「最小」「カスタム」で余白を足されると、Chrome は幅が収まるよう全体を縮める。縮めた高さが収まらないと白紙の2枚目ができる。片側10mm まで足されても1枚(`203 × 277/297 ≦ 190`) |
| 週の行は最低 27mm(`ROW_MM`)で揃える | 余った高さを表に配ると、空の週(翌月だけの週)が細く潰れる |
| **多い月は縮める。切り捨てない** | 黙って消えるほうが困る。縮めたあと実際の位置を測り直し、はみ出していればさらに縮める(文字は縮めても行の高さがきっちり比例しない) |
| 縮めるのは中身だけ。枠の高さは台紙のまま | 割合の高さは `zoom` で縮まないので、割り戻すと枠ごとはみ出す |
| `print-color-adjust: exact` | 指定しないと「背景のグラフィック」を入れない限り色帯が白く抜け、白い文字の曜日が読めない |
| `100vh` / `height:100%` で紙に合わせない | 印刷でも画面の高さを指すことがあり、多い月で下が切れた(確認済み) |
| プレビューに **[印刷する]**・**[閉じる]** を置く(`.noprint` の中) | Ctrl+P を知らない人が、プレビューを開いたまま止まる。[印刷する] は開いた時点で選ばれていて Enter でも押せる。押すと `beforeprint` で収め直してからダイアログを開く。[閉じる] は [印刷] が開いたタブなら閉じ、アドレス欄から開いたタブ(ブラウザが閉じさせない)なら閉じ方を出す ── 黙って何も起きないのがいちばん困る |

**確かめたこと**(Chromium で PDF にし、インクの外周を測った。単位 mm):

| 中身 | 余白=既定/なし | 余白=最小(4mm) | 余白=カスタム10mm |
|---|---|---|---|
| ふつう(1日3〜6件) | 1枚・最小 7.8 | 1枚・最小 11.7 | 1枚・最小 17.4 |
| 多い(1日12件) | 1枚・最小 7.8 | 1枚・最小 11.7 | 1枚・最小 17.3 |
| 空の月 | 1枚・最小 7.8 | 1枚・最小 11.7 | 1枚・最小 17.4 |

(変更前: ふつうの月で2枚、1枚目は下端10mm まで描いていた)

## 8.7 履歴表示 ── 過去の月を、編集できない形で見せる

カレンダー画面でも前月へ戻れば過去の月は見えますが、そこは登録・削除が
できる画面です。昔の月を調べている途中の押し間違いで過去の記録が
変わらないよう、**見るだけの画面を分けました**(`presenters/history.py`、
`routes/history.py`、`views/history.js`)。

| 決めごと | なぜ |
|---|---|
| **書き込む道を持たない**(API は GET だけ・画面のスクリプトに書き込みの呼び出しが無い・ボタンも無い) | 「押せないように隠す」だと、隠し漏れが書ける道になる。道そのものが無ければ漏れようがない(試験で見張る) |
| 選べるのは**登録がある最も古い月から先月まで**。範囲の外はサーバが 422 で断る | 一覧に無いものは選べない。今月はまだ動いているのでカレンダー画面で見る |
| 途中の0件の月も選べる | 「その月は誰も休んでいない」も記録 |
| 年月は**年ごとの12マス**で選ばせ、マスに件数を出す | どの月に記録があるかが、開く前に分かる。選べない月は点線で押せない(件数0と「—」を言い分ける) |
| マス目の組み立ては `calendar.month_view` を共用、描き方は `grid.js` を共用 | 2か所で組むと、片方だけ直したときに同じ月が違って見える |
| 日の中身は `detail` と件数だけ返す(ID・中身の印は返さない) | 削除にしか使わない値を、見るだけの画面へ渡さない |
| 取り込み直しがあれば描き直す | 他の端末が過去の登録を消した・直したときに、古い表示を最新だと読ませない |
| **セピア寄りの配色**(`--hist-*`)・紙色の地・左の帯・「履歴・閲覧のみ」の札 | マス目が同じなので、カレンダー画面と取り違えない。`.cal--history` の中だけ `--day-*` / `--head-*` を `--hist-*` に差し替えるので、部品(`.day` など)は共用のまま。土曜・日曜祝日の**色相の向きは保ち**、彩度だけ落とす(意味の色は入れ替えない)。文字のコントラストは明暗とも 5.5 以上 |

## 8.8 アクセス権限 ── この端末で使えるラインを ID と PC名 で決める

ライン設定は管理者パスワードだけで守っていました。パスワードは教え合えるので、
守っていたのは「誰か」ではなく「合言葉を知っているか」です。そこで梱包資材
マスタの `アクセス権限` 表(梱包資材総合ツールと共用)で、**ログインID と
PC名** から使えるラインを決めます(`calendar_app/access_control.py`)。

    管理番号 INTEGER PRIMARY KEY / ログインID / PC名 / 権限 NOT NULL / 有効 (既定1) / 備考

| 決めごと | なぜ |
|---|---|
| **表の形と読み方は別ツールと同じ**(空欄は問わない・両方空の行は効かない・大文字小文字を区別しない・当たる行の和) | 共用の表。片方だけ違う読み方をすると、同じ行が道具によって違う意味になる |
| このツールが読むのは**権限がライン名の行だけ**。`mode:field` などは読み飛ばし、消しも直しもしない | 他ツールの値が入る表。知らない値を「おかしい」と言うと、別ツールの正しい行まで疑わせる |
| ライン名の打ち間違いらしいもの(`ｺｲﾙ` など。全角・半角をそろえて比べる)だけ指摘する | 共用の表なので、`:` を含む値(他ツールの名前空間)は疑わない |
| 表で決まっている端末は**そのラインに固定**(1行なら画面で選べない。複数ならその中だけ)。**表に無いラインは選べない**(パスワードでも通さない) | 管理の出どころを表1つにする。パスワードで抜けられると、表で決めた意味が無い |
| **切り替えにはいつでも管理者パスワード**(表で決まっていても) | 権限は「使ってよいライン」であって「勝手に変えてよい」ではない(最初はパスワード無しにしていたが、それではおかしいと指摘を受けて改めた) |
| 決まっていない端末は**今までどおりパスワード** | 表をまだ作っていない・登録し忘れた、で全員が締め出されると仕事が止まる |
| いまのラインが表に無ければ、**起動時と、同期で表を取り込み直したとき**に合わせる | マスタ管理で直したら、開いたままの端末も次の同期で合う(閉じて開き直させない)。予約より表が勝つ |
| 表は手元にも写す(班員名簿と同じく、受信のたびに入れ直す) | 共有に届かないときも、この端末のラインの判断が続けられる |
| 表が無ければ作る(同期のときに1度・マスタ管理で足すとき)。形は別ツールと同じ | マスタ管理から行を足せるようにする。既にあれば形を変えない |
| マスタ管理は**足す・直す・消すのどれも管理者パスワード**(`guard_all`) | どの行も「どの端末がどのラインを使えるか」そのもの |
| 管理番号は取り込み元が振る(`auto_key`)。権限・有効には候補を出すが、候補以外も打てる | 打たせると重複や打ち間違いが起きる。共用の表なので候補外の値も入る |
| 両方空の行・有効が 1/0 以外は、書く前に断る | 効かない行を書いた人が、効いているつもりのままになる |

**別ツールへの影響(確かめた):** こちらが足した行を含めても、梱包資材総合
ツールは同じ形で読める。ただし別ツールの設定画面には「知らない権限コード
(コイル)」と指摘が出る(別ツールはライン名を知らないため。動きには影響しない)。

## 8.9 エラーの後追い ── なぜなぜ分析の「事実」をログから埋める

**困っていたこと:** エラーが起きても後から追えない。利用者に聞いて分かるのは
「押したら赤いのが出た」くらいで、いつ・どの端末で・何をしていて・何が原因
だったかは、ログのあちこちに散っているか、そもそも残っていなかった。

| 残っていなかったもの | なぜ | どうしたか |
|---|---|---|
| 思わぬエラーの全文 | Flask は例外を `flask.app` ロガーへ出すが、そこには書き先が無かった(`pythonw` では標準エラーも消える) | `app/tracing.py` が受け、**記録番号**を付けて全文と入力を残す。画面にも同じ番号を返す(500 `internal`) |
| 断った理由 | 断りは画面に出すだけだった | 400/403/409/422 を `code` と文言ごと残す(`断りました ...`) |
| 何をした後だったか | 操作を残していなかった | 状態を変える要求を1行ずつ(`操作 POST ... → 200 (12ms) \| body=...`) |
| 画面(JS)のエラー | ブラウザの開発者ツールにしか出ない | `errlog.js` が `/api/client-log` へ送り、番号付きで残す |
| 裏のスレッドの例外 | `threading` の既定は標準エラーへ出すだけ | `threading.excepthook` / `sys.excepthook` で番号付きで残す |
| いつから共有に届かなかったか | 送れない理由は20秒ごとに DEBUG で並ぶだけ | 同期の**状態の変わり目**だけ WARNING / INFO で残す(`…15秒ぶりに戻りました`) |
| どの端末の・どの設定のログか | 起動の記録に版しか無かった | 見出しに PC名・ログインID・ライン・参照パス・ログの書き先 |

### 1行の形

```text
2026/10/01 08:00:09.500 | ERROR | calendar_app.app.request | waitress-2 | r=DDDDDD 記録番号=E20261001-080009-K3Q | 思わぬエラー ...
日時(ミリ秒)            | 重さ  | 出どころ                 | スレッド   | 追跡                                  | 本文
```

* **追跡番号**は `ContextVar` に持つ。画面からの要求1回ごとに `r=`、同期1回ごとに `s=`
  (「今すぐ同期」は要求の `r=` のまま ── 押した操作とつながるように)。
  同じ番号の行を拾えば、その1回で何が起きたかが揃う
* **記録番号**は ERROR 以上に必ず付く(`_TraceFilter`)。呼ぶ側が `extra={"ref": ...}` で
  渡せばそれを使う ── **画面に出した番号とログの番号が違うと、たどれない**
* 番号は `E` + 日時 + 読み違えにくい3文字。日時が入っているので、集めた何十台ぶんの
  ログでも、まず日付のファイルに絞れる
* フィルタは**ハンドラに**付ける。flask・waitress のようなよそのロガーの行も同じ形にそろう

### 残さないもの

* **パスワード**。キーに `password` / `パスワード` / `token` を含む値は `***` に伏せる。
  ログは共有フォルダに置かれうる
* 起動トークン(`?t=`)。画面のURLも伏せて送る
* 1秒ごとの問い合わせ(`/api/sync`・`/api/alive`・`/api/health`)。1日に何万行も出て、
  肝心の操作が埋もれる。遅かった(3秒以上)ときだけ残す
* 同じ断りの繰り返し。開きっぱなしの古いタブが毎秒断られても、60秒に1行にまとめる
* 画面のエラーの繰り返し。1画面10件まで・同じ文言は10分に1回・全体で1分30件まで

### ログフォルダ

`settings.json` の `ログフォルダ`(設定画面「9. ログ」・配布設定にも入る)。

| 決めごと | 理由 |
|---|---|
| `<指定>\<PC名>\calendar_YYYYMMDD.log` | 共有を指定して全台が同じ場所へ書いても混ざらない。掃除(30日)も自分のフォルダだけ |
| 保存のときに**実際に書いて**確かめる | フォルダが見えるだけでは、書く権限があるかは分からない。受けてから書けないと分かっても、ローカルへ逃げて動き続けるので設定した人は気づかない |
| **書けないときはローカルへ書き続ける**(起動時・途中で切れたとき) | ログが要る日ほどネットワークが不調。切れた瞬間の1行も落とさない(同じ行を逃げた先へ書き直す)。逃げたことは逃げた先に1行残し、設定画面の「直すべきこと」にも出す |
| 指定先へ戻るのは**日付が変わったとき・設定を保存し直したとき** | 1行ごとに見に行くと、共有が止まっているあいだ1行ごとに数秒待たされる |
| 保存したらその場で付け替える(`reconfigure`) | 起動し直さないと効かない設定は、効いたかどうかを確かめられない |
| 付け替えたら新しい書き先にも見出しを書く | 起動の記録は前の書き先にしか無い。新しい書き先のログだけを渡された人が読めなくなる |
| 書くのは同期(キューを挟まない) | 落ちる直前の行こそ要る。キューに積んだまま落ちると消える |
| パスワードは要らない | 業務データの行き先は変わらない。変わるのは「ログがどこにあるか」だけで、それは画面に出ている |

### なぜなぜ分析の材料(`calendar_app/log_report.py`)

記録番号を1つ受けて、1枚にまとめる。設定画面と `tools/log_report.py`(集めた
フォルダを下まで探す)はこれを呼ぶだけ。

| 欄 | 拾い方 |
|---|---|
| 直接の原因 | トレースバックの最後の例外。場所は**こちらのコード**(`calendar_app/`・`app/`)の最後のフレーム ── ライブラリの中を指しても直す場所にならない |
| 原因のつながり | `The above exception was the direct cause ...` / `During handling ...` で区切った各段の例外。根本に近い順 |
| 同じ操作の記録 | 同じ追跡番号の行(DEBUG も含む) |
| 直前の流れ | その前の INFO 以上 30 行 |
| 起動時の様子 | いちばん近い見出し(`起動:` / `見出し:`)。前の日に起動していれば7日まで戻る |
| 画面のエラー | Python の形ではないので、文言が直接の原因、`場所:`(JS の何行目か)が場所 |

**推測は書かない。** 原因を推し量って書くと、読む人がそれを事実と取り違える。
なぜ1〜5・真因・対策・確かめ方は空欄の枠だけ出す。

一覧(最近の記録番号)は、ファイルを全部解析せず**記録番号を含む行だけ**を拾う。
7日ぶんで十数MBになりうるので、設定画面を開いたときではなく押したときだけ読む
(`GET /api/logs`)。

## 8.10 デスクトップ版 ── ポートを使わない(VER4.0.0)

外枠(Rust/Tauri、`src-tauri/`)が窓を持ち、Python(`bridge.py`)を子として起動して
**標準入出力**で要求を渡す。画面は独自の宛先 `app://localhost/`(WebView2 は
`http://app.localhost/`)を読み、ネットワークを通らない。詳しくは
[`デスクトップ版.md`](デスクトップ版.md)。作りは梱包資材総合ツール(python-web-tools)と同じ。

| 決めごと | 理由 |
|---|---|
| 業務は Python のまま。Flask は「URL を関数に振り分ける部品」として残し、待ち受け(waitress)だけ使わない | 重い計算は無く、遅いのは共有フォルダとのやりとり。経路と試験(700 件近く)がこの形で書かれている。書き直す利点が無く危険だけがある |
| 守り(トークン・Host・別オリジン・画面の取り合い)は**そのまま通す**。Host だけ外枠の宛先名を足す(`app_config.BRIDGE_HOSTS`) | 2通りの守りを持つと、片方だけ直す |
| 起動の流れ(待機画面 → 組み立て → 初期化)は `start_app` と共有(`start_bridge`) | 同上 |
| 心拍による自動終了(`idle_exit`)は使わない | 窓が終わりを決める。ブラウザの事情(裏のタブの間引き)を推し量る必要が無い |
| **終わる前に未送信を送り切る**(`sync_service.send_before_exit`、最大 8 秒)。送れなければ件数を覚える | ブラウザ版は見張りが粘って送っていた(§8.4)。窓を閉じたら終わるので、その粘りを終了の手順に移す。「停止を頼んだ」は送り終えてから立てる ── 先に立てると起動側の上限つき待ちが送っている途中で落とす |
| 外枠が先に閉じても(止められても)、Python は送れるだけ送る(5 秒) | 外枠は 8 秒待ってから止める |
| 印刷は外枠の別窓。「閉じる」は外枠に頼む | 外枠の窓は新しいタブを持たない。`window.close` は効かない |
| 「ファイルに保存」は外枠が保存先を訊いて書く | WebView のダウンロードは OS で動きが違う(何も起きないことがある) |
| 外枠は **Python が書けないこと**だけを `desktop_shell.log` に残す | Python が見つからない・起動できない・知らせずに落ちた、は Python のログには残らない(後から追えるように、§8.9) |
| 版は3か所(`config/app.json`・`tauri.conf.json`・`Cargo.toml`)。試験で一致を見る | exe のプロパティと画面の帯の版を食い違わせない |
| 外枠が Python へ渡す Host は**画面の宛先(Origin)から決める**(`page_host`)。要求の URI からは取らない | WebView2 は画面を `http://app.localhost/` で開くが、外枠が受ける URI は `app://localhost/` になる。URI から取ると Origin と合わず、**更新の要求がすべて「別のページ」と断られた**(Windows の起動確認で見つかった。Linux では両方 `localhost` で気づけない)。起動確認(`desktop_smoke`)は、守りに断られた操作があれば NG にする |

## 10. 分かっている穴

* **同期は1台につき1プロセス**。同じPCで2つ起動することは
  `launch_guard` が防ぎますが、別々のフォルダから違う `app_id` で
  起動すれば通ります(運用でそうしない前提)
* **画面の締め出しは「取って代われる」ことで解いています**(§3.4)。
  2枚目を開いた人が [この画面で使う] を押せば、先に使っていた画面から
  奪えます。**押さないと入れない**という作りにすると、ブラウザが落ちた
  ときに45秒待たされるので、そちらを選びました。同じPCを2人で
  取り合う状況は想定していません
* **管理者パスワードはUIガードです**(§8.2)。誤って押されないための
  もので、「誰がその端末を使えるか」は決めません。知っている人なら誰でも
  変えられますし、設定ファイルを直接書き換えれば通ります
* **端末一覧は自己申告です**(§8.1)。起動されていない端末の行は古いまま
  (最終更新で分かる)で、記録できなかった端末は載りません。
  「一覧に無い = そのPCは無い」ではありません
* **`/api/settings/browse` はサーバから見えるフォルダを歩けます。**
  名前しか返さず件数にも上限がありますが、フォルダ構成そのものは見えます。
  守りは §6 の3つが担っています
* **裏に回ったタブでは終わりません**(§8.5)。そのかわり、裏に回したまま
  ブラウザごと落ちて閉じた合図が届かなかったときは、プロセスが残ります。
  次に `Start.vbs` を押せば合流するので、困ることはありません。
  表のまま心拍が90秒途絶えたときは、今までどおり終わります
* **共有が10分以上落ちていると、未送信を残したまま終了します**(§8.4)。
  送り終わるまでは終わりませんが、届かないままなら諦めます。入力は
  失われず次回に送られ、残したことはログと端末一覧に出ますが、
  **その日のうちに他のラインへは届きません**
* **休止をまたいだとき**は、見張りの1周があいたことで気づき、そこから
  数え直します(§8.5)。単調時計と実時刻の大きいほうで見るので、休止中に
  単調時計が進む OS でも止まる OS でも気づけます
* **取り込み元は共有フォルダ上の SQLite です。** Access のような
  レコード単位のロックは無く、SMB 上のロックは OS 任せです。緩和策は
  §4.2 に入れてありますが、同時書き込みが極端に増える運用
  (数十台が数秒おきに書く、など)は想定していません
* **取り込み元を WAL にしないでください。** 共有フォルダに置いた WAL の
  ファイルは誰からも開けなくなります。アプリと変換ツールは
  `journal_mode=DELETE` で開きますが、他のツールで WAL 化はできてしまいます
