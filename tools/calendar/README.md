# ライン管理カレンダー (VBA → Python/Web 移行版) — VER4.1.2

> **日報複合ツールの一部です。** このツールは日報複合ツール([`../../README.md`](../../README.md))の
> `tools/` の下に入っています。**デスクトップ版は 日報複合ツール.exe の窓の「カレンダー」のタブ**です。
> このツールだけの exe(`ライン管理カレンダー.exe(LineCalendar.exe)`)と外枠のソース(`src-tauri/`)は、日報複合ツールの外枠に置き換わりました(以下の説明のうち、単体の exe・`src-tauri/`・GitHub Actions の話は、日報複合ツールの [`docs/デスクトップ版.md`](../../docs/デスクトップ版.md) を見てください)。
> このフォルダの `Start.vbs`(ブラウザ版)は単体でも動きますが、日報複合ツールの窓でカレンダーが
> 開いているときは起動しません(**後から開いたほうが止まります**)。

Excel VBA + Access で動いていた「ライン管理カレンダー」を
**Python + ブラウザ**で置き換えたものです。画面は Flask + HTML/CSS/JS、
業務ロジックは Python、データは**すべて SQLite (`.sqlite3`)**。
Excel も Access も不要で、追加で入れるパッケージは `Flask` と `waitress` の2つだけです
(npm / webpack のようなフロント側のビルド工程は持ちません)。

**普段は `ライン管理カレンダー.exe`(デスクトップ版)をダブルクリックするだけです。**
ポートを使わずに専用の窓で開きます(外枠は Rust/Tauri、業務の処理は今までどおり Python)。
exe が無いとき・動かないときは `Start.vbs`(ブラウザ版)で同じものが使えます。

## 1. 設計の考え方

**正式なデータは共有フォルダに置いた「取り込み元」(`.sqlite3`) だけ**です。
各 PC のローカル SQLite は、次の 2 つの役割しか持ちません。

* 表示を速くするための**読み取り用の写し**
* まだ取り込み元へ送れていない入力を貯めておく**送信待ちの置き場 (outbox)**

VBA 版は毎回 Access へ直接読み書きしていましたが、
ネットワーク越しの往復が遅いためローカルに写しを挟んでいます。

```
ライン1のPC                共有フォルダ              ライン2のPC
┌──────────────┐        ┌───────────┐        ┌──────────────┐
│ SQLite(ローカル) │        │ .sqlite3   │        │ SQLite(ローカル) │
│ ・表示用の写し    │◄──読込──│ (共有・正)  │──読込──►│ ・表示用の写し    │
│ ・送信待ちの入力  │──書込──►│            │◄─書込──│ ・送信待ちの入力  │
└──────────────┘        └───────────┘        └──────────────┘
```

処理の流れ:

```
入力 → ローカル SQLite に保存 (即座に画面へ反映)
         ↓ 直後に自動で
       取り込み元へ送信 (送れたら送信待ちから消す)
         ↓ 一定間隔 (既定 20 秒) で
       取り込み元から取り込み直す (他ラインの登録が見えるようになる)
```

* **読み書きとも Python 標準の `sqlite3`** で行います
  (`calendar_app/dbkit/source_db.py`)。ドライバも Access 本体も要りません。
* **送れなかった場合** — ロック競合・共有フォルダが見えないなどで送信に失敗しても、
  入力は送信待ちに残り、次の機会に送り直します。**入力が失われることはありません。**

### なぜ Access をやめたか

VER3.1.0 で取り込み元を `.accdb` から `.sqlite3` へ寄せました。

| | Access のころ | いま |
|---|---|---|
| 読み取り | `.accdb` のバイナリを自前で解析 (約 800 行) | 標準の `sqlite3` |
| 書き込み | ODBC (`odbc32.dll` を ctypes で直呼び) か `cscript` + ADODB | 標準の `sqlite3` |
| 書けない端末 | 反映用ファイルを書き出して別 PC で流す手動運用 | **無くなった** (どの端末からでも書ける) |
| 書き込み経路の試験 | Windows + ACE が要り、開発機では 1 行も動かせなかった | **そのまま試験できる** |

「書き込み経路を試験できない」のが一番の問題でした。壊れても気づくのは
現場で使ったときで、しかも症状は「保存できたつもり」です。

> **代わりに増えた注意点があります (7 章)。** Access はレコード単位の
> ロックを持っていましたが、SQLite の共有フォルダ (SMB) 上でのロックは
> OS 任せです。そのため
> **WAL を使わない (`journal_mode=DELETE`) / `busy_timeout` を置く /
> 書き込みは 1 トランザクションで短く終える / 書く前に控えを取る**
> の 4 点を入れてあります。

### 既存の Access からの移行

`tools/convert_accdb.py` で 1 回だけ変換します。

```bat
python tools\convert_accdb.py 連絡帳.accdb 梱包資材マスタ.accdb -d 出力先フォルダ
python tools\convert_accdb.py --inspect 連絡帳.accdb     中身を見るだけ
```

* 変換するのはカレンダーが使う 3 表 (`休み管理` / `削除履歴` / `班員名簿`) だけです。
  それ以外は「変換しなかった表」として報告します (黙って落としません)。
* 日付・日時は手元の SQLite と同じ `yyyy/mm/dd` 形式の TEXT にそろえます。
* 出力先に同名のファイルがあれば止まります。`--force` を付けると
  **控えを取ってから**置き換えます。

変換が終わったら、設定画面の「参照パス」に出力先のフォルダを指定します。
`.accdb` を読むコードはこのツールだけが使っており
(`calendar_app/accdb/reader.py`)、アプリ本体はもう `.accdb` を見ません。

## 3. 使い方

### 3-1. 準備 (最初の 1 回だけ)

```bat
pip install -r requirements.txt
```

### 3-1-1. 配布する前に (管理者向け)

#### 設定はどこに保存されるか

**置き場所は3つあり、性質が違います。** 設定画面の **「7. ファイルの置き場所」** に、
この端末での実際の場所と一緒に一覧で出ます。

| 置き場所 | ファイル | 中身 | 注意 |
|---|---|---|---|
| **この端末だけ** (`%LOCALAPPDATA%\LineCalendar\`。このPC・このWindows利用者で引き継ぐ) | `data\settings.json` | この端末の設定 (ライン・参照パス・自動同期・この端末で変えた管理者パスワード・配布設定を読んだ記録) | 消すと初めの状態に戻る |
| | `data\calendar.db` | 共有の写し (休み管理・削除履歴・班員名簿・アクセス権限) と、**まだ送れていない入力** | **消さない** (送信待ちが届かなくなる) |
| | `backup\` `logs\` | 控え・動きの記録 (ログ。**ログフォルダを指定すると、そちらへ書く**: 3-7) | 消してもアプリは動く |
| | `runtime\` `cache\` `work\` `pycache\` | 実行中の情報・一時ファイル | 止めているときなら消してよい |
| **全端末で共有** (参照パスの先) | `連絡帳.sqlite3` | 休み管理・削除履歴・端末一覧 | 全端末の正式なデータ |
| | `梱包資材マスタ.sqlite3` | 班員名簿・アクセス権限 (梱包資材総合ツールと共用) | マスタ管理から直す |
| **アプリのフォルダ** (配ると一緒に届く) | `配布設定\` | 配る前に書き出した設定 | 配った先が起動時に読み込む |
| | `config\app.json` | 版番号・ポートなど | 新しい版で差し替わる |

同じ PC でも**別の人がログインすると「この端末だけ」のファイルは別**になり、
別の PC へは付いていきません。

**端末の設定は、アプリのフォルダには保存されません。**
`%LOCALAPPDATA%\LineCalendar\data\settings.json` に、
**Windows の利用者ごと・PC ごとに別々に**保存されます。

| 保存される値 | 画面 |
|---|---|
| `保存用DBフォルダ` / `マスタDBフォルダ` (参照パス) | 設定 → 2. 参照パス |
| `PCライン` | 設定 → 1. この端末のライン |
| `管理者パスワード` (撹拌した値) | 設定 → 5. 管理者パスワード |
| `自動同期` / `自動同期間隔秒` | 設定 → 2. 参照パス |
| `ログフォルダ` | 設定 → 9. ログ |
| `画面の見た目` (自動 / ライト / ダーク) | 帯の「暗くする / 明るくする」・設定 → 10. 画面の見た目 |

そのため**配る前の PC で設定しても、配った先には付いていきません**
(配った先で最初に起動したときに、空の `settings.json` ができます)。
**配った先で1台ずつ打ち直さなくて済むように、「配布設定」があります** (下記)。

#### 配布設定 ── 1台で決めた設定を、そのまま配る

1台で設定を済ませて、その設定ごと配れます。配った先では**起動したときに
自動で読み込む**ので、1台ずつ設定画面を開いて打ち直す必要はありません。

1. 一度起動して、設定画面の「2. 参照パス」「5. 管理者パスワード」を決める
2. 設定画面の **「6. 配布設定」** を開く
3. 配る項目を選ぶ (既定で、ライン以外が選ばれています)
4. 管理者パスワードを入れて **[配布設定を書き出す]**
5. ツールのフォルダの直下 (**`start.bat` と同じ階層**) に **`配布設定\`** が
   できます。配布用フォルダを作って配ってください (次の「配布用フォルダを作る」。
   `配布設定\` も一緒に入ります)

**配布先に関わるものは、すべて `配布設定\` に入ります。**

```text
<ツールのフォルダ>\
  start.bat
  Start.vbs
  配布設定\
    設定.json          置き場所・自動同期・取り込み間隔・ログフォルダ・管理者パスワード(撹拌した値)
                       ・ライン(選んだときだけ)
    はじめに読む.txt   何が入っているか・配った先で何が起きるか
```

| | 扱い |
|---|---|
| ライン | **既定で入れません。** 端末ごとに違うので、配った先の「1. この端末のライン」で選ぶか、端末一覧で予約する (3-4-2) |
| 管理者パスワード | 撹拌した値が入ります (平文は入りません) |
| この端末で変えていない項目 | 入れません。配った先も同じ既定で動きます |

**配った先での読み込み**

* 起動したとき、`配布設定\` があれば読み込みます
* **その端末にすでにあるものは読み込みません。** 値が入っている項目は
  そのまま (無い項目だけ埋める)
* だから、読んだあとに端末で直した値が、次の起動で戻されることはありません
* 揃えたいときは「配布設定を読み込み直す」(すでにあるものも上書き)
* 読み込んだかは **設定 → 8. いまの状態** の「配布設定の読み込み」で確かめられます
* 読み込んだあとの最初の同期で、休み・連絡と**班員名簿**が入ります。
  ラインだけは配っていないので、「1. この端末のライン」で選ぶか、端末一覧で予約してください
* 置き場所を `Z:\` のような**ドライブ文字**で書き出すと注意が出ます。
  ドライブ文字は PC ごとに割り当てが違うことがあるので、`\\サーバ名\共有` の形が確実です

書き出す・読み込み直す・消すには、**管理者パスワード**が要ります。

**管理者パスワードは配る前に変えてください。** 初期値 `nisk` は
この README に書いてあるので、そのままでは関門の意味がありません。
「5. 管理者パスワード」で変えてから書き出すと、変えた値 (撹拌した値) が
配られます。配布設定から読み込んだ端末で違うパスワードを打つと、
「配布した人に確認してください」と出ます (README の初期値へは案内しません)。

#### 配布用フォルダを作る

配るものだけを新しいフォルダへ写します。手でコピーすると `tests\` や、
開発機の設定・送信待ち (`sync\` `logs\` `settings.json` など) が紛れるので、
こちらを使ってください。

1. 設定も配るなら、先に設定画面の「6. 配布設定」で書き出しておく
2. `tools\make_dist.bat` をダブルクリック (または `python tools\make_dist.py`)
3. ツールのフォルダの隣に **`ライン管理カレンダー_VER版`** ができます。
   これを配ってください。中の **`配布メモ.txt`** に、入れた配布設定と
   配った先ですることが書いてあります

| 付けるもの | すること |
|---|---|
| `--out 場所` | 作る場所を決める |
| `--zip` | zip も作る |
| `--no-settings` | 配布設定を入れない |
| `--force` | 作る場所に前の中身があれば消して作り直す |

* ツールのフォルダの中には作りません (次に作るとき、前のものまで写すため)
* 中身のある場所には、`--force` を付けないかぎり作りません
* 作ったあと、`tests\` などが入っていないことを確かめ、入っていたら
  作るのをやめます

#### 配るときに気をつけること

| 気をつけること | なぜ |
|---|---|
| **共有フォルダ (データ側) は「フォルダに」書き込み権限を付ける** | SQLite は書くときに同じフォルダへ `連絡帳.sqlite3-journal` を作ります。**ファイルだけ書けてもフォルダに書けないと保存できません** |
| 各 PC に **Python 3.9 以上**と、`pip install -r requirements.txt` | Python はインストール時に「Add python.exe to PATH」にチェック。社内プロキシで pip が通らないときは、Flask と waitress の wheel を持ち込んでください |
| **全 PC を同じ版にそろえる** | 端末一覧の「版」列で、古い版が残っていないか確かめられます |
| 配布先で `start.bat --check` を 1 回 | Python・パッケージ・書き込み先がそろっているかをその場で確かめられます |
| 取り込み元は **WAL にしない** (`journal_mode=DELETE`) | 変換ツールが作るものは DELETE です。別の道具で開いて WAL にされると、共有の上では誰も開けなくなります |
| 配るときは `tools\make_dist.bat` で作ったフォルダを使う | 手でコピーすると `tests\` や開発機の設定が紛れます |

**アプリのフォルダは共有に置いてもかまいません。** 実行中に書くものは
すべて `%LOCALAPPDATA%\LineCalendar\` へ行き、アプリのフォルダには
何も書きません (Python の `__pycache__` もローカルへ向けてあります)。

### 3-2. 起動する

**`ライン管理カレンダー.exe` をダブルクリック**します(デスクトップ版)。
専用の窓が開き、「起動しています」→ 待機画面 → カレンダーと進みます。

* **ポートを使いません。** 画面と Python のやりとりは exe の中で済むので、
  ポートの取り合い・プロキシ・セキュリティ製品の影響を受けません
* 2回ダブルクリックしても、開いている窓が前に出るだけです
* 窓の × か、画面の「終了」で終わります。**送れていない入力があれば送ってから**閉じます
  (同期の途中なら、中断してよいか訊きます)
* 印刷は別の窓で開きます。「印刷する」で印刷ダイアログ、「閉じる」でその窓だけ閉じます
* Python は今までどおり各PCのものを使います(要るのは Flask だけ)。
  見つからないときは、入れ方が窓に出ます
* 作り・ブラウザ版との違いは [`docs/デスクトップ版.md`](docs/デスクトップ版.md)

#### ブラウザ版(予備)

**`Start.vbs` をダブルクリック**します。コンソールは出ず、
既定のブラウザにカレンダーが開きます。以下の「画面(タブ)も1枚だけ」「自動で終わる」
などはブラウザ版の話です(デスクトップ版は窓が1つなので要りません)。

起動しないときは `start.bat` を使うと、コンソールに原因が表示されます。

```bat
start.bat --check      実行環境の確認だけして終わる
start.bat              コンソールを開いたまま起動する
```

> **2回ダブルクリックしても、起動するのは1つだけです。** 2つ目は
> 「すでに起動しています」と言って、動いているほうのブラウザを開きます
> (画面が出るまで少し間があるので、つい2回押してしまいます)。

#### 画面(タブ)も1枚だけです

起動が1つでも、**ブラウザのタブは何枚でも開けてしまいます。**
2枚開くと、どちらでも登録できて、どちらも「自分が見ているものが最新」の
顔をします ── 片方で登録してももう片方は古いまま、設定を両方で開けば
後から保存したほうが黙って勝つ、という形で出ます。壊れたようには
見えないぶん、**どちらが本当か分からない**のが一番困ります。

そこで、**2枚目は開いた時点で断ります。**

```
┌────────────────────────────────┐
│  すでに別の画面で開いています        │
│                                │
│  この端末では、別のタブでこのツールを  │
│  開いています。…                  │
│                                │
│           [ この画面で使う ]        │
└────────────────────────────────┘
```

* **締め出されません。** [この画面で使う] を押せば、こちらへ切り替わります
  (前の画面はそこで操作できなくなり、そのことが画面に出ます)。
* 前の画面が異常終了して合図を送れなかったときも、**45秒で自動的に空きます**。
  ブラウザごと落ちた・PCが固まった、といった場合です。
* **同じタブの中の移動(カレンダー↔設定)は2枚目として数えません。**
* タブを閉じれば、その場で次の画面が使えます。
* 裏に回しているタブ (別のタブを見ている・最小化している) も「使用中」です。
  2 枚目を開くと断られます。そのタブが残っていないのに断られるときは、
  「この画面で使う」を押してください。

断るのは画面だけではありません。画面の作りに関係なく、
**使ってよい画面以外からの登録・削除・設定変更はサーバ側で断ります**
(`calendar_app/screen_lock.py`)。
なお `stop.bat` のように画面を持たない経路は巻き込みません。

> プロセスの二重起動 (`launch_guard`) とは別の仕組みです。
> あちらは「起動を1つに絞る」、こちらは「その1つを使う画面を1枚に絞る」。
> 片方を止めても、もう片方は止まりません。

### 3-3. 終了する

画面右上の **[終了]** を押します。タブを閉じただけでも、
しばらくすると自動で終了します。確実に止めたいときは `stop.bat` です。

**裏に回したタブでは終了しません。** 別のタブや Excel に切り替える・
ブラウザを最小化する、のあいだは、ブラウザが心拍のタイマーを間引いたり
タブを凍らせたりしますが、それで終わることはありません。表に戻せば、
すぐに接続を確かめて最新の状態に取り直します。PC のスリープから戻ったときも
同じです (戻った瞬間に終わることはありません)。

**未送信の入力があるあいだは終了しません。** 送り終わるまで(最大10分)
待ってから終わります ── 蓋を閉じて帰った端末が、翌朝ふたを開けた瞬間に
「送らずに終了」していたのを防ぐためです。共有に届く状態なら、
開けてから20秒ほどで送り終わって静かに終了します。
届かないままなら10分で諦め、**残したことを記録します** (3-4-2)。

### 3-4. 設定 (最初の 1 回だけ)

左のレールから **[設定]** を開き、上から順に決めます。

1. **この端末のライン** — 休み・コメントの表示絞り込みに効きます
2. **参照パス** — 取り込み元の**フォルダ**。[参照] で辿れます
3. **取り込む** — 参照パスから取り込みます
4. **マスタ確認・管理** — 班員名簿の確認と修正 / 端末一覧 / 削除履歴
5. **管理者パスワード** — 1 と 2 を変えるときに聞かれます

> **参照パスが決まるまで、休み・連絡の登録はできません。**
> 送り先が無いまま登録すると、入力がこの端末に溜まったまま
> 他のラインに届かないためです (7 章)。

**参照パスはフォルダで持ちます。** ファイルのフルパスにすると、
上流がファイル名を変えただけで動かなくなり、現場からは
「急に読めなくなった」としか見えません。フォルダなら
`連絡帳2026.sqlite3` のように名前が変わっても拾えます。

| 設定 | 中身 |
|---|---|
| 保存用DB のフォルダ | `連絡帳.sqlite3`(休み管理・削除履歴)がある場所 |
| マスタDB のフォルダ | `梱包資材マスタ.sqlite3`(班員名簿)がある場所。**空欄なら保存用と同じ場所**を見ます |

**班員名簿は自動同期のたびにマスタDBから入れ直します** (休み・連絡と同じ間隔)。
配ったばかりの端末でも、最初の同期で名簿が入ります。マスタDB が見えないときも
休み・連絡の同期は止まりません (設定画面に理由が出ます)。

班員名簿は CSV からも取り込めます (マスタ DB が見られない端末向け)。
列は VBA と同じ順 (`管理番号,苗字,班,名前,読み,担当ライン`) で、
Excel が書き出した Shift_JIS の CSV もそのまま読めます。

コマンドからも取り込めます。

```bat
python tools\import_source.py 連絡帳.sqlite3 梱包資材マスタ.sqlite3
python tools\import_source.py --inspect 連絡帳.sqlite3     中身を見るだけ
python tools\import_source.py --members-csv 班員名簿.csv
```

> **ライン設定と参照パスを変えるには管理者パスワードが要ります。**
> VBA 版はどの端末からでも誰でもライン設定を変えられましたが、
> 押し間違えた端末では**何も起きていないように見えたまま表示だけがずれます**
> ── 気づくのは「あの連絡が来ていない」と言われたときです。
> どちらも「毎日使うもの」ではなく「最初に1度決めるもの」なので、
> 関門を置いても手数は増えません (3-4-3)。

### 3-4-1. マスタ管理 (班員名簿の修正)

設定画面の「マスタ管理」で、班員名簿の**確認と修正**ができます。
名前や班が違っていると「休みにしたい人が一覧に出ない」となるため、
DB を開ける人を探さずに直せるようにしてあります。

**直す先は取り込み元 (共有の `.sqlite3`) だけです。** 手元の SQLite は
取り込みのたびに総入れ替えされるので、直しても次の取り込みで消えます。

```
画面 → 取り込み元へ書く → その表だけ取り込み直す → 手元が追いつく
```

最後の取り込み直しはアプリが自動で行います。「直したのに効かない」を
起こさないためです。

* 行を指す鍵は `管理番号`。**あとから変えられません** (変えると同じ人が 2 行に増えます)
* `管理番号` と `名前` は空にできません
* **マスタDB のパスが無い / ファイルが見つからない / 開けない / 班員名簿が入っていない**
  ときは、見るだけになり、理由がその場に出ます
* 書く前に控えを取ります (`%LOCALAPPDATA%\LineCalendar\backup\`)。
  共有フォルダ上の SQLite は最悪の壊れ方が「破損」になりうるためです。
  控えは `sqlite3` の写し取りで作るので、**他の端末が書いている最中でも
  中身が混ざりません**。続けて直すときは 5 分に 1 回にまとめます
  (1 行ごとに共有を丸ごと読むと、台数ぶん行き来が増えるため)
* **列名を押すと並べ替えます。** 押すたびに 昇順 ▲ → 降順 ▼ → 元の並び と変わります。
  数だけの列は数として並べ (`2` が `10` より前)、空欄はどちらの向きでも最後です。
  並べ替えはアプリ側で行うので、**200 行を超える表でも全行の中での順番**になります。
  保存したあとも同じ並びのまま戻ります。打ちかけの行があるときは、
  消えてよいか先に確かめます

### 3-4-2. マスタ確認 (どのPCがどの設定か / 削除履歴)

同じ画面の表の切り替えで、**班員名簿・端末一覧・削除履歴**を選べます。
確かめたいものと直したいものを別の画面に分けると、探すところから始まるためです。

#### 端末一覧

各PCの設定が見えます。

| 列 | 何が分かるか |
|---|---|
| PC名 / ログインID | どの端末か |
| ライン | **その端末に何が表示されるか** |
| 保存用DB / マスタDB のフォルダ | 参照パスの取り違え |
| 版 | 更新が行き渡っていない端末 |
| 最終更新 | しばらく起動されていない端末 |
| 未送信のまま終了 | **前回、送れないまま終わった端末**(件数と日時) |

これが無いと、ライン設定を調べる手立ては**その端末まで歩いて行って
設定画面を開くこと**だけでした。各端末が同期のついでに自分の設定を
置いていくので、どこに行かずに確かめられます。

**「ライン」は実績なので直せません。** そこを直しても、その端末の
`settings.json` は変わらず次の同期で元に戻ります。
**直ったように見えて直っていない**のが一番たちが悪いので、断ります。

#### 前もってラインを決めておく (ライン予約)

直すのではなく、**「次はこうしてほしい」を置きます**。
一覧の **[次のライン]** に入れておくと、**その端末が次に起動したときに
自分で受け取り**、自分の設定に反映してから予約を消します。

```
一覧の [次のライン] に入れる      → 予約日時・予約者も一緒に残る
        ↓
その端末が次に起動する            → 受け取って settings.json に入れる
        ↓
一覧の [ライン] が変わる           → 効いたことが一覧で分かる
   [次のライン] は空になる
```

* **まだ一度も起動していない PC も登録できます。** [行を追加] で PC 名と
  次のラインを入れておけば、配ったあと最初の起動で効きます
  (ログイン ID を空にすると**そのPCの誰でも**向け、入れるとその人向け。
  両方あればその人向けが優先です)
* **効くのは次の起動のときだけです。** 使っている最中に黙って切り替わると、
  その人には何も起きていないように見えたまま表示だけがずれるためです
* **管理者パスワードが要ります。** 他の端末のラインを決めるのは、その端末で
  ラインを変えるのと同じこと ── むしろ目の前に無いぶん危ないので、
  同じ関門を通します
* 一覧に無いライン名を入れてしまった場合は、受け取らずに予約を消して
  ログに残します (毎回同じ警告が出るだけの状態を作らないため)

**使わなくなった端末の行は消せます。** 入れ替えたPCの行が残り続けると
「まだ古い設定の端末がある」ように見えて、探しに行くことになります。
消してもその端末が次に起動すればまた出るので、取り返しはつきます。

**1 行は「ログインID@PC名」です。** 設定は `%LOCALAPPDATA%` に置くので
**Windows の利用者ごとに別**で、3 交替で同じ PC を別の ID で使えば
ライン設定も別々に持てます。PC 名だけを鍵にすると、その 2 人が 1 行を
奪い合い、後から起動したほうの設定だけが見えることになります。
逆に、同じ ID で別の PC を使う場合は PC 名 が違うので別の行になります。

> 前の版が作った一覧 (PC 名が鍵) は、次に起動したときに自動で作り直します。
> 記録されていた内容はそのまま引き継ぎます (先に控えも取ります)。

> 記録は**変わったときと、古くなったとき (既定 6 時間) だけ**書きます。
> 共有フォルダ上の SQLite は同時書き込みが弱点なので (7 章)、
> 台数ぶん書き込みを増やさないようにしてあります。

#### 削除履歴

**カレンダーから消したものを、後から探せます。** 表の切り替えで
**[削除履歴]** を選ぶと、新しい順に並びます (直近を探しに来るためです)。
絞り込み欄で日付・名前・ライン・削除実行者から探せます。

| 列 | 中身 |
|---|---|
| 削除日時 / 削除実行者 | **いつ・どの端末の誰が**消したか (`ログインID@PC名`) |
| 対象日付 / 区分 / 登録内容 / 識別コード / 班 / ライン | **何が**消えたか |

**ここからは直せません。** 記録なので、直せる記録は記録になりません。
消した内容はカレンダーから削除した時点で必ずここに残ります。

### 3-4-2-1. アクセス権限 (この端末で使えるラインを ID と PC名 で決める)

ライン設定はこれまで管理者パスワードだけで守っていました。パスワードは
教え合えるので、**「誰か(どの端末か)」で決められるように**しました。
梱包資材マスタの **`アクセス権限` 表** (梱包資材総合ツールと共用) を使います。

| ログインID | PC名 | 権限 | 有効 | 意味 |
|---|---|---|---|---|
| yamada | (空) | コイル | 1 | 山田さんはどの PC でもコイル |
| (空) | NLM-PC-042 | 作業長 | 1 | この PC は誰でも作業長 |
| yamada | NLM-PC-042 | mode:field | 1 | (梱包資材総合ツールの現場モード。このツールは読まない) |

* **権限にはライン名を入れます。** この表は別ツールと共用なので、
  `mode:field` (現場モード)・`mode:material` (資材モード) など
  ライン名以外の値も入ります。このツールはライン名の行だけを読み、
  ほかの行はそのまま残します
* 空欄は「問わない」です。ただし **ログインID と PC名 の両方が空の行は
  効きません** (全員への許可になるため。別ツールと同じ決まり)
* 大文字小文字は区別しません。当たる行が複数あれば、どのラインも使えます

**行の足し方:** 設定 → 4. マスタ確認・管理 → 表で「アクセス権限」を選び、
[行を追加]。管理番号は自動で振られます。権限の欄にはライン名などの候補が出ます
(候補以外も入れられます)。**足す・直す・消すには管理者パスワードが要ります。**
表が梱包資材マスタに無ければ、同期のときと行を足すときに作ります
(形は梱包資材総合ツールと同じです)。

**この端末のラインへの効き方:**

| この端末(ログインID・PC名)の行 | ラインの切り替え |
|---|---|
| **ある** (1 行) | **そのラインに固定**。画面では選べません |
| **ある** (複数行) | そのラインの中でだけ選べます。切り替えには**管理者パスワード**が要ります |
| **無い** (表が無い・登録していない) | 今までどおり、**管理者パスワード**でどのラインにも切り替えられます (登録前に全員が締め出されないように) |

* **表に無いラインは、パスワードを知っていても選べません。** ほかのラインに
  するときは、マスタ管理でアクセス権限の行を直します (これにも管理者パスワードが要ります)

* いまのラインが表に無ければ、**起動したときと、同期で表を取り込み直したとき**に
  表のラインへ合わせます。マスタ管理で行を直せば、開いたままの端末も次の同期で
  合います。端末一覧の「次のライン」(予約) で表に無いラインが入っていても、表が優先です
* 設定画面「1. この端末のライン」に、この端末のログインID と PC名、使えるラインが
  出ます (登録が無ければ、何を足せばよいかも出ます)

### 3-4-3. 管理者パスワード

ライン設定と参照パスを変えるときに聞かれます。設定画面の
**[管理者パスワード]** から、この端末だけで変えられます。

* **初期値は `nisk` です。** 変更していない端末はこれで通ります。
  **配る前に変えて、「6. 配布設定」で書き出してください** (3-1-1)
* 保存するのは撹拌した値だけで、**平文では持ちません** (PBKDF2)
* **忘れたときは** `settings.json` の `管理者パスワード` の行を消すと
  既定に戻ります
  (`配布設定` があるツールでは、次の起動で配布設定のパスワードが入ります)

> **違うときは「違います」と出ます。** 同じ問いが出続けるときは
> 打ち間違いではなく、3 回で打ち切って戻し方を案内します。

> **これはアクセス制御ではありません。** 誤って押されないための
> ガードで、パスワードを知っている人なら誰でも変えられますし、
> 設定ファイルを直接書き換えれば通ります。

### 3-5. 同期の状態

画面上部の帯に常に出ています。

| 表示 | 意味 |
|---|---|
| `自動同期オフ` | 参照パスが未設定。**登録もできません** |
| `同期済み (日時)` | 送信済みで、その日時の取り込み元の内容を表示している |
| `送信待ち N 件` | 送信中、または次の送信を待っている |
| `未送信 N 件 / 理由` | 送れていない (入力は保持されている。復旧すれば自動で送られる) |

すぐ反映したいときは帯の **[今すぐ同期]** を押します。

**開いたままでも画面は自動で描き直されます。** 他ラインの登録が取り込まれた
とき(既定 20 秒ごと)と、日付が変わったときに、触らずに最新になります
── 帯だけが「同期済み」と言って中身が古い、という状態を作らないためです。
選んでいる途中(ダイアログを開いているあいだ)は描き直さず、閉じたあとに
追いつきます。

> tkinter 版・VER3.0.0 にあった **[反映用ファイルを書き出す]**
> (`sync_*.sql` + `apply_*.vbs` を作り、Access が使える PC で流す手動運用) は、
> **無くなりました。** 取り込み元が `.sqlite3` になり、
> どの端末からでも直接書けるようになったためです。

### 3-6. 版(バージョン)の確かめ方

端末はフォルダごとコピーして配るので、「その端末に入っているのはどれか」を
聞かれます。**聞かれる場面ごとに、その場で読める場所に出してあります。**

| 場面 | どこを読むか |
|---|---|
| 使っているとき | 画面左上の帯。`ライン管理カレンダー` の右の `VER3.1.0` |
| 紙を渡されたとき | 印刷した 1 枚の**右下**(出力日時と並べてあります) |
| 起動できないとき | 起動エラーの画面の右上 / 起動待機画面 |
| ログだけ渡されたとき | `calendar_YYYYMMDD.log` の**1 枚目**(`起動: pid=... VER3.1.0`)。ログフォルダを変えた日は `見出し: ...` の行にも出ます |
| コマンドで調べるとき | `start.bat --check` の「バージョン」 |
| 他の端末のぶん | 設定画面の**端末一覧**の「版」列 (3-4-2) |

出どころは `config/app.json` の `version` **ただ 1 つ**です。
上げるときはそこだけ直します (画面の表示・`/api/health`・端末一覧が追随します)。

> 版が変わると、開いたままのタブは**自動で読み込み直します**。
> 古い画面で新しいサーバを叩かせないためです (`health.js`)。

### 3-6-1. 画面の見た目 (ライト / ダーク)

上の帯の **「暗くする / 明るくする」** を押すと、背景を暗い色 (ダーク) と明るい色 (ライト) で
切り替えられます。夜勤や暗い場所で画面がまぶしいときに使ってください。

* **設定 → 10. 画面の見た目** では「自動 (Windows の設定に合わせる)」も選べます。
  最初は「ライト」です (日報複合ツールの4ツールでそろえる)
* **この端末だけ**の設定です (`settings.json`)。他の端末には効きません。開き直しても覚えています
* 日曜・祝日は赤系、土曜は青系、当日は橙の枠、履歴はセピア系 ── **色の意味はどちらでも同じ**です
* 印刷は見た目に関係なく、いつも白い紙の色で刷ります

### 3-7. エラーの後追い (ログ・なぜなぜ分析)

エラーが起きたあとで困るのは、**事実が残っていない**ことです。
「押したら赤いのが出た」だけでは、いつ・どの端末で・何をしていて・何が原因だったかが
分かりません。そこで、**なぜなぜ分析の「事実」の欄をログから埋められる**ようにしてあります。

#### 記録番号

思わぬエラーが起きると、画面に **記録番号** が出ます。

```text
思わぬエラーが起きました(記録番号 E20261001-142233-K3Q)。
もう一度やってもだめなときは、この番号を管理者に伝えてください。
```

* 番号の頭は**日時**です (`E` + 年月日 + 時分秒 + 3文字)。番号だけで、どの日のログかが分かります
* 読み違えやすい字 (0/O・1/I・5/S など) は使っていません。電話で読み上げても伝わります
* **画面(ブラウザ)で起きたエラー**も、サーバのログに番号付きで残します。
  ブラウザの中のエラーは、そのままでは誰も気づけない (「押しても何も起きない」としか見えない) ためです
* 裏の処理 (同期など) が例外で止まったときも、番号付きで残します

#### まとめる (設定 → 9. ログ)

記録番号を入れて **[まとめる]** を押すと、次の1枚ができます。
**[写す]** で報告書や表計算に貼れます。**[ファイルに保存]** でテキストにもできます。

| 欄 | 中身 |
|---|---|
| 何が起きたか | 日時・端末(PC名)・どこで(画面からの操作 / 同期 / 画面(ブラウザ) / 裏の処理)・内容 |
| 直接の原因 | 最後に起きた例外と、**このツールのコードのどこか** (ファイルと行) |
| 原因のつながり | 例外が別の例外から起きていれば、その連鎖 (上ほど根本に近い) |
| 同じ操作の記録 | その1回の操作でほかに何が書かれたか |
| 直前の流れ | その前に何をしていたか (操作・同期の状態の変わり目・断り) |
| 起動時の様子 | 版・PC名・ログインID・ライン・参照パス・ログの書き先 |
| なぜなぜ | なぜ1〜5・真因・対策・確かめ方 (空欄。**ここから下は人が埋めます**) |

**原因の推測は書きません。** 書くと、読む人がそれを事実と取り違えるためです。
並べるのはログにあった事実だけです。

**[最近の記録を読む]** で、最近 7 日の記録番号を新しい順に出せます (番号を聞きそびれたとき)。

#### ログに残るもの

| 残るもの | 例 | 何に使うか |
|---|---|---|
| 操作 | `操作 POST /api/rest → 200 (12ms) \| body={...}` | 何をした後に起きたか |
| 断り | `断りました POST /api/rest → 422 duplicate: すでに登録されています` | 「登録できなかった」と言われたとき、**なぜ断ったか** |
| 思わぬエラー | `思わぬエラー ...` + 入力 + 例外の全文 + 記録番号 | 直接の原因・場所 |
| 画面のエラー | `画面でエラー: TypeError: ...` + どのJSの何行目か | 画面の中で起きたこと |
| 同期の状態の変わり目 | `同期の状態: 同期済み → 取り込み元へ送れません(...)` / `...15秒ぶりに戻りました` | **いつから・いつまで**共有に届かなかったか |
| 見出し | 版・PC名・ログインID・ライン・参照パス | どの端末の・どの設定のログか |

* どの行にも**追跡番号** (`r=XXXXXX` は画面からの1回の操作、`s=XXXXXX` は同期1回) が付きます。
  同じ番号の行を拾えば、その1回で何が起きたかが揃います
* **パスワードは残しません** (`"password": "***"` と伏せます)
* 1 秒ごとの問い合わせ (同期の状態・心拍) は残しません。肝心の操作が埋もれるためです。
  同じ断りが続くときは 60 秒に 1 行にまとめます (開きっぱなしの古いタブなど)

#### ログフォルダ (書き先を変える)

既定では、この端末の `%LOCALAPPDATA%\LineCalendar\logs\` に書きます。
**設定 → 9. ログ** でフォルダを指定すると、そちらへ書きます。

```text
<指定したフォルダ>\
  PC-01\calendar_20261001.log
  PC-02\calendar_20261001.log
```

* 指定したフォルダの中に **PC名のフォルダ** を作って書きます。
  共有フォルダを指定すれば、全端末のログを1か所に集められます (混ざりません)
* 保存するときに、**実際に書けるか**を確かめます (無いフォルダ・書けないフォルダは断ります)
* 保存したらすぐに切り替わります (起動し直さなくてよい)。新しい書き先にも見出し (版・端末・ライン) を書きます
* **指定先に書けないとき (ネットワークが切れた・共有が止まった) は、この端末の既定の場所へ書き続けます。**
  ログが要る日ほどネットワークが不調だからです。切り替えたことは既定の場所のログに 1 行残り、
  設定画面のいちばん上にも出ます。指定先へは、日付が変わったとき・設定を保存し直したときに戻ります
* 30 日より古いログは、その端末が自分のフォルダのぶんだけ消します
* 全端末に同じフォルダを配るときは「6. 配布設定」に入れられます (ドライブ文字だと注意が出ます)
* パスワードは要りません (業務データの行き先は変わらないため)

#### 集めたログをまとめて見る (管理者向け)

ログフォルダを共有にしてあれば、`tools\log_report.bat` (または `python tools\log_report.py`) で
全端末ぶんを探せます。

```text
tools\log_report.bat --dir \\サーバ\共有\カレンダーログ                       … 最近7日の記録番号の一覧(端末名つき)
tools\log_report.bat E20261001-142233-K3Q --dir \\サーバ\共有\カレンダーログ  … 1件をまとめる
tools\log_report.bat E20261001-142233-K3Q --out なぜなぜ材料.txt                … ファイルに書く
```

## 4. 操作方法 (VBA 版と同じ)

日付をクリックすると **[休み] [コメント・連絡] [内容閲覧] [削除]** を選べます。

* **休み** — 作業者を選び、3 交替 (A/B/C/D 班) の場合は直と
  残業繋ぎ・早出繋ぎの担当者を続けて選びます
  (**休む本人 → 直 → 残業繋ぎ → 早出繋ぎ** の 4 段階です)。
  繋ぎは**休んだ直の前が残業・次が早出**なので、
  2 直の休みなら「1 直の残業で繋ぐ人」「3 直の早出で繋ぐ人」と聞きます。
  この 2 つは作業者の一覧が続けて出るため、**残業は橙・早出は青緑**で
  見出しの帯ごと色を変え、**ここまでに選んだもの**を画面上部に出して
  取り違えを防いでいます (色だけに頼らず、札の文字と段数でも分かります)。
  A/B/C/D 以外 (昼勤・日勤など) は 3 交替に属さないため、直の確認をせずに登録します。
  同じ日に同じ人を二重登録しようとすると警告します
  (この時点で見えるのは手元に取り込んだ内容までです。
  他ラインとの重複は取り込み元へ送る時点で防ぎます → 7 章)。
* **コメント・連絡** — ライン → 班の 2 段階で対象を絞ってから本文を入力します。
  1 つ目を選ぶと 2 つ目の候補が実在する組み合わせだけに絞られます。
* **内容閲覧** — その日の全登録内容を表示します (閲覧のみ)。
* **削除** — 消したいものだけチェックして削除します。削除内容は必ず履歴に残ります。

セルにマウスを乗せると、残業繋ぎ・早出繋ぎがツールチップで表示されます
(VBA 版の `ControlTipText` に相当)。当日のセルはオレンジ枠で強調されます。
`PageUp` / `PageDown` で月を移動できます。

### 表示の絞り込み

PC のライン設定によって、セルに出す内容が変わります (VBA 版と同一)。

| PC のライン設定 | 休みの表示 | コメントの表示 |
|---|---|---|
| 作業長 | 全ライン | 全ライン |
| コイル | コイルのみ | コイル宛のみ |
| その他のライン | コイル以外すべて | 自分のライン宛のみ |

### 印刷

**[印刷]** ボタン (カレンダー・履歴のどちらにもあります) で、A4 横 1 ページの
印刷プレビューを別タブで開きます。プレビューの上の **[印刷する]** を押すと
印刷ダイアログが開きます (Ctrl+P でも同じ)。「PDF に保存」を選べば PDF 化できます。
**[閉じる]** でそのタブを閉じます。ボタンと案内は紙には刷られません。
VBA 版は Excel シートを作って `PrintPreview` していましたが、
Excel に依存しないようこの方式にしています。

**文字・罫線・色帯は、すべて紙の端から 8mm 以上内側に描きます。**
プリンターは紙の縁から約 4mm には印刷できず、ブラウザのプレビューは
紙の端まで描くので、プレビューで収まって見えても紙では欠けることがあります。
そのため余白はページの内側で取っていて、印刷ダイアログの余白設定に
左右されません。

* 余白は **「既定」のまま**で印刷してください (「なし」「最小」でも欠けませんが、
  「最小」などで余白を足すと少し小さく刷られます)
* **倍率は変えないでください。** 登録の多い月は、1 枚に収まるように
  自動で縮めて刷ります (切り捨てはしません)
* 曜日の見出しや土日祝の色は、「背景のグラフィック」を入れなくても刷られます
* 印刷用のタブでは、描いてよい範囲を点線で示しています (点線は刷られません)

### 履歴 (過去の月を見る・編集不可)

レールの **[履歴]** で、過去の月を**見るだけ**の画面が開きます。
ここからは登録も削除もできません (ボタンも、書き込む道もありません)。
昔の月を調べている途中で押し間違えて、過去の記録が変わらないようにするためです。

1. **[年月を選ぶ]** を押すと、年ごとに 12 か月のマスが出ます。
   [前の年] [次の年] で年を移り、見たい月を押します
2. 各マスに**その月の登録件数**が出ます (0 件の月も選べます)
3. 日付を押すと、その日の登録内容が出ます (読むだけ)
4. [前月] [翌月] で隣の月へ、[印刷] でその月を印刷できます

* 選べるのは、**登録がある最も古い月から先月まで**です。今月以降は
  カレンダー画面で見てください (選べない月は点線で、押せません)
* 他の端末が消した・直したものは、同期で取り込まれしだい表示に反映されます
* **見た目をカレンダー画面と変えてあります。** 紙のようなセピア色の地に
  左の茶色の帯、上に「履歴・閲覧のみ」の札が出ます (土曜・日曜祝日の色分けは
  同じ向きのまま、色味だけ落としてあります)

### 主な変更点と理由

* **レジストリ → JSON** — Windows 以外でも動かせるようにするため。
* **Excel 印刷 → HTML 印刷** — Excel への依存を外すため。体裁と色分けは踏襲しています。
* **9 要素の配列 → `DayRecord`** — VBA では `item(7)` が班、`item(8)` がラインでしたが、
  意味が読み取れないため名前付きの構造体にしました。
* **ロック競合リトライの移動** — Access のファイルロック対策 (`IsLockError` と
  最大 3 回のリトライ) は、PC ごとに独立した SQLite に対しては不要ですが、
  **共有の取り込み元へ書き込む場面では依然として必要**です。
  そのため同じ判定基準のまま取り込み元への書き込み側へ移しました (7 章)。
  手元の SQLite 側は `busy_timeout` の設定に留めています。
* **Access → SQLite** — 1 章の「なぜ Access をやめたか」を参照。
* **ライン設定に関門を置きました** — VBA 版は
  `frmCalendar` の [ライン設定] ボタンから誰でもどこでも変えられました。
  ライン設定は「この端末に何を見せるか」を決めるもので、押し間違えても
  **その端末の人には何も起きていないように見えます**。管理者パスワードを
  要る形にし、併せて**どのPCがどの設定かを一覧で確かめられる**ようにしました
  (3-4-2 / 3-4-3)。
* **tkinter → ブラウザ** — 下の 5-1 を参照。

### DB 周りの再利用可能な部分 (`calendar_app/dbkit/`)

取り込み元との連携の汎用的な部分は `calendar_app/dbkit/` に切り出してあり、
このアプリを一切知らずに動きます。他の VBA → Python 移行案件でも
そのままコピーして使えます。

| モジュール | 役割 |
|---|---|
| `source_db.py` | 共有フォルダ上の `.sqlite3` への接続 (3 通りの開き方、ロック再試行、`INSERT`/`UPDATE`/`DELETE` の組み立て、WHERE 無しの更新・削除の拒否、状態調べ `probe()`、控え取り) |
| `outbox_sync.py` | 手元の SQLite → 取り込み元への「追加」の送信待ち管理 (予約・確定・期限切れ回収)。`Access同期記録` テーブルを自前で用意する |
| `sqlite_toolkit.py` | 手元の SQLite 側のちょっとした共通処理 (ロック再試行付き実行、`INSERT`/`UPDATE` の組み立て、値のサニタイズ) |

`source_db.py` は取り込み元を**3 通りの順で開きます**
── URI (`mode=ro`) → 素のパス → 手元への写し。
共有フォルダでは 1 つ目が通らないことがあり、
「開けません」だけで止めると現場では原因に辿り着けないためです。
写しから読んだときは**その旨を必ず言います** (中身が少し古いことがあるため)。
写しは**読み取りのときだけ**で、書き込みには決して使いません。

> テーブル名 `Access同期記録` は Access をやめた後もそのままです。
> 名前を変えると**それまでの送信記録が読めなくなり、全件が再送**になります。
> 名前より、既に送ったという事実のほうが大事です。

このアプリ固有の部分 (`calendar_app/sync/`) は、上記を土台に
「休みの二重登録防止」「削除の転送」「どのテーブルをどう送るか」
といったカレンダー特有のルールだけを実装しています。
削除の送信待ち管理は `outbox_sync.py` が追加しか面倒を見ないため、
アプリ側 (`sync/deletes.py` + `db._pending_deletes`) で別途行っています。

### 起動基盤も再利用できます

`start_app.py` / `launch_guard.py` / `server.py` / `boot_server.py` /
`process_manager.py` / `calendar_app/app_config.py` / `boot_screen.py` /
`idle_exit.py` は、社内「汎用Webアプリ作成 基盤仕様書」の実装です。
アプリ固有の値は `config/app.json` に集約してあるので、
**そこを書き換えれば別のアプリの土台になります**。

## 6. データの保存先

**PC ごとに持つ**のが前提です (基盤仕様書 2.7)。

```
%LOCALAPPDATA%\LineCalendar\
├── data\      calendar.db (SQLite) / settings.json
├── logs\      calendar_YYYYMMDD.log (日付が変わると書き先も移る / 30日で消す。
│              ログフォルダを指定すると <指定先>\<PC名>\ へ書く: 3-7)
├── runtime\   app.lock (PID・ポート・トークン) / instance.lock (起動の入口)
├── work\      起動エラー.html などの一時ファイル
├── cache\  backup\  pycache\
```

Windows 以外では `~/.local/share/LineCalendar/` を使います。
環境変数 `CALENDAR_HOME` (業務データ) と `CALENDAR_LOCAL_DIR` (領域ごと)
で差し替えられます。

> **共有フォルダに置いて複数 PC で 1 つの `calendar.db` を共有しないでください。**
> SQLite は SMB 共有上ではファイルロックが正しく働かないことがあり、
> 同時書き込みでデータベースが壊れる可能性があります。
> 複数ラインで運用する場合は「PC ごとに `calendar.db` / 共有するのは
> 取り込み元の `.sqlite3` 1 つ」という構成にしてください (次章)。
> 共有するほうにも同じ性質があるため、緩和策を入れてあります (次章)。

アプリ本体 (このフォルダ) は共有フォルダに置いてかまいません。
実行中に変化するファイルは上のローカル領域にしか書きません。

## 7. 複数ラインでの同時運用

各 PC が自分の SQLite を持ち、**共有するのは取り込み元だけ**という構成です。

```
 L-1 のPC   [SQLite] ─┐  送信(標準の sqlite3)
 HVC のPC   [SQLite] ─┼─→ 共有フォルダの 連絡帳.sqlite3 (正)
 コイルのPC [SQLite] ─┘  ←─ 取り込み
```

### 何が同時アクセスされるのか

| 対象 | 同時アクセス | 対策 |
|---|---|---|
| PC ごとの `calendar.db` | 起きない (プロセスは `launch_guard` が ── 起動の入口をOSの排他ロックで1つに絞る、画面は `screen_lock` が ── タブを2枚開かせない) | 更新は 1 トランザクションにまとめ、`busy_timeout` を設定。要求ごとに接続を開き直す |
| 共有の取り込み元への**書き込み** | **起きる** (複数ラインが同時に送信) | 下の 4 点。ロック競合を検出して再試行し (`dbkit.source_db.is_lock_error`、最大 3 回・1/2/3 秒待機)、送れなければ送信待ちに残して次回やり直す |
| **同じ行**への同時の書き込み | **起きる** (2人が同じ班員を直す / 同じ日に同じ文面の連絡を出す) | マスタは「開いたときの値」と合わなければ 409 で断る。削除の転送は**班・ラインまで見て1行だけ**消す (9 章) |
| 共有の取り込み元からの**読み取り** | **起きる** | `busy_timeout` を置き、読めなければ再試行する。直接開けないときは手元へ写して読み、**その旨を必ず表示する** |

### 共有フォルダ上の SQLite で気をつけていること

Access はレコード単位のロックを持っていましたが、SQLite の共有フォルダ (SMB)
上でのロックは OS 任せです。**壊れ方が「エラー」ではなく「破損」になりうる**
のがこの構成の唯一の弱点なので、次の 4 点を入れてあります。

| 対策 | なぜ |
|---|---|
| `journal_mode = DELETE` (**WAL にしない**) | WAL は共有メモリ (`-shm`) を使う。SMB にはそれが無く、WAL のまま置くとそのファイルは誰からも開けなくなる |
| `busy_timeout` (10 秒) | 他ラインが書いている最中でも、すぐ諦めずに待つ |
| 書き込みは **1 文ずつ短いトランザクション**で終える | 掴んでいる時間が短いほど、鉢合わせも、途中で切れる危険も減る |
| **書く前に控えを取る** (`backup\`、直近 10 世代) | 万一壊れても戻せる状態を先に作る。マスタは全員が使う |

変換ツールが作る `.sqlite3` も `journal_mode=DELETE` です。
`-wal` / `-shm` が残っているファイルを見つけたときは、
`probe()` がその旨と次の一手を返します。

VBA 版にあった SQL 単位のロックリトライ (`ExecuteSQLWithRetry` / `IsLockError`) は、
**取り込み元への書き込み側に同じ判定基準・同じリトライ回数で移植しています。**
手元の SQLite 側は PC ごとに独立しているため不要です。

### 二重登録の防止

VBA は登録前に毎回 Access へ問い合わせていました (`ExistsRecord`)。
Python 版は手元の SQLite しか見られないため、
**別のラインが同じ作業者を同じ日に登録していても、登録時点では気づけません。**

そこで送信する直前に取り込み元へ問い合わせ、同じ日・同じ識別コードの行が
既にあればその 1 件を送りません (`sync/business_rules.py` の `duplicate_guard`)。

```sql
SELECT COUNT(*) FROM "休み管理" WHERE "日付" = ? AND "識別コード" = ?
```

既に登録されていた場合は送らずに取りやめ、**その端末の画面に知らせます**
(「送らなかった登録があります」)。いまカレンダーに出ているのは先に届いた
登録なので、直や繋ぎが違う場合は、その日の登録を確かめて削除してから
登録し直してください。知らせは [閉じる] を押すまで出続けます
(2 枚目のタブなど、使っていない画面には出ません)。

> 以前は画面に何も出ず、後から届いた側で選んだ直や繋ぎが**知らせなしで
> 消えていました** (2 台で同時に登録して確かめたときに見つかりました)。

### 反映漏れ・二重反映の防止

* 取り込み元への送信が成功した時点で、その変更は送信待ちから外れます。
  失敗した場合は残るため、送信漏れは起きません。
* 送信 1 回ごとに**送信ID**を振り、取り込み元側に一意索引を張っています。
  同じ送信が 2 回届いても 2 行にはなりません
  (上の「重複の防止」は**業務上の重複**、こちらは**同じ送信の二重適用**で、
  別々の話です)。
* 反映前に「登録してすぐ削除」した行は、取り込み元へ送らず相殺します。
  そのまま送ると、存在確認で INSERT が飛ばされた場合に、
  続く削除が別ラインの同じ行を消してしまうためです。
* 削除の転送で消すのは**必ず 1 行だけ**です。取り込み元の ID がまだ
  分からないあいだは `日付・区分・登録内容・識別コード・班・ライン` で
  対象を指しますが、この条件は一意とはかぎりません。
  **1 件のつもりで 2 件消すのは取り返しがつかず、消した人にも見えません。**
  消し足りなければ次の転送でまた当たります。

### 同じ行を 2 人が同時に直したとき

マスタ管理は、保存のときに**その画面を開いたときの値**も一緒に送ります。
送る内容が鍵以外の全列なので、これが無いと、後から保存したほうが
自分の触っていない欄まで古い写しで上書きし、先に直した人の修正が
黙って消えます (両方に「直しました」と出てしまいます)。

開いたあとに別の端末が直していれば `409` で断り、**そのときの最新の内容を
画面に出します**。相手の修正を見たうえで、もう一度直せます。

### 表示の遅れについて

ローカル SQLite は写しなので、**手元の表示は最後に取り込んだ時点の取り込み元の内容**です。
既定では 20 秒ごとに取り込み直すため、他ラインの登録は最大 20 秒ほど遅れて見えます。
間隔は設定画面で変えられます (最短 5 秒)。

自分の入力は即座に画面へ出て、その直後に取り込み元へ送られます。

### 参照パスが無いときは登録させない

**正式なデータは共有の取り込み元だけ**で、手元の SQLite は写しと送信待ちの
置き場にすぎません。送り先が決まっていないのに登録を受けると、入力は
その端末に溜まり続け、他のラインには永遠に届きません。
**「保存できたつもり」が一番たちが悪い**ので、入り口で断ります。

| 操作 | 断る条件 |
|---|---|
| 休み・連絡の登録、削除 | 保存用DB(連絡帳)が見つからない |
| 班員名簿の追加・修正・削除 | マスタDB が見つからない / 開けない / 班員名簿が入っていない |

断るのは**そもそも場所が決まっていない**ときだけです。設定してある共有が
一時的に見えないだけ (ネットワーク断・共有の停止) なら断りません ──
そのための送信待ちです。**閲覧・印刷はいつでもできます。**

### 送信できなかったとき

共有フォルダが見えない、他ラインが同時に反映していてロック競合した、
といった場合は送信待ちに残り、次の機会に送り直します。
**入力が失われることはありません。**
未送信の入力がある間は取り込みを行いません
(取り込みはテーブルを入れ替えるため、まだ送れていない入力が消えてしまうからです)。

### Access の数を勝手に変えて読まない (VER4.1.2)

- Access の「単精度浮動小数点型」は 4 バイトの近似値なので、そのまま読むと 2.9 が
  2.9000000953674316 になっていました。Access の画面に出る数(同じ 4 バイトに戻る一番短い 10 進)で
  読みます。「十進型」は桁の並びと小数点の位置を取り違えていて、2971.5 が別の数になっていました。
  小数点の位置は列の定義(精度の次のバイト)から読みます
- 試験: `tests/test_accdb_numbers.py`(2.9・2971.5・100.01725・負の数・桁の大きい整数)

### 同期の状態と「いま同期」の重なり (VER4.1.1)

- 同期の状態を写しで返す(同期の最中に画面が見に来ると、同期が覚えた「前の状態」まで書き換わり、
  変わり目の記録が狂っていた)
- 「いま同期」が背景の同期と重なっても頼みを捨てない(同期していないのに「同期しました」と答えていた)。
  走っている 1 回のあとにもう 1 回回るのを待つ(上限 60 秒。過ぎたら「同期中」と断る)

### 打った行・打った値を黙って失わない (VER4.1.0)

現場の声:「打った行が消えることがありました」「打った値が勝手に戻ることが
ありました」── とんでもない話です。2台・2本の処理が重なったときにだけ
起きる抜け道を、1つずつ塞ぎました。

| 起きていたこと | いまの動き |
|---|---|
| 取り込みが共有を読んでいる数秒のあいだに登録した行が、入れ替えで消えた(送信待ちにも残らない) | 共有を**読み終えてから**手元の錠(`BEGIN IMMEDIATE`)を取り、その中で送信待ちを数え直す。増えていれば入れ替えをやめ、次の周期で送ってから取り込む。錠を待ちきれなかった登録は「いま取り込み中のため、まだ登録していません」(503)と出し、**打った内容を開いたまま残す** |
| 送れない日に「消してから同じ人・同じ日を登録し直す」と、両方とも消えた | 送るときは**削除を先に**送る。削除が届いていない周期は、登録を「先に登録済み」として取りやめずに待つ |
| 送っている最中の行を消すと、次の取り込みで戻ってきた | 「送信中」の行も削除を予約し、**送信ID**でその1行だけを消す |
| 同じ人・同じ日の休みを同時に2回送ると2行できた / 返事が届かずに送り直した連絡が2行できた | 確かめと書き込みを1つの錠の中で行う。画面は「登録する」1回ごとに札(`submit_id`)を付け、同じ札の送り直しは書かずに成功を返す |
| 保存用DBとマスタDBを続けて取り込むあいだに入った登録が、送っていないのに「送信済み」になった | 「送信済み」に揃えるのは**入れ替えた表だけ**。どの取り込み元でも送信待ちを確かめる(名簿だけの取り込み元は断らない) |
| 背景の同期の最中に頼んだ送信が捨てられ、次の周期まで送られなかった | 終わったら続けてもう1回回す |
| 連絡の本文が、背景クリック・Esc・送信の失敗・サーバの起動し直し(黙って読み込み直し)・窓の × で消えた | 本文は打つたびにタブの中(`sessionStorage`)へ置き、読み込み直しても戻す。本文がある画面は閉じる前に訊く。送れなかったら**同じ本文のまま開き直す**。読み込み直す前・日報複合ツールの窓を閉じる前(`alltools:before-close`)・タブを閉じる前に、保存していない入力があれば訊く |
| 設定画面で選んだライン・打ったパスが、帯の同期のたびに描き直されて戻った / 遅れて届いた読み込みが保存した値を戻した / 断られた保存で打ったパスが消えた | 欄ごとに「触った」印を持ち、保存が通るまで描き直しで触らない(印のある欄は色が付く)。保存を挟んだ読み込みの返事は捨てる |
| 参照パスを保存するたびに、切ってあった自動同期が入り直った | 利用者が決めた入切は変えない(はじめて場所を決めた端末だけ入れる) |
| 設定の保存が重なると、片方の値が古い値で上書きされた | 設定ファイルの「読む→直す→書く」を錠で1つずつにし、一時ファイルは書くたびに別の名前にする |
| マスタ管理で、ほかの行の保存・追加・再読込のたびに打ちかけの行が消えた / 追加の値が断られると消えた / 保存のダブルクリックで「先に直されています」と断られた | 打ちかけの行は鍵ごとに覚えて描き直したあとに戻す(開いたときの中身もそのまま)。再読込・絞り込み・表の切り替え・並べ替えは先に訊く。追加は断られたら同じ値で開き直す。保存は返事が来るまでその行のボタンを押せなくする |
| 月の返事が遅れて届くと、移った先の月が古い月に戻った / 「翌月」を続けて2回押しても1か月しか進まなかった / 裏の問い合わせが前に押したボタンを止め、その1回が消えた | 最後に頼んだ月の返事だけを描き、「翌月」は最後に頼んだ月から数える。待機の印は押したその1回にだけ付け、押せるかどうか(`disabled`)には触らない |

試験は `tests/test_data_integrity.py`。

## 8. テーブル構成

取り込み元とテーブル名・列名をそろえています
(名前は VBA / Access のころのまま引き継いでいます)。

**休み管理** — 休みとコメントの本体

| 列 | 内容 |
|---|---|
| ID | 主キー。取り込み時は取り込み元の ID をそのまま使う |
| access_id | 取り込み元側の ID (この端末で追加した行は NULL)。**手元にしかない列** |
| 日付 | `yyyy/mm/dd` |
| 区分 | `休み` または `その他` |
| 登録内容 | 休みなら作業者名、コメントなら本文 |
| 識別コード | 作業者の管理番号 (コメントは `-`) |
| 直 | `1` / `2` / `3` (日勤は空) |
| 残業者 / 早出者 | 繋ぎの担当者名 (未選択は `未登録`) |
| 班 / ライン | 所属 |

**削除履歴** — 削除の追跡用 (いつ・誰が・何を消したか)
**班員名簿** — 作業者マスタ (マスタ DB から取り込む読み取り専用データ)
**Access同期記録** — 取り込み元へ未反映の変更 (`dbkit.outbox_sync` が管理する汎用テーブル。名前が `Access` のままな理由は 5 章)
**_pending_deletes** — 取り込み元へ未転送の削除予約 (`dbkit.outbox_sync` は追加のみ担当のため、削除はこのアプリ側で管理)
**_sync_meta** — 最終取込日時などのメタ情報

**端末設定** — どのPCがどのラインか (取り込み元にだけ置く。手元には取り込みません)。
各端末が自分の行だけを書き、設定が変わったときと 6 時間経ったときに更新します

取り込み元 (共有の `.sqlite3`) が持つのは、上のうち
`休み管理` / `削除履歴` / `班員名簿` と、`端末設定` です
(`端末設定` は最初の端末が同期したときに自動で作られます)。
送信ID の列 (`送信ID`) と一意索引 (`IX_<表名>_送信ID`) は、
初回の送信時にアプリが自動で足します。

設定 (`settings.json`) の主なキー:

| キー | 中身 |
|---|---|
| `PCライン` | この端末のライン |
| `保存用DBフォルダ` / `マスタDBフォルダ` | 参照パス。**フォルダで持つ** |
| `Access保存用DBパス` | 旧設定 (ファイルのフルパス)。読むだけ残してある |
| `自動同期` / `自動同期間隔秒` | 同期の入切と間隔 |
| `管理者パスワード` | 撹拌済みの値 (PBKDF2)。**平文では持ちません**。消すと既定に戻ります |

`休み管理` / `削除履歴` には取り込み元に無い `access_id` 列があるため、
取り込み元への送信は列を除いた VIEW (`休み管理_送信用` / `削除履歴_送信用`) 経由で行います。

| `test_screen_lock.py` | **タブを2枚開かせない**(2枚目を断る・断ったのに書けない・同じタブの移動は数えない・取って代われる・閉じたら次が使える) |

Access リーダ (`calendar_app/accdb/reader.py`) は変換ツールだけが使いますが、
移行の日に 1 回しか動かないぶん失敗に気づきにくいので、試験は残してあります。
実物の `.accdb` (`tests/data/sample.accdb`) を読んで検証しており、
全テーブル (システムテーブル含む) について
**テーブル定義の行数と実際に読めた行数が一致すること**を確認しています。

開発時には、上記に加えて実運用の 2 ファイル
(連絡帳 108 ページ / マスタ 4328 ページ・ユーザーテーブル 25 個・全 4221 行) を
`mdb-export` (mdbtools) の出力と突き合わせ、
**全ユーザーテーブルが 1 セル単位で一致すること**を確認しています。
差異が残るのは MSys 系システムテーブルのバイナリ列 (`SID` / `Owner` / OLE 列) のみで、
これは値ではなく表現形式の違いです。

この照合により、初期実装では次の不具合が見つかり修正しました。
実際の運用データで検証しないと表面化しないものばかりです。

| 不具合 | 症状 | 原因 |
|---|---|---|
| データページの特定 | 一部テーブルの件数が実際より多くなる | 全ページ走査だけに頼り、テーブルから切り離された古いページを拾っていた。使用ページマップと突き合わせるよう修正 |
| 行の列数の検査 | 一部テーブルが 0 件になる | 行の列数がテーブル定義と一致することを要求していた。列を削除した後の行は定義より多い列数を保持している |
| Unicode 圧縮テキスト | `PETバンド` が `PET…` と化ける | 圧縮形式で `0x00` が 1 バイト/2 バイトモードの切替エスケープになることを未考慮 |
| メモ型のページ参照 | 長いメモ型の値が空になる | ページ参照のビット分割を誤っていた (正しくは 下位 8 ビット=行番号 / 上位 24 ビット=ページ番号) |
| 日時の丸め | `10:35:05` が `10:35:04.962` になる | シリアル値の浮動小数点誤差。秒単位に丸めるよう修正 |

## 10. 制限事項

* **取り込み元は共有フォルダ上の SQLite です。** Access のような
  レコード単位のロックは無く、SMB 上のロックは OS 任せです。
  緩和策は入れてありますが (7 章)、
  **取り込み元を WAL (`journal_mode=wal`) にしないでください。**
  共有フォルダに置いた WAL のファイルは、誰からも開けなくなります。
* 変換ツール (`tools/convert_accdb.py`) の制限:
  * パスワードで暗号化された `.accdb` は読めません。Access で暗号化を解除してください。
  * Access 97 (Jet3) 形式は未対応です。Access 2000 以降の形式に変換してください。
  * 添付ファイル型・複数値フィールドは読み取り対象外です (値は `None`)。
  * 変換するのはカレンダーが使う 3 表だけです (他の表は報告して残します)。
* **共有が10分以上落ちていると、未送信を残したまま終了します。**
  送り終わるまでは終了しませんが (3-3)、届かないままなら諦めます。
  入力は失われず、次に起動したときに送られます。残したことは
  ログと端末一覧の「未送信のまま終了」に出るので、翌朝どの端末が
  取りこぼしたかは**その端末へ行かずに**分かります。
* **管理者パスワードはアクセス制御ではありません。** 誤って押されない
  ためのガードで、知っている人なら誰でも変えられますし、設定ファイルを
  直接書き換えれば通ります。「誰がその端末を使えるか」は決めません。
* **端末一覧は各端末の自己申告です。** 起動されていない端末の行は古いまま
  ですし (最終更新で分かります)、記録できなかった端末は載りません。
  「一覧に無い = そのPCは無い」ではありません。
* 未送信の入力が残っている状態では取り込みを行いません
  (取り込みはテーブルを入れ替えるため、送れていない入力が消えてしまうからです)。
  設定画面から取り込むと確認を求め、了承すれば破棄して取り込みます。
* 他ラインの登録が見えるまでに最大で同期間隔ぶん (既定 20 秒) の遅れがあります。
* 元 VBA にあった共有フォルダ上の HTML 説明書を開く機能 (`説明書を開く`) は、
  参照先がイントラネット固有のパスのため移植していません。
