# 移行仕様(VBA → Python)

VBA 版のどの処理が Python 版のどこに移ったか、そして意図的に変えた点をまとめます。

## 0. データアーキテクチャ

**共有 SQLite が正式なデータで、各端末のローカル SQLite はその端末専用の
作業用の写し + 送信待ちの一時置き場です。** VBA 版には「手元の DB」という
概念自体が無く、毎回 Access に直接読み書きしていました。Python 版は
「操作のたびに共有フォルダへ問い合わせると遅い」という問題に対応するために
ローカルの写しを挟んでおり、正式なデータの置き場所が 1 箇所という点は
VBA 版と同じです(`sqlite_path` は既定で端末ごとのローカルディスクを指し、
複数端末で手元の SQLite を共有する構成ではありません)。

正データは当初 Access(.accdb)でしたが、共有 SQLite へ移しました
(**2 層構造はそのまま**。経緯と根拠は 3.11 参照)。

```
 ライン1のPC              共有 SQLite(.sqlite3)            ライン2のPC
┌───────────────┐        ┌──────────────┐        ┌───────────────┐
│ SQLite(ローカル)  │        │              │        │ SQLite(ローカル)  │
│ ・マスタの写し      │◀──読込── │   共有・正データ   │ ──読込──▶│ ・マスタの写し      │
│ ・入力した発注/発送 │──書込──▶│              │◀──書込── │ ・入力した発注/発送 │
└───────────────┘        └──────────────┘        └───────────────┘
```

同期は 2 方向を独立に回します。

* `kanban.db.sync.Exporter` — 手元 → 共有。この端末の操作を、
  変更のあった列だけ既定 60 秒ごと(および操作直後)に書き戻す
* `kanban.db.sync.Importer` — 共有 → 手元。他端末が書き戻した
  内容を、既定 30 秒ごと(および「更新」操作)に取り込む

起動時の 1 回きりの取り込みだけでは、他端末の変更はこの端末を再起動するまで
画面に反映されません。`Importer` はこれを解消するために追加したもので、
VBA 版のダブルクリック再読み込み(共有側から直接読み直す)に相当する処理を
定期的に自動実行しているとも言えます。実際、画面の「更新」操作(ダブル
クリック)は `Importer.run_once()` を同期的に呼んでから画面を再描画します
(`/api/refresh`)。

複数端末が同じ行の異なる列を独立に操作した場合に互いを消し合わないための
仕組みは 3.3.1 を参照してください。

## 1.1 画面の分離

VBA 版と同じく、現場・倉庫・倉庫参照は **それぞれ独立した画面** です。
1 回の起動で開くのはどれか 1 つだけで、モードごとに **別ポートの別プロセス**
として起動します(現場 8741 / 倉庫 8751 / 倉庫参照 8761)。

VBA 版は現場・倉庫それぞれ別々の Excel ブックを配ることでモードを固定して
いました。Python 版は実行ファイルを 1 つに保ったまま、この端末のモードを
ローカル SQLite に記憶させる方式にしています(初回は現場モード、以後は
記憶したモードで直接起動。変更は設定画面から。詳しくは 3.8 参照)。
「モードによって操作できる範囲が完全に分かれる」という制約そのものは
変えていません。

盤面そのものは 3 モードで **同じ 1 つの画面** を使い、違うのは操作可否だけ
です(`presenters/board.py` の `BoardPolicy`)。tkinter 版は同じ「資材フレーム
× サイズ行」をモードごとに 3 回組み立てていましたが、差は次の 3 点しか
ありませんでした。

| モード | サイズ | 発送 | 注文中 |
| --- | --- | --- | --- |
| 現場 | 操作可(※) | 操作可(※) | 表示のみ |
| 倉庫 | 表示のみ | 操作可 | 操作可 |
| 倉庫参照 | 表示のみ | 表示のみ | 表示のみ |

(※)現場のサイズ/発送はラインマスタの `発送無効` で入れ替わります。VBA が
`sizeEnabled = disableShipping` / `shipEnabled = Not disableShipping` として
いたのと同じです。

**操作可否はサーバが決めます。** 画面はボタンを出すだけで、押せるかどうかを
自分で判断しません。加えて、押された側(`app/routes/board.py`)でも同じ判断を
引き直して確かめます — 画面が出したボタンだけを信じると、URL を直接叩かれた
ときに素通しになるためです。

## 2. 業務ルール(そのまま維持)

### サイズ(資材)ボタン

| 現在の状態 | 操作後 |
| --- | --- |
| 未発注 | 欲 = `〇` / 不 = 空 / 更新日 = 現在時刻 / **発送 = クリア** |
| 発注中 | 欲 = 空 / 不 = `〇` / 更新日 = クリア / 発送 = **維持** |
| 発注中 + 発送済み | 「この資材は届いていますか？」で [はい] のときだけ 欲・不・更新日・発送 をリセット |
| **発注中 + 注文中(倉庫対応中)** | **無言で何もしない**(倉庫が注文中を解除するまで現場は一切操作不可) |
| 未発注 + 発送済み(発送処理中に注文が取り消された) | **Python 版で追加**: 出し直さずに「発送処理中に注文が取り消されました」と確認を出す。現場が「確認した」を押すと 発送・倉庫確認日時 をクリア(そのあとは通常どおり) |

### 発送ボタン

* 発注(欲 = `〇`)が無い状態で発送しようとすると「注文がありません。」
* **注文中(保留 = `〇`)の資材を発送すると、発送すると同時に注文中を
  自動的に解除する**(発送 = `〇`・倉庫確認日時 = 現在時刻、かつ 保留・
  注文中日時をクリア。以前のようにエラーで発送を拒む仕様ではない)
* 発送を解除する方向(発送済み→未発送)は注文中の状態を変えない
* 発送 → 発送解除では倉庫確認日時もクリア

### 注文中ボタン(旧: 保留ボタン)

* キャプションは「注文中」(内部の列名・クラス名は旧称の `保留`/
  `cls_HoldButton` のまま)
* **倉庫モードでのみ操作できる**(現場モードでは表示のみ。ボタンの色・
  ツールチップで注文中かどうかは分かるが、押しても何も起きない)
* **理由入力・確認ダイアログはどちらの方向も無く、即座に切り替わる**
  (以前あった「理由入力ポップアップ」「解除確認ダイアログ」はいずれも
  廃止。DB の列自体は変更していない)
* 未注文中 → 注文中にする: 保留 = `〇`・注文中日時 = 現在時刻を自動記録
  (自由入力の理由ではない)。**発送していれば強制解除**(発送 = 空)
  される。欲(現場の赤)は一切変更しない
* **発注の無い行は注文中にできない**(VBA から変えた点。下記 3.16)
* 注文中 → 解除: 保留・注文中日時を即座にクリアする(発送列には触れない)。
  **こちらは発注の有無を見ない** ── 付いた印を外す道は、どんな状態でも残す
* 現場・倉庫どちらの画面でも、注文中のボタン(現場は表示のみのボタン、
  倉庫は操作可能なボタン)にマウスを乗せると注文中の時刻がツールチップで
  見える。倉庫参照モードのラベルはツールチップではなく、キャプションに
  直接時刻(または「注文中」)を表示する

### 一括処理

* 現場「届いた資材を一括確認(リセット)」: 欲 = `〇` **かつ** 発送 = `〇` の行を
  欲・不・更新日・発送・倉庫確認日時までリセット
* 倉庫「表示中のラインを全て発送済みにする」: 欲 = `〇` **かつ** 発送 = 空 の行に
  発送 = `〇` と倉庫確認日時をセット。**注文中かどうかは見ない**(発送
  ボタン単体のクリックとは異なり、一括発送は注文中の有無を判定しない。
  アップロードされた VBA のこの版でも同様であり、Python 版もそのまま
  移植している。そのため一括発送を経由すると、注文中のまま発送済みに
  なる行が実際に起こりうる。下記の印刷除外条件はこのケースも正しく
  除外する)

### 画面表示

* 発注中 = 赤 `RGB(255,100,100)` / 発送済み = 緑 `RGB(100,255,100)` /
  注文中 = 黄 `RGB(255,255,0)` / 既定 `RGB(240,240,240)`
* 非常設品(常設品 = `×`)は青字・斜体、注意書き「※文字色青は非常設品」
* ライン状態ラベル: 起動中 = 黄、閉 = 青
* 資材フレームはサイズ数の多い順、サイズ 1 つだけの資材は後段にまとめる
* ライン表示名: `LS` → `機側`、`L1` → `L-1`
* 倉庫モードの選択中タブは `【 ライン名 】`
* 現場モードでは発送ボタン・注文中ボタン、倉庫モードではサイズボタンが
  操作不可(ラインマスタの `発送無効` に従う。見た目はグレーアウトしない)

### 印刷対象

| 帳票 | 条件 |
| --- | --- |
| 現場の注文票 | 欲 = `〇` かつ 発送 ≠ `〇` かつ **注文中 ≠ `〇`** |
| 倉庫の発送明細 | 欲 = `〇` かつ 発送 = `〇` かつ **注文中 ≠ `〇`** |
| 非常設品リスト | 欲 = `〇` かつ 常設品 = `×` かつ **注文中 ≠ `〇`** |

## 3. 意図的に変えた点

### 3.1 キー列を列順ではなく列名で決める(不具合修正)

VBA は `m_FieldData(1, LBound(m_FieldData, 2))`、つまり **`SELECT *` の先頭列**を
キー列として UPDATE の `WHERE` に使っていました。

実際の `看板マスタ.accdb` を解析すると、`看板_L1` と `看板_大板小板` の 2 テーブルは
`管理番号` が後から追加されており、列順が `資材, サイズ, …, 管理番号` になっています。
このため先頭列を使うと `WHERE [資材] = '外装紙'` のようになり、**同じ資材の複数行を
まとめて書き換えてしまう**危険がありました。

Python 版は列名 `管理番号` を探してキーにします(見つからない場合だけ先頭列に戻し、
その旨をログに残します)。

### 3.2 日時書式の統一

VBA にはボタン操作時の `yyyy/m/d h:mm` と一括処理時の `yyyy/mm/dd hh:nn:ss`
(`NowDBString`)が混在していました。これらは TEXT 列に入り**文字列比較**で
ソート・抽出されるため、混在するとソート順が崩れます。

Python 版は書き込みを `yyyy/mm/dd hh:nn:ss` に統一し、表示だけ `m/d h:mm` に整形します
(`FormatKanbanTime` と同じ見た目)。読み取り側は両方の書式を解釈できます。

### 3.3 排他制御の強化

| | VBA | Python |
| --- | --- | --- |
| ロック競合 | ADO のエラーをリトライ(3 回・1,2,3 秒) | SQLite の `busy_timeout` + `BEGIN IMMEDIATE` + 同条件のリトライ(ローカル SQLite に対して)、Access への読み書きは ADO 側で同じリトライ |
| 競合検出 | `recAffected = 0` で気づく | 行バージョン `rev` による楽観ロック(自端末内の読み取り〜更新間) |
| 読み取り〜更新 | 別々の接続で実行(その間に他端末が変更しうる) | 1 トランザクション内で完結 |
| 一括処理 | 対象収集 → 更新の間に取りこぼしが起きうる | 収集と更新を 1 トランザクションで実行 |

### 3.3.1 列単位の書き戻し保護(dirty_columns)

ローカル SQLite は端末ごとの写しであるため(1.1 参照)、「まだ Access へ送って
いない行の状態列は丸ごと保護し、丸ごと Access へ送る」という単純な実装では、
**この端末が触っていない列まで巻き込んで上書きしてしまう**可能性があります。

具体例: 現場が資材Xを「発注解除」した(欲・不・更新日だけを変更する操作)
直後、まだ Access へ送っていない間に、倉庫が同じ行を Access 上で「発送済み」
にしていたとします。この端末が次に再取り込みや書き戻しを行うとき、

* 発注解除の操作が返す変更内容には、そもそも「発送」列が **含まれていません**
  (VBA のコメント通り「発送は維持」であり、値を読み書きする対象にしない)
* SQLite 側は行ごとに `dirty_columns`(この端末が実際に変更を意図した列名、
  カンマ区切り)を記録しており、書き戻しはその列だけを Access へ送る
* 再取り込みは `dirty_columns` に載っていない列(この例では発送)を
  Access の最新値で更新し、載っている列(欲・不・更新日)はローカルの
  未反映の値のまま保護する

この結果、現場の発注解除と倉庫の発送は独立した列の変更として両立し、
どちらの操作も消えません(`tests/test_sync.py` の
`test_site_and_warehouse_do_not_clobber_each_others_column` で検証)。

なお、この保護のために `order_button_changes` の「欲→不」分岐は、以前は
`"shipped": item.shipped`(ローカルに見えている値をそのまま書き戻す)として
いましたが、ローカルの値が古い場合にこれが誤って発送済みを消す経路になって
いたため、**発送列を返り値に含めない**(＝一切触らない)よう修正しました。

再取り込みはまた、値が実際に変わった場合だけ `rev` を進めます。無条件に
`rev` を進めると、定期的な Access 再取り込みが走るたびに画面が保持している
`expected_rev` が本当は無関係な理由で古くなり、ボタン操作が誤って
「他の端末が同じ項目を更新しました」という競合エラーになってしまうためです。

### 3.3.2 チャンク書き戻しの `use_transaction` を無効化(不具合修正)

`_export_items`(1 ラインぶんの状態列 UPDATE をまとめて Access へ送る処理)は
当初 ADO ブリッジへ `use_transaction=True` で渡していました。ADO ブリッジ
(`ado_bridge.py` の VBScript)は、チャンク内の 1 文が失敗すると
`RollbackTrans` でチャンク全体を巻き戻しますが、それより前に成功していた
文の応答は既に「OK」として応答バッファに積まれてしまっており、Python 側は
それをそのまま成功として受け取ってしまう欠陥がありました。これにより、
実際にはロールバックされて Access に反映されていない更新が「送信済み」と
誤認され、ローカルの `dirty` フラグが消えて再送されなくなる
(サイレントなデータ消失)可能性がありました。

`_export_items` の呼び出し側の結果処理はもともと 1 文ずつ独立に成否判定して
`mark_items_synced` / `mark_items_failed` を呼ぶ設計であり、複数文の
アトミック性を前提にしていません。そのため `use_transaction=False`
(1 文ずつ自動コミット、VBA の元々の 1 行ずつ書き戻す挙動と同じ)へ変更し、
この欠陥を回避しました。`tests/test_sync.py` の
`test_export_items_uses_independent_statements_not_transaction` で
`use_transaction=False` が実際に渡されることを検証しています。

新設した `kanban/accdb/odbc_bridge.py`(ODBC 経由の代替接続経路)は、
そもそも複数文をまたぐロールバックを提供しない設計にしており、この種の
欠陥が構造的に起こり得ません。

### 3.4 印刷方法

Excel シートの生成・`PrintOut` をやめ、印刷用 HTML を作って開きます
(`auto_print` を有効にすると印刷ダイアログを自動表示)。Excel が不要になり、
印刷中に他の作業ができます。

Web 化でここはさらに単純になりました。tkinter 版は帳票 HTML を一時ファイルへ
書き、既定のブラウザで開いていました(`write_document` → `open_document`)。
Web 版はもうブラウザの中に居るので、**URL を 1 つ開くだけ**です
(`/report/<種類>?line=<ライン>`)。一時ファイルも、その後始末も要りません。

帳票が 0 件のときは白紙ではなく「印刷する明細はありません」と出します。
また、印刷ボタンの脇に**押す前に件数**を出します(`/api/report/available`)。

#### 出す前に直せる(現場・倉庫ともに)

**帳票は人へ渡す紙です。** 渡す直前に「この数だけ違う」「この資材名は現場の
呼び方に直したい」と気付くことがあり、Excel 版ではその場でセルを打ち替えて
から印刷できていました。HTML を出しっぱなしにすると、その手が無くなります
── 直すには看板そのものを触るしかなくなり、**紙を直したいだけなのに実データを
動かす**ことになります。

そこで、開いた帳票(= 印刷前の確認画面)の各マスをそのまま打ち替えられる
ようにしました。注文票・発送明細・非常設品リストの**3 種類すべて**です。

| できること | どうなるか |
| --- | --- |
| マスを押して打ち替える | その紙にだけ効きます |
| 左のチェックを外す | その行は印刷されません |
| 「元に戻す」 | システムが出した値へ戻します |
| 「印刷する」 | 印刷ダイアログを出します(Ctrl+P と同じ) |

**共有 DB へは一切書きません。** ここで直すのは紙だけです。実データを触って
いないことがコードを見て分かるよう、この画面の JavaScript には `fetch` も
`form` もありません(テストでも確かめています)。

直した跡は画面では色が付き、外した行は取り消し線になりますが、**紙には
出ません** ── 編集の跡が紙に残ると、受け取った側が「これは何の印か」と
迷います。チェック欄の列も印刷時には消えるので、**打ち替えなければ出来上がる
紙は今までと 1 ドットも変わりません。**

実装は `printing.render_html(doc, editable=True)`(既定)。`editable=False` に
すると、今までどおりの直せない帳票になります。元の値は各マスの `data-orig`
に控えてあり、「元に戻す」はそれを書き戻すだけです ── サーバへ訊き直さないので、
直している最中に他端末が共有 DB を変えても、手元の紙が勝手に書き換わりません。

`auto_print` は今までどおり**開いた直後に**印刷ダイアログを出します。直したい
人はそのダイアログを閉じてから直し、「印刷する」を押せます(押さずに刷りたい
人の手数を増やさないため、既定の動きは変えていません)。

### 3.5 画面の自動更新(**誰も押さなくても追いつく**)

VBA は背景をダブルクリックしたときだけ再読み込みでした。**押す人と押さない
人が出て、押し忘れた端末だけ古い盤を見ていた**というのが、そもそもの不具合の
入り口です。Python 版は誰も押さなくても追いつくようにしています。

| 経路 | 間隔 | 設定 |
| --- | --- | --- |
| 画面 → 手元の SQLite | 5 秒 | `refresh_interval_sec` |
| 手元 ← 共有DB(取り込み) | 30 秒 | `import_interval_sec` |
| 手元 → 共有DB(書き戻し) | 60 秒(**操作直後にも**) | `export_interval_sec` |

自分の操作は即座に画面へ出ます。**他端末の操作が自分の画面に出るまでは
書き戻し + 取り込みで最大 90 秒ほど**(操作直後にも書き戻すので実測は
30 秒前後)。変わっていなければ描き直しません(描き直すとホバー中の
ツールチップが消え、押しかけたボタンが作り直されるため)。

#### 裏に回っていたタブは、戻った瞬間に取り直す

隠れているあいだ(`document.hidden`)は描き直しを止めています ── 見えない
画面のために共有を叩くのは無駄だからです。ところが**ブラウザは裏のタブの
`setInterval` を間引きます**(Chrome は 5 分隠れると 1 分に 1 回まで落とす)。
そのまま待たせると、戻ってきた直後に**最大 1 分ほど古い盤を見せてしまい**、
見ている人には「更新されない」に映ります。

そこで `visibilitychange` / `focus` / `pageshow` で**戻った瞬間に 1 回取り直し
ます**(実測 0.1 秒)。

#### 止まったことが見えるようにする

**自動更新は、動かなくなったことが見えて初めて信用できます。** 共有フォルダが
落ちていると、画面は元気に動いているのに中身だけ古いまま ── VBA 版の
「更新できていないのに気付かない」と同じ形です。

`last_import_at`(**取り込みに成功したときだけ**書かれる)が
`import_interval_sec` の 4 倍(下限 150 秒)より古くなったら、帯に出します。

```
担当 LVC   未反映 0   ⚠ 取り込めていません 12 分前
```

* **順調なときは何も出しません** ── いつも出ていると読まれなくなります
* 1 回や 2 回の失敗では騒ぎません(共有フォルダは瞬間的に落ちることがある)
* 共有が戻れば**自分で消えます**
* `import_interval_sec = 0`(定期取り込みをしない端末)では出しません ──
  古いと言われても直しようがないためです

明示的に取り込み直したいときは、設定画面の「↻ いま取り込む」(3.9)です。

#### 閉じ忘れても、他の端末の邪魔にならない

VBA(Access)では、フォームを開きっぱなしにした端末がいると書き戻せなく
なり、印刷にデータが載らないことがありました。**この構成ではそれが起きません。**

* 共有ファイルを **SQLite として開くのは、書く一瞬だけ**です
  (`with self._connect(...)` の中で 1 文ずつ自動コミット)。読むときは
  そもそも開かず、バイト列を手元へ写してから読みます(3.12)
* **待っているあいだ、共有ファイルに対して何も掴んでいません。** 2 端末を
  開いたまま放置した状態で別プロセスから書き込みを試したところ、ロック待ち
  0.000 秒で書けました
* 端末間の排他(`app_lock`)は**手元の SQLite** にあり、共有側には作りません。
  しかも 120 秒で期限切れになるので、異常終了した端末が残したものは
  次の端末が奪います
* 開きっぱなしの端末も 30 秒ごとに取り込み続けるので、**その端末の画面も
  印刷も古くなりません**

残る影響は「開いている端末」の表示(3.14)に出続けることだけで、これは
事実どおりです。

### 3.6 未反映データの保護

Access へ書き戻す前に再取り込みが走っても、未反映(`dirty`)の行の状態列は
上書きしません。資材名やサイズなどのマスタ列だけ最新化します。

### 3.7 追加した安全策

* Access 側に対象行が無い(削除された)場合は「要確認」として記録し、
  無限に再送しない(5 回で打ち切り)
* 書き戻しは端末間ロックで 1 台ずつ実行し、Access への同時書き込みを避ける
* 数値列に数値以外を入れようとした場合は SQL を組み立てずにエラーにする
  (VBA は `CStr` でそのまま埋め込んでいたため SQL が壊れる可能性があった)
* 操作履歴を `operation_log` テーブルに記録

### 3.8 モード(現場 / 倉庫 / 倉庫参照)の SQLite 記憶化 + 設定画面からの変更

VBA 版は現場・倉庫それぞれ別々の Excel ブックを配ることで、どの画面が
開くかを固定していた。Python 版は実行ファイルを 1 つに保ちたいため、
代わりに次の仕組みにした。

* この端末のモードは `config.json` ではなくローカル SQLite の `meta`
  テーブルへ保存する(`Store.get_device_mode`/`set_device_mode`)。
  `config.json` は導入時にまとめて配る「雛形」の性質が強く複数端末で
  使い回されがちな一方、モードは端末ごとに個別の値であり、かつ
  アプリを再起動せずに変更できるようにしたい(下記)ため、端末固有の
  ローカル SQLite の方が実態に合う。
* 初回起動時、SQLite にモードが記録されていなければモード選択画面
  を出し、選択結果を保存する。以後の起動は
  選択画面を出さず記憶したモードで直接起動する
  (`Application._resolve_mode`)。
* 画面の「設定」→「モードを変更…」から、稼働中に変更することもできる。
  現在のウィンドウを閉じて新しいモードのウィンドウをその場で開き直すだけ
  で、プロセスの再起動は不要(`Application._change_mode`。ライン変更
  `_change_line` と同じやり方)。同期スレッド(`Exporter`/`Importer`)は
  `self.mode` を毎回評価してから使う設計のため、この切り替えだけで
  正しいライン集合に追従する。
* CLI の `--mode` は SQLite の記憶を変えない一時的な上書きとして残して
  ある(検証やバッチ実行向け)。

モード変更・接続パス変更(3.9)は、どちらも端末の役割を左右する操作
であり誤操作の影響が大きいため、共通の管理者パスワードで保護している
(`app/routes/settings.py` の `_check_admin`)。パスワードは平文を保存せず、PBKDF2-HMAC-SHA256
のソルト付きハッシュだけを `config.json` の `admin_password_hash` に持つ。
未設定の状態で保護された操作を初めて行おうとすると、その場で新しい
パスワードの設定を求める(以後はそのパスワードで認証する)。複数端末に
同じ管理者パスワードを持たせたい場合は、ハッシュ済みの
`admin_password_hash` の値をそのまま他端末の `config.json` へコピーすれば
よい(平文はどこにも残らない)。

### 3.8.1 この PC で動いてよいのは 1 つだけ

多重起動の判定は、**これから開こうとしているモードだけでなく、すべての
モードのロックを見ます**(`launch_guard.check_existing`)。モードごとにしか
見ていなかったころ、現場でこうなりました。

1. 現場モードで起動(`site.lock` / ポート 8741)
2. 設定画面でモードを倉庫に変える
3. もう一度ダブルクリック → `warehouse.lock` は無いので**2 つめが起動**

さらに、2 で動いているプロセスの名乗りだけ倉庫に変えていたため、
`site.lock` の相手が「倉庫です」と答えるようになり、`is_our_app` が
**別人と判断してロックを消し、3 つめ**まで立ち上がりました。ログにそのまま
残っています。

```
pid=360 は生きているが site:8741 は自分ではない
ポート 8741 は使用中です
```

直したのは 2 か所です。

* **走ったままモードの名乗りを変えない**(`POST /api/mode`)。モードはポートと
  ロックに結びついているので、走ったまま入れ替えられません。設定画面は
  「次に開いたときのモード」を記録するだけにし、そう画面に出します
* **全モードのロックを見る**。見つけたものの扱いは 3 通り

| 見つけたもの | どうするか |
| --- | --- |
| 同じモード・同じ版 | 合流する(そのブラウザを開く) |
| 違う版 | 古いほうを終わらせて立て直す(更新の経路、5 章) |
| **違うモード** | 同じく終わらせて立て直す |

「違うモードなら終わらせる」がモード変更の受け皿になります ── 変えてから
開き直せば、古いモードは自動で終わり、新しいモードで立ち上がります。
どちらの入れ替えも、**取り込み・書き戻しの途中なら終わらせません**
(中途半端な書き戻しを残すほうが害が大きいので、そのときは合流して次の
起動に任せる)。

### 3.8.2 押してよい画面は 1 枚だけ(`kanban/screen.py`)

**3.8.1 とは別の話です。** あちらが防ぐのは `pythonw.exe` の二重起動で、
こちらが防ぐのは**同じプロセスにタブを 2 枚繋いで、両方から押せてしまう**
ことです。VBA 版はフォームが 1 つしか開けなかったので起きなかった形で、
Web にした時点で新しく持ち込んだ穴でした。

タブは簡単に 2 枚になります。

* ショートカットをもう一度ダブルクリックする
  ── 起動側は「すでに起動中」と判断し、**既存の URL でブラウザを開く**。
  プロセスは増えませんが、**タブは 1 枚増えます**
* アドレスを控えておいて別の窓で開く / タブを複製する

2 枚とも押せると、同じラインの同じ看板を 2 画面で取り合います。片方で
発送を押した時点でもう片方は古い盤を見ており、そこで押すと `rev` が
合わずに「別の端末が更新しました」と断られます ── **別の端末ではなく
自分のもう 1 枚**です。一括発送のように「いま何件か」を数える操作では、
見えている件数と実際の件数がずれます。

**開くこと自体は止めません。止めるのは「2 枚とも押せる」ほうだけです。**
画面は名札(`screen id`)を持ち、持ち主は 1 枚だけ。守りは 2 段構えです。

1. **持ち主でない画面には覆いを出す**(`app/static/js/app.js`)。
   「この画面では操作できません」と理由を出し、`こちらの画面を使う` で
   持ち主を移せる。もう一方を使うならこのタブは閉じてよい、とも書く
2. **サーバも断る**(`app/__init__.py` の `_check_screen`)。持ち主でない
   画面からの「変える操作」は **423** を返す。覆いが出るまでの数秒と、
   覆いを消された場合に素通しになるのを防ぐ

断らないものを 3 つ決めてあります。

| 断らないもの | なぜ |
| --- | --- |
| 読む操作(GET) | 古い盤を見ること自体は害が無い。むしろもう 1 枚で何が起きたかは見えたほうがよい |
| `/api/shutdown` | **使えない画面にも出口を残す。** `stop.bat` もここを叩く |
| 名札を名乗らない相手 | `stop.bat`・試験・手元の `curl` を巻き添えにしない。ここは事故を防ぐ仕切りで、守りはトークンと Host 検証が持つ |

持ち主は**開いただけでは移りません**(作業中の画面が黙って使えなくなる)。
移るのは `こちらの画面を使う` を押したときと、持ち主の返事が
`screen.STALE_SEC`(20 秒)途切れたときだけです。後者が無いと、ブラウザごと
落ちた画面が席を占めたまま**開き直しても二度と押せなくなります**。

#### 閉じたときの取り違えも、ここで直りました

心拍の送り主を区別していなかったので、**2 枚のうち 1 枚を閉じただけで
アプリごと終わって**いました。閉じた合図には猶予 8 秒、心拍は 20 秒間隔
だったため、残った 1 枚の次の心拍が猶予に間に合いません。動いている本体で
再現しています。

```
タブA 心拍: 200
タブB 心拍: 200
タブA だけ閉じる(sendBeacon leaving=1): 200
  ...
  10秒後 タブBから見たサーバ: Connection refused
```

`kanban/screen.py` が画面を数えるようにしたので、**最後の 1 枚が閉じるまで
終わりません**。心拍も 20 秒から 5 秒に縮めました ── 持ち主を移したあと、
奪われた側が 20 秒も押せてしまうためです(手元のメモリを触るだけで共有
フォルダには行かないので、短くしても負荷になりません)。

### 3.9 接続パスの変更(設定画面)— その場で繋ぎ直す

共有 DB の場所が変わった場合、`config.json` を直接編集しなくても
設定画面の「接続先」(管理者パスワード保護)から変更できる。

**変更したら、その場で繋ぎ直して取り込み直します。開き直しは要りません。**

以前は「開き直してください」と案内していました。そのほうが実装は簡単
ですが、**その案内どおりにできない**ことが現場で分かりました ── ブラウザを
閉じても `pythonw.exe` は残り(窓が無いのでタスクマネージャーの「アプリ」
にも出てこない)、次の起動が「すでに起動しています」で止まります。
利用者から見ると「開き直せと言われたので閉じたのに、開けなくなった」。

繋ぎ直しは `start_app._reconnect()` が行います。`Importer` / `Exporter` は
毎回 `self.gateway` を見る作りなので、**属性を差し替えるだけ**で以後の同期が
新しい接続先を使います(スレッドは作り直しません)。差し替えたあと
`importer.run_once()` をその場で回し、取り込めたライン数を画面へ返します。

あわせて、設定画面に **「↻ いま取り込む」**(`POST /api/reimport`、管理者
パスワード保護)を置きました。接続先を変えた直後だけでなく、共有フォルダが
一時的に落ちていて取り込めなかったあとの復旧にも使います。**「開き直す」を
案内に使わないための受け皿**です。

### 3.9.1 画面が居なくなったら終わる(`kanban/idle_exit.py`)

上の不具合には**もう半分**あります。仮に開き直しを求めなくなっても、
**閉じたのにプロセスが残る**こと自体が誤りです。実際に起きたログ:

```
2026/08/31 09:44:18 | すでに起動しています: site (pid=8372 port=8741 版=3.0.0)
2026/08/31 09:44:18 | 起動しません: 同じアプリが起動中
```

tkinter 版には窓があったので、閉じればプロセスも終わりました。Web 版は
**窓とプロセスが別**です。画面(ブラウザ)を閉じてもサーバは生き続け、
しかも窓を持たないため「バックグラウンド プロセス」に埋もれて**利用者には
見つけられません**。基盤仕様書 2.8 / 2.9 が言う自動終了を入れます。

* 画面は `alive_poll_ms`(= `idle_exit.HEARTBEAT_MS`)ごとに
  `POST /api/alive` を打つ。**間隔の出どころはモジュール 1 つ**で、画面へも
  そこから渡す(逆転すると、開いているのに落ちる)
* 閉じるとき(`pagehide`)は `navigator.sendBeacon` で
  `POST /api/alive?leaving=1` を送る。閉じる瞬間の通常の `fetch` は
  捨てられることがあるため。戻る・進むのキャッシュへ入るとき
  (`pagehide` の `persisted`)は閉じたのではないので、裏に回った扱いにする
* `leaving` を受けたら **8 秒待って**から終える(`GRACE_SEC`)。再読込や
  モード切替でも `pagehide` は飛ぶので、猶予の内に心拍が戻れば取り消す
* 心拍が **90 秒**(`IDLE_SEC`)途切れたら終える。閉じる合図が届かない
  経路(タブのクラッシュ)への保険。**ただし裏に回った画面とスリープは別扱い**
  (次の 3.9.1.1)
* **1 度も繋がっていなければ落とさない。** `--no-browser` で立てておく
  使い方(検証・並行運用)を巻き添えにしない。そもそも `--no-browser` では
  見張り自体を立てません
* **書き戻しの途中では落とさない。** 停止してよいかは
  `_busy_reason(store)`(`/api/shutdown` と同じ判定)に聞きます

`/api/alive` は**トークンを要求しません**。トークンが古くなった画面から
心拍が弾かれると、開いているのに「黙って死んだ」扱いになるためです。
書き込みロックの対象からも外しています。

#### 3.9.1.1 裏に回った画面・スリープ明けで終わらない

**ブラウザは裏のタブのタイマーを間引きます。** Chrome は 5 分隠れたタブの
タイマーを 1 分に 1 回まで落とし、Edge の「スリープ中のタブ」やメモリ
セーバーは止めたり捨てたりします。別の道具では、これで心拍が途切れて
**開いているのに終了**しました。この道具も、心拍が 20 秒途切れた画面を
「居ない」と見なし、90 秒で終わっていたので同じ形でした(凍結したタブで
再現: 裏に回る合図が無いと 90 秒で終了)。

| 起きること | 画面(`app.js`) | サーバ(`kanban/screen.py` / `idle_exit.py`) |
| --- | --- | --- |
| 裏に回る(タブ切替・最小化) | `visibilitychange` で `sendBeacon(?hidden=1)`。裏で間引かれて届く心拍にも `hidden=1` を付ける | 隠れた画面は心拍が無くても **24 時間**(`HIDDEN_MAX_SEC`)開いているものとして数える。自動終了しない |
| 凍結される | `freeze` で `sendBeacon(?hidden=1)` | 同上 |
| 表に戻る・凍結が解ける | `visibilitychange` / `resume` / `pageshow` で即座に心拍、`app-resumed` を投げて盤と接続を取り直す | 見えている画面に戻す |
| PC のスリープから起きる | 見えているのに心拍が大きく遅れた(30 秒超)ら「止まっていた」と読み、即座に心拍 + `app-resumed`。`online` でも同じ | 見張りの時計が 15 秒以上飛んだら、**飛んだぶんを数えない**(心拍の時刻を後ろへずらす)。起きてから 120 秒(`RESUME_GRACE_SEC`)は終わらせない |
| ブラウザが裏のタブを捨てて読み込み直す | `document.wasDiscarded` なら前の名札を `replaces=` で送る | 前の名札(隠れた画面)を引き取り、持ち主の席も引き継ぐ |

* **スリープを数えない理由:** Windows の `time.monotonic()` はスリープ中も
  進みます。起きた直後に「何時間も心拍が無い」と読み、画面が繋ぎ直すより
  先に終わっていました
* **持ち主の席:** 持ち主が裏に回ったまま 20 秒返事が無ければ、見えている
  別の画面が名乗ったときに席を渡します(以前も、返事の無い画面は 20 秒で
  一覧から落ちて席が移っていたのと同じ動き)。隠れた画面は一覧に残るので
  アプリは終わらず、戻ってきたら「別のタブで開いています」から取り戻せます
* **閉じたことはこれまでどおり効く:** 閉じるときは「隠れます」と「閉じます」が
  続けて飛び、届く順は決まっていません。閉じた名札を 2 分覚えておき、あとから
  届いた「隠れます」で 24 時間残らないようにしています
* 24 時間の上限は、隠れたままブラウザごと落ちた(閉じた合図が来ない)画面が
  アプリを残し続けないためです。残っていても、次に起動すれば動いている
  アプリへ繋がるので「閉じたのに開けない」にはなりません

### 3.9.2 「すでに起動しています」で終わらせない

それでも本当に多重起動になることはあります(別の利用者が同じ端末で開いた、
など)。そのとき **断るだけで終わらない**ようにしました。窓が無いアプリで
「起動中です」とだけ言われても、利用者には**どこを見ればよいのか分からない**
からです。断り書きに、居場所と止め方を並べます。

```
すでに起動しています(同じアプリが起動中)。ブラウザを開きました。

  場所 : http://127.0.0.1:8741/
  PID  : 8372(タスクマネージャーの「バックグラウンド プロセス」にいます)
  起動 : 2026/08/31 09:31:02

開いた画面が使えない・見覚えが無いときは、いったん止めてください:
  stop.bat            … 止める
  stop.bat --force    … 未反映の操作があっても止める
```

### 3.10 画面を tkinter から Web(Flask)へ

**業務ロジックは 1 行も変えていません。** 変えたのは描画層だけです。

| 層 | 扱い |
| --- | --- |
| `kanban/domain/`(状態遷移・帳票の中身) | そのまま |
| `kanban/db/`(SQLite・Access 同期) | そのまま |
| `kanban/accdb/`(Access 読み書き) | そのまま |
| `kanban/ui/`(tkinter、10 ファイル) | **廃止** |
| `app/`(Flask + HTML/CSS/JS) | 新規 |
| `kanban/presenters/` | 新規(ドメイン → ビューモデル) |

社内「汎用Webアプリ作成 基盤仕様書」に沿った構成で、起動・監視・停止の
下回りは同じ基盤を使う他の社内ツールと揃えてあります。

```
Start.vbs ─▶ start_app.py ─▶ launch_guard.py ─▶ server.py (waitress)
  (通常)       (環境確認)      (多重起動判定)      │
                                                   ├─ boot_server(待機画面) ─▶ ブラウザ
                                                   └─ 差し替え ─▶ app/ (Flask)
start.bat ─▶ 同じ経路(コンソール表示・診断ログ詳細)
stop.bat  ─▶ process_manager.py ─▶ POST /api/shutdown → 応答が無ければPIDで停止
```

守っている約束(破ると事故になるので、違反はバグとして扱います):

1. **業務判断はすべて Python。** JS が持つのは「ビューモデル → DOM」の
   変換だけ。二重に持つと、テストの無い側に分裂する
2. **API は更新後の盤面ぜんぶを返す**(差分ではない)。この規模(数 KB)で
   差分を使う利点は無く、画面側の不整合バグの温床になる
3. **断りの種類は HTTP ステータスで分ける。** `400` 入力の形が違う /
   `403` そのモードではできない / `409` 他端末が先に変えていた /
   `422` 業務として断る / `503` DB が混んでいる
4. **色の出どころは `tokens.css` ただ 1 つ。** サーバは状態の名前
   (`ordered` / `shipped` / `held` / `neutral`)だけを渡す
5. **同じ事実を 2 か所に持たない**

**SPA にしていません。** ルータ・状態管理・ビルド工程という 3 つの複雑さに
見合うものが、画面 2 つのこの規模では得られないためです。npm も webpack も
使わないので、社内端末では `pip install -r requirements.txt` だけで動きます。
依存は Flask と waitress の 2 つだけです。

Web 化で新しく増えた守り(いずれも tkinter 版には無かったもの):

* **起動トークン。** 起動ごとの合言葉を持ち、`/api/*` と `/report/*` は
  これが無いと通らない。同じ PC 上の別プロセスや、利用者が偶然開いた外部の
  Web ページから叩かれないようにする
* **Host 検証と同一オリジン確認。** DNS リバインディングと別オリジンからの
  操作を弾く。CORS ヘッダは一切返さない(返さないことが対策)
* **多重起動の防止。** 同じモードを 2 つ起動すると、Access への書き戻しが
  同じ端末から 2 重に走る。ロックファイル + `/api/health` の `app_id` 照合で
  判定し、既に動いていればブラウザだけ開く
* **接続断の帯。** バックエンドが落ちても画面は古い盤面を出し続けてしまう。
  看板は「いまの状態」を見る画面なのでそれは事故そのもの。定期的に
  `/api/health` を叩き、切れたら画面上に明示する
* **処理中は止めない。** Access へ未反映の操作が残っているうちは、画面の
  「終了」も `stop.bat` も止めずに理由を返す(`--force` で押し切れる)

### 3.11 正データを Access(.accdb)から共有 SQLite へ

**2 層構造は変えていません。** 変えたのは共有側のファイル形式だけです。

```
    共有 SQLite(正データ)  ← ここが .accdb から .sqlite3 になった
            ↕
    手元の SQLite(端末ごとの写し + 送信待ち)
```

2 層をやめない理由は変わりません ── 操作のたびに共有フォルダへ往復すると
遅く、共有が落ちている間は何もできなくなります。2 層なら手元で操作を続け、
繋がったときにまとめて送れます。

#### なくなったもの

| ファイル | 行数 | 役目 |
| --- | --- | --- |
| `accdb/ado_bridge.py` | 618 | **cscript + VBScript を起動**して書き戻す |
| `dbkit/access_odbc.py` | 658 | ODBC を ctypes で叩く代替経路 |
| `accdb/sql.py` | 161 | Access 方言のリテラル生成(`#yyyy-mm-dd#`・引用符の二重化) |
| `accdb/odbc_bridge.py` | 131 | 上記のラッパ |
| `accdb/gateway.py` | 186 | 3 経路(ado/odbc/file)の切り替え |
| `dbkit/outbox_sync.py` | 452 | Access 前提の追記型書き戻し(kanban は未使用) |

設定の `accdb_access_mode`(auto/ado/odbc/file)も不要になりました。

`accdb/reader.py` と `accdb/types.py` は**変換のために残して**あります
(`tools/accdb_to_sqlite.py`)。運用では使いません。

#### 得られたもの

* **ACE OLEDB への依存が消えた。** 以前は書き戻しに ACE のインストールが
  必要で、入っていない端末では読み取りしかできませんでした
* **書き戻しを Windows 以外でも検証できる。** 以前は ADO ブリッジが Windows
  専用だったため、書き戻しの経路だけテストできていませんでした
  (`tests/test_shared_db.py` はこの移行で初めて書けたテストです)
* **SQL のエスケープ漏れが構造的に起きない。** 値を文字列へ埋め込むのを
  やめ、プレースホルダで渡すようにしました(`shared.build_update`)

#### 共有フォルダの上で気をつけていること

Access(ACE/Jet)は `.laccdb` を使った「共有フォルダで複数端末が使う」前提の
設計でした。SQLite はそうではないので、置き方で補います。

* **WAL を使わない。** WAL は共有メモリ(`-shm`)を使いますが、SMB には
  それがありません。共有フォルダに置いた WAL のファイルは**読むだけでも
  開けない**ことがあります(参照リポジトリ python-web-tools が現場で踏み、
  「手元へ写してから読む」逃げ道を作っています)
* **読むときは共有ファイルを直接開かない。** 手元へ写して、その写しを開く
  (下記)
* **ロック待ちを長めに取る**(`busy_timeout` 既定 10 秒)。SQLite の書き込みは
  DB 全体の排他なので、他端末と当たったら少し待てば通ります
* **1 文ずつ自動コミットし、長いトランザクションで共有を掴み続けない**

書き込みは 60 秒間隔のまとめ送り(と操作直後)で、1 回に送る量も小さいため、
端末が増えても待ちは実用上問題にならない見込みです。

なお `dirty_columns` による**列単位の競合保護**(3.3.1)は、UPDATE 文を
組み立てる側の仕組みなので、送り先が Access でも SQLite でも同じように
効きます ── 現場が発注列を、倉庫が発送列を同時に触っても互いを消しません。

#### 移行のしかた

```bash
python tools/accdb_to_sqlite.py "看板マスタ.accdb" "看板マスタ.sqlite3"
```

変換したファイルを共有フォルダへ置き、設定画面の「接続先」をそのパスへ
変えて、全端末でアプリを開き直します。元の `.accdb` は触りません ──
切り戻したくなったら接続先を戻すだけで済みます。

`start_app.py --check` は、共有 SQLite がまだ無く `.accdb` だけがある状態を
見つけると、**実行すべき変換コマンドをそのまま表示します**。

### 3.12 読むときは共有ファイルを直接開かない(手元へ写す)

**現場で起きたこと**: 他の端末が開いている最中の共有 SQLite を読みに行くと、
共有フォルダに `pending_20260811_164850.sqlite3` のようなファイルが増えて
いきました。読むだけのつもりが共有フォルダを汚し、しかも**誰が消してよいのか
分からない**ファイルが残ります。

SQLite は書き込み中・ロック中・処理未完了のときに一時ファイル
(`-journal` / `-wal` / `-shm`、および復旧途中の中間ファイル)を作ることが
あります。読み取り専用で開いても、他の書き手が残した状態しだいでは触りに
行きます。

**対策: 読む前に手元へ写し、写しを開く**(`SharedDb.local_copy`)。

```
共有フォルダ                     手元(ローカル領域の cache)
看板マスタ.sqlite3  ──コピー──▶  shared_<パスのハッシュ>.sqlite3
   ▲                                    │
   └────── 書き戻しはこちらへ直接 ◀──────┘ 読むのはこちら
```

* 共有フォルダに対しては**バイト列をコピーするだけ**。SQLite としては一切
  開かないので、一時ファイルは手元にしか作られません
* **書き戻しは写しへ向けません。** 写しへ書いても誰にも届かないので、書くとき
  だけ共有ファイルを直接開きます。写しは `query_only` で開き、書けないように
  してあります(書けてしまうと「直したのに反映されない」という一番たちの悪い
  壊れ方になります)
* **同じものを何度も写しません。** 取り込みはテーブルごとに開き直すので、
  ラインの数だけ写すと共有への往復だけで待たされます。大きさと更新時刻が
  変わっていなければ写しを使い回します
* `-wal` / `-shm` / `-journal` も一緒に写します。本体だけ写すと、**直前に
  書かれた分が抜けた**中身を読むことになります
* 写した直後に開いて確かめ、読めなければもう一度だけ写します(写している
  最中に他端末が書くと、途中の状態を写しうるため)

参照リポジトリ python-web-tools は「共有の上で開けなかったときの最後の手」
として写していましたが、こちらは**常に写します** ── 開けるかどうかに関わらず、
共有フォルダに一時ファイルを作らせないことが目的だからです。

### 3.13 設定画面の「参照...」とマスタ管理

どちらも Web 化と Access 廃止で必要になったものです。

#### 参照...(サーバ側のフォルダ一覧)

ブラウザのファイル選択ダイアログは**クライアント側**のパスしか返しません。
アプリが読むのはサーバ(=この PC)から見たパスなので、選ばせても意味が
ありません。tkinter 版は同じプロセスに画面があったので
`filedialog.askopenfilename` がそのまま使えていました。

代わりに `GET /api/fs/list` がサーバ側のフォルダを一覧します
(`kanban/presenters/fs_browse.py`)。直接打つこともできます。

* **フォルダの名前**と、そこにある**共有 DB ファイルの名前**だけを返す。
  ファイルの中身は返さない(読み取り口をここに作らない)
* 件数に上限(300)を置く
* 変換前の `.accdb` も**あることは見せるが選ばせない** ── 移行の途中は
  「.accdb はあるが .sqlite3 がまだ」になり、そこで何も見えないと
  「フォルダを間違えた」のか「変換がまだ」なのかが分からないため

上のフォルダへ行けないようにするたぐいの制限は付けません(それでは置き場所を
探せません)。守りは 127.0.0.1 バインド + 起動トークン + Host 検証 +
同一オリジン確認が担います。

#### マスタ管理

Access をやめたことで「Access を開いて中身を目視する・手で直す」という経路が
無くなりました。資材やサイズを 1 つ足したいだけのときの受け皿です。

**とりわけ「足す」が要ります。** 看板を 1 枚増やすとは `看板_<ライン>` に
1 行足すことです。直すだけでは看板を増やせず、増やせないと結局 Access を
開くことになります ── その Access をやめたので、ここが無いと運用が回りません。

| | |
| --- | --- |
| 一覧 | `GET /api/master` — **中身は読まない**(共有への往復を増やさない) |
| 表を開く | `GET /api/master/table?table=&page=` — 100 行ずつ |
| 足す | `POST /api/master/insert` — **1 行**。管理者パスワードが要る |
| 直す | `POST /api/master/update` — **1 マスだけ**。管理者パスワードが要る |
| 消す | `POST /api/master/delete` — **1 行**。管理者パスワードが要る |

* **表ごと保存しません。** 画面が持っている古い行をまとめて書き戻すと、その間に
  他端末が変えた分を巻き込んで消します
* **キー列(`管理番号`)は直せません。** 書き換えると、どの行だったのかが
  辿れなくなります。番号を打ち間違えて足した行は**消して足し直し**ます
  ── だから「消す」が要ります
* **行は `rowid` で指します**(下記)
* 一覧に無いテーブルは開かせません(画面で絞るだけでなくサーバでも確かめる)
* 対象の行が消えていれば `409` を返し、画面は開き直します
* **書けたら、その場で手元へ取り込みます。** ここを飛ばすと、共有 DB は
  直っているのに盤が変わりません ── 看板を足したのに出てこなければ、
  足せていないのと区別が付きません。取り込みに失敗しても**書けたことは
  書けた**ので成功として返し、「取り込みは別途」と付け足します

##### 行は `rowid` で指す(`__行`)

書き換え・削除は **SQLite の `rowid`** で行を指します。画面には
`__行` という名前(業務の列と衝突しない名前)で渡り、そのまま返ってきます。

**業務のキーで指してはいけません。** `管理番号` は重複しうるので、それで
指すと **1 回の操作が 2 行に当たります** ── 参照リポ(python-web-tools)が
「直したつもりが別の行だった」として踏んだ穴で、同じ作りにしてあります。

`__行` は隠し列です。表の見出しにも入力欄にも出しません。画面から来た値が
本当にその表の行を指しているかは、**書く前に確かめます**(指していなければ
「画面を開き直してください」と断る ── 当てずっぽうで別の行を触るよりよい)。

##### 直せない表は、隠さず理由を出す

直せるのは **`看板_<ライン>` だけ**です。それ以外は一覧にも中身にも出しますが、
直す手立ては出さず、代わりに**なぜ直せないのか**を表の上に出します。

| 表 | 理由 |
| --- | --- |
| `Form状態管理` | 端末が開いているかどうかを、各端末が自動で書き込む表です。手で直しても、次に書き込まれた時点で元に戻ります |
| それ以外 | この道具が直す表ではありません。中身の確認だけできます |

**隠さないのが要点です。** 隠すと、探している人には画面が壊れて見えます
(「あるはずの表が無い」)。断りは画面だけでなく経路でも行います
(`view_only` ── 画面を通さず叩かれても書けない)。

##### スキーマが守ってくれない分をアプリで守る

Access から変換した `看板_*` には **主キーも NOT NULL も UNIQUE もありません**
(`tools/accdb_to_sqlite.py` は元の形をそのまま写すため)。つまり DB は
`管理番号` が重複した行を平気で受け付けます。ところが書き戻しは
`WHERE 管理番号 = ?` で行を決めるので、**重複した瞬間に 1 回の書き戻しで
2 行が同時に変わります。** そこで足すときに次を確かめます。

| 決まり | なぜ |
| --- | --- |
| キーは必須 | キーの無い行は書き戻しから永久に外れる(画面に出るのに誰も直せない) |
| キーは重複させない | 上記のとおり、書き戻しが 2 行を巻き込む |
| 看板なら `資材` も必須 | 空の看板は盤ではただの空ボタン。足した本人にも見分けが付かない |
| 数値列は数値、日時列は日時 | **形が違えば断る。黙って直さない** ── 打ち間違いを別の日時にすり替えない |
| 空欄は空文字のまま(数値列だけ NULL) | Access から変換したファイルが空文字で揃っている。ここだけ NULL を混ぜると、SQLite を直接覗いた人に「この行だけ何か違う」と読ませる |

重複の確認は**2 重**です。先に読んで確かめ、さらに `INSERT ... WHERE NOT
EXISTS` で 1 文の中でも確かめます ── 読んだあと・書く前に他端末が同じ番号を
入れると、前者だけでは擦り抜けるためです(`affected == 0` で分かります)。

画面には、次のキー(`管理番号` の最大 + 1)と看板の初期値(`不 = 〇`、
`常設品 = 〇`)を**入れて見せます**。サーバが黙って足すことはしません ──
枝番のような連番でない運用を塞がないためです(キーが数字で揃っていない表では
当てずに空を返します)。

#### 守るもの・開けておくもの

**この画面で守らないのは「マスタを読むこと」だけです。** それ以外はすべて
管理者パスワードを要求します。

| 経路 | パスワード |
| --- | --- |
| `GET /settings` / `GET /api/settings` | 不要(この画面自体の描画) |
| `GET /api/master` | **不要**(マスタの一覧) |
| `GET /api/master/table` | **不要**(マスタの中身を読む) |
| `POST /api/master/insert` | 必要(1 行足す = 看板を増やす) |
| `POST /api/master/update` | 必要(1 マス直す) |
| `POST /api/master/delete` | 必要(1 行消す) |
| `POST /api/mode` | 必要 |
| `POST /api/line` | 必要 |
| `POST /api/shared-db-path` | 必要 |
| `POST /api/reimport` | 必要 |
| `POST /api/fs/list` | 必要(この PC のフォルダを返す) |

読むことだけを開けておくのは、**調べる手段を塞がない**ためです。「なぜデータが
古いのか」「マスタに何が入っているのか」を確かめるのに、いちいち管理者を呼ばずに
済みます。一方、**状態を変えるものは 1 つ残らず守ります** ── この道具は共有 DB
への書き込みが壊れると業務が成立しないので、誤操作の入口を作りません。

担当ラインの変更(`/api/line`)は tkinter 版では通常操作でしたが、Web 版では
保護しています。担当ラインを変えると**取り込むラインと書き戻すラインが入れ替わる**
ため、現場の端末が別ラインを指したまま操作されると、そのラインの発注が本来の
担当者の知らないところで動きます。

フォルダ参照は `GET` ではなく `POST` です ── パスワードを本文で受けるため
(URL に載せると履歴とログに残ります)。毎回訊くとフォルダを 1 つ辿るたびに
入力させることになるので、画面は**「参照...」を開いているあいだだけ**手元に
持って毎回送り、閉じたら捨てます。**サーバ側に解錠状態は持ちません** ──
開きっぱなしのタブが解錠のまま残るのを避けるためです。

#### パスが無ければ何もできない

**共有 DB の場所が設定されていない・届かない端末では、開くことも直すことも
できません。** 当たり前に見えますが、ここを黙って空表にすると「マスタが
消えた」に見えます。理由を返し、次に何をすればよいかまで言います
(`master.availability`)。

| 状態 | `blocked` | 画面に出ること |
| --- | --- | --- |
| 設定が空 | `no_path` | 「接続先」で設定してください |
| 設定が空 + 既定の場所にも無い | `no_path` | 既定の場所も見たがそこにも無い、と場所つきで言う |
| 設定はあるが届かない | `missing` | 共有フォルダに届いているか確認してください |
| 開けたが読めない | `unreadable` | 読めなかった理由をそのまま出す |

「設定していない」のか「設定したが届かない」のかを言い分けるのは、**直し方が
違う**ためです。同じ関門は開く側だけでなく**直す側にも**置いてあります
(表を出してから「保存できません」と言うより、開く前に言うほうが早い)。

### 3.14 いま誰が開いているか(`kanban/presence.py`)

倉庫が確認している最中に現場の画面が開いていれば、**これから看板が出るかも
しれない**と身構えられます。逆に現場からは、倉庫が見ているかどうかが分かり
ます。VBA 版も `Form状態管理` に開いた印を付けていましたが、

* 印を付けるのは**開いた瞬間だけ**
* 見るには**自分でダブルクリックして更新**する

という作りだったため、ふたつ困ることがありました。

1. **異常終了すると開いたままになる。** 印を消す経路を通らずに落ちると、
   誰も開いていないのに「開いています」と出続けます。**一度でも嘘をつくと、
   その表示は二度と信じてもらえません**
2. **押さないと分からない。** 警戒のための表示なのに、警戒しようと思って
   押さないと見えません

#### 印を付け直し続ける(心拍)

2 分ごと(`presence.HEARTBEAT_SEC`)に `状態` / `更新日時` / `ホスト名` を
書き直します。**印が立っていても、しばらく打たれていなければ「もう居ない」と
判ります**(`presence.STALE_SEC` = 600 秒)。画面では、生きているものは色付き、
打たれていないものは**破線に `?` 付き**で別に見せます ── 消してしまうと
「なぜ残っているのか」が分からないので、残したうえで言い分けます。

10 分と長めなのは、心拍の間隔だけでは足りないからです。相手が打ってから
こちらが気付くまでに**取り込み間隔ぶんの遅れ**が乗るので、健全でも 150 秒
前後は古く見えます。生きているものを死んだと言うほうが害が大きいので、
余裕を取っています。**正常に閉じたときは即座に消える**(閉じるときに `閉` を
書く)ので、ここが効くのは異常終了のときだけです。

##### なぜ 2 分なのか ── 心拍は共有フォルダに高くつく

最初は 30 秒にしていましたが、**共有フォルダへの往復を大きく増やして
いました**。書けば更新時刻が変わり、変われば全端末の「中身が同じなら
写さない」(3.12)が外れます。つまり**心拍 1 回が、全端末にファイル 1 個ぶんの
コピーをやらせます。**

実測(取り込み 10 秒間隔、誰も操作していない状態):

| | 共有への書き込み | 60 秒あたりのコピー |
| --- | --- | --- |
| 心拍なし(倉庫参照) | 0 回 | **0 回**(取り込みは 6 回走っている) |
| 30 秒心拍 | 2 回 | **2 回** |
| 2 分心拍 | 0〜1 回 | **0〜1 回** |

効いてくるのは**誰も操作していない時間帯**です ── 夜間・休憩中・閉じ忘れ。
以前ならコピーがゼロだったところが、端末の数だけ動き続けます。

「誰が開いているか」は**数分の粒度で足りる情報**です(秒単位で知っても
することは変わりません)。一方、共有フォルダの静けさは全端末に効きます。
そこで業務の速さではなく共有フォルダ側で間隔を決めました。

なお、これでも往復をゼロにはできません(書けば必ず更新時刻が変わる)。
**ファイルが大きくて往復が無視できない場合は、心拍だけ別ファイルに
分けるのが次の手**です ── そうすれば看板データのコピーは「誰かが実際に
操作したときだけ」に戻ります。判断できるよう、設定画面の「取り込みの状態」に
**共有DBの大きさ**と**起動してから写した回数**を出しています。

#### 時計のずれに寄りかからない

`更新日時` は**相手の端末の時計**で書かれます。工場の端末どうしで時刻が
揃っている保証は無いので、こちらの時刻と引き算しません。代わりに
「`更新日時` の値が**変わった**のを見たこちらの時刻」(`line_status.seen_at`)
を手元に持ち、それだけで古さを判じます ── 相手が打ち続けるかぎり値は変わり、
`seen_at` も進みます。相手の時計が 10 年ずれていても正しく動きます。

#### 書くのは直接、読むのは取り込みに相乗り

心拍は**共有 DB へ直接書きます**。未反映の待ち行列(`dirty`)に入れると、
帯の「未反映 N 件」に混ざって本当の書き残しが埋もれ、失敗すれば延々と
再試行されます ── 心拍は**届かなければ諦めてよい**種類の書き込みです。
共有フォルダが落ちている程度のことで看板の操作が道連れになってはいけないので、
失敗はログに 1 度だけ書いて、あとは黙って次を打ちます。

読むほうは、取り込み(`sync.import_all`)が `Form状態管理` を**すでに読んで
いる**ので、共有フォルダへの往復は増えません。帯の `/api/status` は
手元の SQLite しか見ません(数秒おきに叩かれる経路に共有を混ぜると、
端末が増えるほど共有が重くなります)。そのぶん新しさの上限は
`import_interval_sec` です。

#### 名乗るモード・名乗らないモード

| モード | 名乗るか | `ライン名` |
| --- | --- | --- |
| 現場 | 名乗る | 担当ライン |
| 倉庫 | 名乗る | `倉庫` |
| 倉庫参照 | **名乗らない** | — |

倉庫参照は読むだけの端末なので、誰かを身構えさせる理由がありません。
名乗らせると「倉庫が開いている」が常時点灯し、**本物の倉庫と見分けが
付かなくなります**。名乗らない以上、表示から自分を外すこともしません
(`registered_line` が空を返す)── 名乗ってもいないのに、設定に書いてある
ラインだけ見えなくなるのはおかしいためです。

#### `Form状態管理` の列はそのまま

列を増やしていません(`管理番号` / `ライン名` / `状態` / `更新日時` /
`ホスト名`)。`更新日時` や `ホスト名` が無い共有 DB でも `状態` だけは
書きます ── 読む側は列が無くても既定値で済ませているので、書く側だけ
落ちるのは釣り合いません。どの列があるかは取り込みのときに覚えておき
(`meta.state_table_columns`)、書くたびに共有 DB を読み直しません。

1 ラインに 1 行(VBA と同じ)です。同じラインに端末が 2 台あれば、
後から打ったほうの `ホスト名` が残ります。

### 3.15 送りようの無い変更を、溜めたまま黙らない

未反映の行(`dirty = 1`)は「まだ共有DBへ届いていない操作」です。これには
**送れば届くもの**と、**何度送っても届かないもの**の 2 種類があります。
この区別をしていなかったため、次の 2 つが起きました。

#### 共有DBから消された行(要確認)がアプリを終わらせなくした

`_busy_reason` は「未反映があるなら止めてはいけない」と答えます。ところが
数えていたのが `pending_count()`(`dirty = 1` の全部)だったため、5 回失敗
して**諦めた行**まで数え続けました。諦めた行は二度と送られないので、
この数は永久に減りません。

```
1 回目: 失敗=1 未反映=1 要確認=0  止まれるか= いいえ
...
5 回目: 失敗=1 未反映=1 要確認=1  止まれるか= いいえ
6 回目: 失敗=0 未反映=1 要確認=1  止まれるか= いいえ   ← もう送られないのに
```

結果、**タブを閉じてもアプリが終わらず**、「終了」ボタンは毎回 409 で断られ、
`stop.bat` も `--force` 無しでは効かなくなります ── 3.9.1 で直したはずの
「閉じたのに開けない」が、別の入口から戻ってきていました。

`retryable_pending_count()`(`sync_attempts < 5`)を足し、止めてよいかの
判断はこちらで行います。画面の「未反映」は `pending_count()` のままです
── 届いていないことに変わりはないので、0 件と言うのは嘘になります。

#### 共有DBに無い列への変更が、成功にも失敗にもならず残った

`保留` と `注文中日時` は任意列です(`config.REQUIRED_COLUMNS` に入って
いません)。持たない `看板_*` テーブルで「注文中」を解除すると、
`dirty_columns` は `hold,hold_at` だけになります。書き戻しは送り先の列を
1 つも見つけられず、**`continue` で黙って飛ばしていました**。

飛ばされた行は成功でも失敗でもないので `dirty` が落ちず、`sync_attempts` も
増えません。つまり「要確認」にもならないまま、**永久に未反映として残ります**。
上の `_busy_reason` と合わさると、その端末は二度と終われません。

直したのは 3 か所です。

| どこ | 何を |
| --- | --- |
| `sync._export_items` | 送り先が 1 つも無ければ、理由を付けて**失敗として記録する**(5 回で「要確認」へ) |
| `service.storable_columns` | そのラインで共有DBへ書ける状態列を返す |
| `presenters.board.policy_for` | 書けない列のボタンは**出さない** |

いちばん効くのは 3 つめです。押せて・色が変わって・手元にも残るのに
**共有DBには一生届かない**ボタンは、倉庫に「注文中にした」と思わせたまま
現場には何も見せません。出さないほうが正直です。理由はログに残ります。

```
共有DBの 看板_LVC に 保留, 注文中日時 列がありません。この変更は送れません
```

あわせて「サイズ(発注)」も、発送ボタンと同じく**押す前にポリシーを引き
直す**ようにしました。モードだけ見ていたので、URL を直接叩けば
`発送無効` でないラインでも発注できてしまう状態でした。

### 3.16 「注文中」を、発注とつじつまの合う状態にする

「注文中」は *現場から来た発注を、倉庫が仕入れ先へ注文した* という意味です。
VBA はこの意味を状態の遷移では守っておらず、次の 2 つが起きていました。

#### 発注(赤)が無い行にも注文中(黄)を付けられた

`cls_HoldButton` に発注の確認がありませんでした。発注の無い行に注文中を
付けても指すものがありません。発送ボタンは同じ理由で
「注文がありません。先にサイズボタンで発注してください。」と断るので、
そちらに揃えました。

* **付ける**方向だけ断ります(`OrderMissingError` → 422)
* **外す**方向はどんな状態でも通します ── 発注が先に取り消されても、倉庫は
  注文中を下ろせなければなりません
* 盤面でも、押せない行の注文中は**押せない見た目**にして理由を出します
  (「発注がありません。現場が発注してから注文中にできます」)。押しても
  断られるだけのボタンを出すより先に止めます

#### 一括発送だけ、注文中(黄)が残った

発送ボタン 1 つを押すと注文中は一緒に解除されます(VBA の `needClearHold`)。
ところが「表示中のラインを全て発送済みにする」が呼ぶ `ExecuteSQLBatchShip`
は保留列を触らないので、**緑が付いているのに黄も点いたまま**の行ができました。

倉庫から見れば「発送したのにまだ注文中」で、どちらが本当か読めません。
しかも発送明細(`build_warehouse_document`)は注文中の行を載せないので、
**発送したのに明細から黙って抜け落ちます**。

1 行ずつ押しても一括で押しても同じ結果になるよう、一括発送も注文中を
解除するようにしました。試験では、まとめて出す変更が発送ボタン 1 つぶんと
**完全に一致すること**を確かめています(ずれたら意味がないので)。

### 3.17 担当ラインを変えたら、名乗る行も移す

`Form状態管理` に「開いています」と書くのは `kanban/presence.py` の心拍
です。ところが設定画面で担当ラインを変えても、**心拍は前のラインを名乗り
続けていました**(接続先を差し替える `set_gateway` はあったのに、ラインを
移す口が無かった)。

ラインを切り替えながら試すと必ず踏み、こうなります。

* 前のラインが共有DBで `開` のまま残り、他端末には**居もしない端末が
  開いて見える**。やがて `STALE_SEC`(10 分)を過ぎて `L-1?` のように
  破線の `?` になる
* 新しいラインは一度も名乗らないので、**本当に開いているほうが見えない**
* 自分の画面の「開いている端末」から自分を外す判定は**いまの**ラインで
  引くのに、印は**前の**ラインに立っている ── つまり
  **自分自身が他人として並びます**

`presence.set_line` を足して、前のラインへ `閉` を書いてから新しいほうを
名乗るようにしました。なお、**担当ラインを変えてもアプリは閉じません**
(画面を読み直すだけです)。

### 3.18 「未反映 N 件」の中身を見られるようにする

数だけ出ていて、**何が届いていないのか確かめる手段がどこにもありません
でした**。設定 →「取り込みの状態」に一覧を出します。

| 列 | 中身 |
| --- | --- |
| ライン / 管理番号 / 資材 / サイズ | どの看板か |
| 操作 | 発注 / 発送 / 注文中(`dirty_columns` を利用者の言葉にまとめたもの) |
| 押した時刻 | いつから残っているか |
| 状態 | 送信待ち / 再送待ち(N 回失敗)/ **要確認(送れません)** |

列名(`want,unwant,ordered_at`)のまま出しても伝わらないので、3 つの操作に
まとめています。諦めた行は赤で「要確認(送れません)」と出し、待っても
減らないことを言います(3.15)。

| VBA | 理由 |

## 5. Access ファイルの読み取りについて

`kanban/accdb/reader.py` は ACE / Jet4 の物理フォーマットを直接解析します。
実装にあたって特に必要だった点:

* **Unicode 圧縮テキスト**: `0xFF 0xFE` で始まる値は、`0x00` を境に「1 バイト文字」と
  「UTF-16LE」が交互に切り替わります。`2200 × 50M : 3本` のような値はこの形式です。
* **移動済み行(オーバーフロー行)**: 更新でページに収まらなくなった行は別ページへ移り、
  元の位置には `[行番号 1byte][ページ番号 3byte]` のポインタだけが残ります。
  移動先は削除済みフラグが立つため、両方を正しく扱わないと件数が合いません。
* **使用状況マップ**: 解放後に再利用されていないページには古い所有者情報が残るため、
  ページを総なめするのではなく使用状況マップを辿る必要があります。

実ファイル(48 テーブル)で、テーブル定義が持つ行数と読み取り行数が一致することを
確認済みです(`看板_*` は全テーブル一致)。
