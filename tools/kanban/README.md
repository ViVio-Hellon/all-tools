# 看板発注システム(Python 版)

> **統合ツールの一部です。** このツールは統合ツール([`../../README.md`](../../README.md))の
> `tools/` の下に入っています。**デスクトップ版は 統合ツール.exe の窓の「看板」のタブ**です。
> このツールだけの exe(`資材発注看板システム.exe(KanbanSystem.exe)`)と外枠のソース(`src-tauri/`)は、統合ツールの外枠に置き換わりました(以下の説明のうち、単体の exe・`src-tauri/`・GitHub Actions の話は、統合ツールの [`docs/デスクトップ版.md`](../../docs/デスクトップ版.md) を見てください)。
> このフォルダの `Start.vbs`(ブラウザ版)は単体でも動きますが、統合ツールの窓で看板が
> 開いているときは起動しません(**後から開いたほうが止まります**)。

Excel マクロ(VBA)+ Access で作られていた資材の看板(かんばん)管理ツールを、
**Python + ブラウザ**で置き換えたものです。Excel も Access も起動しません。

画面は Flask + HTML/CSS/JS、業務ロジックは Python、データは SQLite です。
社内「汎用Webアプリ作成 基盤仕様書」に沿った構成で、起動・監視・停止の
下回りは同じ基盤を使う他の社内ツールと揃えてあります。追加で要るのは
`Flask` と `waitress` の 2 つだけで、npm も webpack も使いません。

| | 移行前 | 移行後 |
| --- | --- | --- |
| 画面 | Excel UserForm(動的生成) | ブラウザ(Flask + HTML/CSS/JS) |
| データ | Access(.accdb)を直接読み書き | 共有 SQLite(正データ)+ 端末ごとのローカル SQLite(作業用の写し) |
| 排他制御 | ADO のロックエラーをリトライ | SQLite のトランザクション + 行バージョン + リトライ |
| 接続 | ACE OLEDB(ADO / ODBC)が必要 | **不要**(標準ライブラリの sqlite3 だけ) |
| 印刷 | Excel シートを生成して `PrintOut` | 印刷用ページを開くだけ(`/report/<種類>`) |
| ライン設定 | Windows レジストリ | 設定ファイル(JSON) |

## データの流れ

**共有フォルダ上の SQLite(`看板マスタ.sqlite3`)が正式なデータで、各端末の
ローカル SQLite は「その端末専用の作業用の写し + 送信待ちの一時置き場」です。**

VBA 版には「ローカルの写し」という概念が無く、毎回 Access に直接読み書き
していました。Python 版が写しを挟むのは「操作のたびに共有フォルダへ
問い合わせると遅い」ためで、正式なデータの置き場所が 1 箇所である点は
VBA 版と同じです。

```
 ライン1のPC             共有 SQLite(.sqlite3)             ライン2のPC
┌───────────────┐        ┌──────────────┐        ┌───────────────┐
│ SQLite(ローカル)  │        │              │        │ SQLite(ローカル)  │
│ ・マスタの写し      │◀──読込── │   共有・正データ   │ ──読込──▶│ ・マスタの写し      │
│ ・入力した発注/発送 │──書込──▶│              │◀──書込── │ ・入力した発注/発送 │
└───────────────┘        └──────────────┘        └───────────────┘
```

* **起動時**: 共有DBの `看板_<ライン>` と `Form状態管理` をローカル SQLite へ取り込む
* **操作時**: ボタンを押すとまずローカル SQLite に保存され、即座に画面へ反映される
* **書き戻し**: その直後(数秒〜既定 60 秒以内)に、変更のあった**列だけ**を
  自動で共有DBへ UPDATE する(終了時にも必ず 1 回実行)
* **再取り込み**: 既定 30 秒ごとに共有DBを読み直し、他ライン・倉庫が
  書き戻した内容をこのローカル SQLite へ反映する(「↻ いま取り込む」でも即時実行)

書き戻しが**行ではなく列単位**なのは、現場が発注列を、倉庫が発送列を、
同じ行に同時に書いても互いを上書きしないためです(`dirty_columns`)。

`sqlite_path` は既定でこの端末のローカルディスクを指すため、**手元の SQLite を
複数端末で共有するわけではありません**。書き込みが必ず 1 か所(共有DB)へ
集約される点は VBA 版と同じです。

**読むときは共有ファイルを直接開かず、いったん手元へ写してから読みます。**
共有フォルダ上の SQLite を別端末が見ている最中に開くと `pending_*.sqlite3`
のような中間ファイルができてしまうためです(詳しくは
[docs/移行仕様.md](docs/移行仕様.md) の 3.12)。

正データは当初 Access(.accdb)でしたが、**共有 SQLite へ移しました**
(2 層構造はそのまま。詳しくは同 3.11)。これにより ACE OLEDB への依存と、
`cscript.exe` で VBScript を起動する書き戻し経路がなくなりました。
`.accdb` は**初回の変換で読むだけ**になり、運用中は一切触りません。

## 動作要件

* Python 3.9 以降
* `pip install -r requirements.txt`(Flask と waitress の 2 つだけ。デスクトップ版は Flask だけでよい)
* デスクトップ版は WebView2 ランタイム(Windows 10/11 に標準で入っています)

**外部の DB ドライバは要りません。** 共有側も手元側も標準ライブラリの
`sqlite3` で読み書きします。

> **導入前に必ず**: 正データが共有フォルダ上の SQLite になったため、その
> 共有フォルダでファイルロックが正しく効くことを先に確認してください。
> 手順は [docs/運用手順.md](docs/運用手順.md) の 1.2.2 にあります。

Access からの移行は `tools/accdb_to_sqlite.py` で 1 回変換するだけです。

## 使い方

最初に一度だけ、依存パッケージを入れます。

```bash
pip install -r requirements.txt
```

### 画面を開く

**`資材発注看板システム.exe`(デスクトップ版)をダブルクリックするだけです。**
専用の窓で画面が出ます。**ポートを使いません**(窓の外枠が Rust/Tauri、
業務の処理は今までどおり Python)。帳票は別の窓、CSV は「名前を付けて保存」、
モードの切り替えは開き直さずにその場で効きます。作りと確かめたことは
[docs/デスクトップ版.md](docs/デスクトップ版.md) にあります。

**`Start.vbs`(ブラウザ版)もそのまま使えます**(予備)。ブラウザが開いて画面が
出ます。デスクトップ版とブラウザ版は同時には動きません(あとから開いたほうが
案内するか、ブラウザ版に終わってもらってから開きます)。

どのモード(現場/倉庫/倉庫参照)で開くかは、この端末に保存された設定と
アクセス権限で決まります。

起動しないときは `start.bat` を使ってください。コンソールを開いたまま
経過とエラーを表示します。

```bat
start.bat                     :: 診断起動(経過を表示)
start.bat --mode warehouse    :: モードを指定して開く
stop.bat                      :: バックエンドを止める
```

```bash
python start_app.py --check   # 実行環境の確認だけ(起動しない)
```

### 画面を使わない実行(定時バッチ・調査)

```bash
python main.py --import-only        # 取り込みだけ実行
python main.py --export-only        # 書き戻しだけ実行
python main.py --show-config        # 有効な設定を表示
```

VBA 版のマクロとの対応:

| VBA | Python |
| --- | --- |
| `総資材反映` | `Start.vbs`(この端末のモードで開く。初回は現場モード) |
| `総資材反映_倉庫モード` | 設定画面でモードを「倉庫」にする / `start.bat --mode warehouse` |
| `総資材反映_倉庫参照モード` | 設定画面でモードを「倉庫参照」にする / `start.bat --mode view` |

## 設定

この端末の設定(接続先・取り込み/書き戻し間隔・自動印刷・管理者パスワード・担当ライン)は
`%APPDATA%\KanbanSystem\config.json`(その他: `~/.config/kanban_system/config.json`)に
入ります。ふだんは設定画面から直すだけです。**アプリのフォルダの外にあるので、
新しい版に入れ替えても消えません。**

**配布設定**(python-web-tools と同じつくり)で、1 台で決めた設定を配れます。

1. 1 台で設定し、設定画面の「配布設定」で**書き出す** → アプリの直下に `配布設定\` ができる
2. 「配布用フォルダを作る」(または `scripts\make_dist.bat`)で、配るものだけを
   アプリの隣の新しいフォルダへ写す
3. そのフォルダを配る。配った先は**起動したときに `配布設定\` を読み込む**
   (その端末にすでにある設定は上書きしない。揃えたいときは「読み込み直す」)

担当ラインは既定で入れません(端末ごとに違う)。詳しくは
[docs/運用手順.md](docs/運用手順.md) の 1.5。

`--config` で 1 つのファイルを渡すと、そのファイルに全部を読み書きします
(検証用)。`KANBAN_CONFIG` でこの端末の設定ファイルの場所を変えられます。

設定ファイルの例(組み込みの既定と同じ値は書かれません):

```json
{
  "shared_db_path": "\\\\nlmfangyshrd\\各課共有\\...\\看板マスタ.sqlite3",
  "export_interval_sec": 60,
  "import_interval_sec": 30,
  "refresh_interval_sec": 5,
  "frames_per_row": 4,
  "auto_print": false,
  "admin_password_hash": "(設定画面で決めると入る)"
}
```

`sqlite_path` は基本的に指定不要です(既定でこの端末のローカルディスクを使います)。
どの画面(現場/倉庫/倉庫参照)で起動するかはこの設定ファイルではなくこの
端末のローカル SQLite に保存されます(下の「画面は現場・倉庫で完全に
分かれています」参照)。`mode` フィールドは CLI の `--mode` を一時的に
運ぶためだけのもので、通常は編集不要です。

主な項目:

| 項目 | 既定 | 説明 |
| --- | --- | --- |
| `shared_db_path` | 共有の `看板マスタ.sqlite3` | 正式なデータの置き場所(取り込み元 / 書き戻し先) |
| `sqlite_path` | ローカル `%LOCALAPPDATA%` 配下 | この端末専用の作業用の写し。**通常は変更不要** |
| `accdb_path` | 未設定 | **初回の変換のときだけ**使う変換元。`shared_db_path` が未設定のときに手がかりとして探す |
| `line` | 未設定 | 担当ライン。未設定なら起動時に選択画面 |
| `export_interval_sec` | 60 | 手元 → 共有DB への書き戻し間隔(秒)。0 で自動書き戻しなし |
| `import_interval_sec` | 30 | 共有DB → 手元 への再取り込み間隔(秒)。0 で自動再取り込みなし |
| `refresh_interval_sec` | 5 | ローカル SQLite の変化を画面へ反映する間隔(秒) |
| `admin_password_hash` | 未設定 | 管理者パスワードのハッシュ。未設定なら初回操作時にその場で設定を求める |
| `access_db_path` | 共有DBと同じフォルダの `梱包資材マスタ.sqlite3` | アクセス権限(誰がどのモードを使えるか)を読む梱包資材マスタ |
| `history_db_path` | 共有DBと同じフォルダの `看板履歴.sqlite3` | 看板履歴(集計のための記録)。**全端末で同じ場所** |
| `csv_dir` | ローカル領域の `export` | CSV の書き出し先(この端末だけ) |

**管理者パスワードが要るのは** 接続先などの変更と、マスタの編集(看板を増やす・減らす・直す、
アクセス権限の行を足す・直す・消す)です。**マスタを読むだけならパスワードは
要りません**(調べる手段を塞がないため)。**モードの切り替えはパスワードではなく
アクセス権限で決まります**(次節)。

## 画面は現場・倉庫で完全に分かれています

VBA 版の `MaterialForm` / `WarehouseForm` / `WarehouseViewForm` と同じく、
3 つの独立した画面です。**1 台の PC で動くのは 1 つだけ**で(モードごとに
別ポート・別ロック)、画面同士が混ざることはありません。別のモードが動いて
いる状態で起動すると、古いほうを終わらせてから立て直します。

| 画面 | 操作できるもの | ポート |
| --- | --- | --- |
| 現場モード | サイズ(発注)ボタン、届いた資材の一括確認、注文票の印刷 | 8741 |
| 倉庫モード | 発送ボタン・注文中ボタン(全ラインをタブで切替)、一括発送、発送明細の印刷 | 8751 |
| 倉庫参照モード | なし(表示のみ) | 8761 |

盤面そのものは 3 モードで同じ画面(`/board`)を使い、**違うのは操作できる
範囲だけ**です。何を押せるかはサーバが決め(`kanban/presenters/board.py` の
`BoardPolicy`)、押された側でも同じ判断を引き直して確かめます。

どのモードで起動するかは `config.json` ではなくこの端末のローカル SQLite に
記憶されます。初回は現場モードで起動し、その内容を保存するため、以後は
同じモードで直接起動します(現場の端末で誤って倉庫画面を開くことが
ありません)。後から変更したい場合は画面の「設定」→「この端末」→「モード」
から切り替えられます。**変更は次にアプリを開いたときから効きます** ── モードは
ポートとロックに結びついているので、走ったまま入れ替えられないためです。

**使えるモードはアクセス権限で決まります**(`kanban/access_control.py`)。梱包資材マスタの
「アクセス権限」の表(python-web-tools と同じ表・同じ読み方)を **Windows のログインID と PC名**
で引き、`mode:field` = 現場モード / `mode:material` = 倉庫モード を読みます(倉庫参照は
いつでも可。ほかのツールの権限の文字列は読まずにそのまま)。`権限` 列のライン名(L-1・LVC・HVC・機側・NS1・AIM。正規の呼び名だけ。全角半角は同じ字)からは**担当ライン**も決めます(`kanban/line_names.py`。日報と同じ定義)。当てはまる行が無い端末は
**現場モードだけ**です。行はマスタ管理の「アクセス権限(梱包資材マスタ)」で足せます
(表が無ければ作ります)。詳しくは [docs/運用手順.md](docs/運用手順.md) の
「1.3.1 モードの選び方・変更のしかた」「1.3.1.1 アクセス権限」を参照してください。

設定画面は用ごとに 9 つのタブに分かれています ── この端末 / 接続先 /
マスタ管理 / 看板集計 / 取り込みの状態 / 記録 / ファイルの場所 / パスワード認証 / 配布設定。
「記録」では、エラー・断った操作・画面のエラーを端末・入力・**原因の連鎖・直前の操作**つきで探して開け、**なぜなぜ分析シート**の下書きを作れます。画面のエラーには**記録番号**が出ます([docs/運用手順.md](docs/運用手順.md) の「4.1.1」)。
「ファイルの場所」には、**複数の PC で共有するファイル**(看板マスタ・看板履歴・梱包資材マスタ)と、
**この PC だけに置いて引き継ぐファイル**(設定ファイル・手元の SQLite・CSV の書き出し先・ログなど)を
分けて出します。
「看板集計」では、出した日・届いた日(赤を消した日)から、何日で届いたか(平均・最短・最長)・
次に出すまで何日か・週/月に何回出したか・ライン別月別の提出率(グラフ)を出し、CSV に書き出せます
(詳しくは [docs/運用手順.md](docs/運用手順.md) の「1.3.4 看板集計」)。

Access のほうが新しいときは、**Access をまるごと変換して差し替えずに**、設定 →「マスタ管理」の
「Access の最新で表の中身を入れ替える」を使ってください(両方にある表の中身だけを入れ替え、
看板履歴・看板コメント・看板の状態は残します。[docs/運用手順.md](docs/運用手順.md) の「1.3.3」)。

看板の右端の 💬 で、倉庫と現場が看板ごとにコメントをやり取りできます(相手には未読の印と帯が出て、
届いたら片付きます。既読は倉庫どうし・そのラインの現場どうしで共有し、書いた側には「既読」が出ます。[docs/運用手順.md](docs/運用手順.md) の「3.7.2」)。
「パスワード認証」で認証すると、解除されるまで(「認証を解除する」・30 分操作なし・
アプリを閉じる)守られた操作でパスワードを訊きません。

## 複数ライン(複数端末)での運用

構成は上の図の通り、**各端末がそれぞれローカル SQLite を持ち、共有 SQLite を
介して間接的につながる**というものです。`sqlite_path` を変更する必要は
ありません。この構成での複数端末間アクセスは次のように動きます。

* ある端末の操作 → その端末のローカル SQLite → 数秒〜60 秒以内に共有DBへ反映
* 他端末は 30 秒ごと(または「↻ いま取り込む」)に共有DBを読み直し、
  他ラインの発注・発送状況を自分のローカル SQLite へ取り込む

複数端末が同時に読み書きする相手は **共有 SQLite 1 つ**であり、そこは
SQLite 自身のロックと、ロック競合時のリトライに任せています
(`kanban/db/shared.py` に VBA と同じ 3 回・1/2/3 秒のリトライを実装)。
ローカル SQLite はどの端末のプロセスからも 1 つしか触られないため、
SQLite の「書き込みは 1 プロセスずつ」という制約が複数端末間で問題になる
場面はありません。

> **導入前に必ず検証してください。** 正データが共有フォルダ上の SQLite に
> なったため、**その共有フォルダでファイルロックが正しく効くかどうかが
> 直接効いてきます。** SQLite は公式にネットワークファイルシステム上での
> 使用を推奨していません(SMB/NFS 実装によってはファイルロックが不完全な
> 場合がある)。`tools/check_shared_lock.py` で実環境のロック挙動を確かめ、
> **不一致が出た共有フォルダは使わないでください。** 手順は
> [docs/運用手順.md](docs/運用手順.md) の 1.2.2 にあります。

手元での工夫は次のとおりです。

* **WAL を使わない。** WAL は共有メモリ(`-shm`)を要求しますが SMB には
  それが無く、共有フォルダに置いた WAL のファイルは読むことすらできません
* 読むときは共有ファイルを直接開かず、**手元へ写してから**読む
  (中身が変わっていなければ写し直さない)
* 書き込みは 1 文ずつ自動コミットし、長く掴み続けない

### 同じ端末で 2 つ開かない

**本体(`pythonw.exe`)もブラウザのタブも、1 つだけです。**

* **本体**: 起動時に全モードのロックを見て、別のモード・別の版が動いて
  いれば終わらせてから立て直します(`launch_guard.py`)
* **画面**: タブを 2 枚開いても、押せるのは 1 枚だけです。2 枚目には
  「この画面では操作できません」と出し、`こちらの画面を使う` で持ち主を
  移せます(`kanban/screen.py`)

2 枚とも押せると、同じ看板を 2 画面で取り合い、片方が古い盤のまま押して
しまうためです。詳しくは [docs/移行仕様.md](docs/移行仕様.md) の 3.8.1 と
3.8.2 を参照してください。

## dbkit(DB 汎用部品)について

`dbkit/` は kanban 専用ではなく、他の VBA→Python 移行プロジェクトでも
そのまま持っていける「プロジェクトのスキーマ・業務ルールを一切知らない」
DB まわりの部品を集めたパッケージです。kanban 側は次の 2 か所で実際に
使っています。

* `kanban/db/store.py` の `is_lock_error`(SQLite のロック競合判定)は
  `dbkit.sqlite_toolkit.is_lock_error` をそのまま使う。
* `kanban/db/sync.py` の `Exporter` / `Importer`(定期書き戻し・定期取り込み
  のバックグラウンドスレッド)は `dbkit.periodic.PeriodicTask` の薄いラッパー。
* `dbkit.logging_utils` は dbkit 側のログを `kanban/applog.py` の出力先へ
  合流させるための受け口。dbkit が kanban を知らないまま、ログだけ 1 か所に
  集まる。

**正データを Access から共有 SQLite へ移したときに、ACE OLEDB / ODBC 経由の
接続部品(`dbkit/access_odbc.py`、`kanban/accdb/` の各ブリッジ)は削除しました。**
外部ドライバも `cscript.exe` も要らなくなったためです。`kanban/accdb/` に
残っているのは、初回の変換で `.accdb` を読むためのリーダーと型定義だけです。

書き戻しは kanban 側の `sync.py`(`export_pending` / `Exporter`)の独自実装
です。「行が確定したら 1 回だけ INSERT する」追記型ではなく、「発注/発送
ボタンで同じ行の同じ列を何度も UPDATE し続ける」状態更新型なので、他端末との
**列単位**の競合保護(`dirty_columns`。現場が発注列を、倉庫が発送列を、同じ行の
別々の列に同時に書いても互いを上書きしない仕組み)を持たせる必要があります。

## テスト

```bash
python -m unittest discover -s tests

# 実際の .accdb を使った検証も行う場合(初回変換のリーダーの確認)
KANBAN_TEST_ACCDB=/path/to/看板マスタ.accdb python -m unittest discover -s tests

# デスクトップ版(外枠の Rust)
cd src-tauri && cargo test
```

**画面も画面を開かずに試験します**(`tests/test_web_app.py`)。Flask の
`test_client` で経路を叩くので、仮想ディスプレイは要りません。Flask が
入っていない環境では、そのぶんだけスキップされます。
